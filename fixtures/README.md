# fixtures —— 测试固件

owner：**A**

---

## 为什么固件由 A 持有

固件是**三人之间的解耦点**，不是某个人的测试数据。

- `golden-state/` 让 C 不必等控制平面跑起来
- `sample-project/` 让 B 有真实输入可测
- 两者都要通过 `contracts` 的 schema 校验——**所以它们同时是契约的活体验证**

固件写错，三个人一起走偏。所以它跟契约同属一个 owner。

---

## golden-state/ —— 状态快照

`.codentum/` 目录在某一时刻的完整状态。C 拿它渲染，A 拿它测调和循环，B 拿它测上下文装配。

**第 0 周必须产出 ≥3 个**，覆盖这几种形态：

| 快照 | 形态 | 主要验什么 |
|---|---|---|
| `empty/` | 刚初始化，什么都没有 | ★ 空态不崩（最常被忘的用例） |
| `mid-flight/` | 多个 packet 并行中，有锁占用、有排队 | 主路径渲染 |
| `blocked/` | 有卡住的 packet、待审批项、超预算告警 | 异常态呈现 |

建议再加：`done/`（全部完成，用于交付页）、`large/`（几百个节点，用于性能）。

**每个快照目录里放一份 `NOTE.md`**：这个快照代表什么情况、是怎么产生的、哪些字段是关键。没有这个，半年后没人知道为什么 `budget_remaining` 是负数。

---

## sample-project/ —— 样例被开发项目

给系统去开发的**输入**：一个真实但小的软件需求。

选型要求：

```
□ 小到能在一次 Demo 里跑完
□ ★ 大到需要多个模块并行 —— 否则验不到并行安全，而并行安全是全案的核心论证
□ 有明确的、机器可判定的验收标准
□ 不依赖外部账号/付费服务（否则冷启动测试跑不了）
```

> ⚠️ **样例太简单是最容易犯的错。** 单模块任务跑通了，什么都没证明——
> 路径锁、契约冻结、并行调度、集成门禁这些机制全都没被触发。

---

## 硬约束

1. **所有固件必须能通过 `contracts` 的 schema 校验**，并进 CI。
   固件与契约脱节 → 基于它写的测试全部失去意义，且不报错。
2. **固件里不许有真实凭证。** 需要凭证的地方用明显的占位符（`REPLACE_ME_xxx`）。
3. **快照是手工构造或从真实运行导出的，不是随手编的。** 编的会缺字段，缺字段的地方正好是最容易出 bug 的地方。
4. **改固件要说明改了什么**——它是三个人的共同基准，静默改动会让别人的测试莫名其妙地红/绿。
