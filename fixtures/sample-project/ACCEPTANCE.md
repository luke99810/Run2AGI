# 期望验收 —— 对照用，**不是给系统的输入**

> 用途：拿它对照 QA 生成的验收谓词、对照 Planner 切出来的 packet。
> ⚠️ **不要把这份文件喂给系统。** 它是标尺，不是输入 —— 喂进去就没有东西可对照了。

---

## 一、★ 这份需求为什么合格：它能逼出真并行

`fixtures/sample-project/README.md` 定的硬判据是：

> **这个需求能不能自然地切成 ≥3 个可并行的模块，且它们之间有真实的契约依赖？**

能。而且切分是需求本身自带的，不是我们硬凑的：

```
                    ┌─ 契约（数据模型 + 模块间接口）
                    │   architect 独占，串行，所有人等它
                    ↓
     ┌──────────────┼──────────────┐
     │              │              │
  任务模块       日记模块      鼓励语模块      ★ 三个真并行，路径互不相交
  src/tasks/     src/journal/  src/encourage/
     │              │              │
     └──────────────┼──────────────┘
                    ↓
                前端整合
                src/ui/
```

**三个模块之间没有任何共享路径** —— 这正是路径锁要保证的东西，而且这次它有真东西可锁。

### 为什么这个需求比"带认证的记账应用"更适合做 Demo

之前的候选倾向是记账/待办类。这份更好，三个原因：

1. **并行是天然的，不是设计出来的。** 任务、日记、鼓励语是三件语义上就无关的事，
   一个正常的 Planner 也会这么切。用一个需要刻意拆分才能并行的需求，
   等于在 Demo 里替 Planner 作弊。
2. **鼓励语模块埋了一条真实的跨模块依赖**（见 §三），可以触发 P1 的依赖通道演示。
3. **没有外部依赖**：不用登录、不联网、本地存储 —— 冷启动复现测试跑得了。
   带认证的应用要么得接第三方，要么得自己造一套，两条都是噪声。

### ⚠️ 一个诚实的风险

这个需求**偏简单**。六条不变量的仪式成本（写 packet、锁路径、备证据、过门禁）
放在这种规模的项目上，比例上会显得重。

这正是 `docs/项目进展与记忆.md` §十一列的第 3 条经验性未知 ——「最小有效任务尺度」。
**Demo 时要主动讲这一点**，而不是等评审问「你们这套东西是不是杀鸡用牛刀」。
可用的回答方向：仪式成本是固定的，项目越大摊得越薄；小项目上跑通是为了让**流程本身**
可被完整观察，不是主张这个规模值得上这套流程。

## 二、期望的模块切分与验收谓词

### 模块 1 · 任务（`src/tasks/**`）

| 期望的验收谓词 | 机器可判定 |
|---|---|
| 能新增一条当天任务，重启后仍在 | ✅ |
| 任务分「必做 / 可选」两类，且能分别筛出来 | ✅ |
| 能把任务标记为完成，且可撤销 | ✅ |
| 能查询某一天的「完成数 / 总数」 | ✅ |
| 能查询最近 7 天每天的完成数 | ✅ |

### 模块 2 · 日记（`src/journal/**`）

| 期望的验收谓词 | 机器可判定 |
|---|---|
| 能为某一天写一段自由文本并保存 | ✅ |
| 同一天重复写入是**更新**而不是新增第二条 | ✅ |
| 能按日期倒序列出历史日记 | ✅ |
| 能按日期取出某一天的日记 | ✅ |

### 模块 3 · 鼓励语（`src/encourage/**`）

| 期望的验收谓词 | 机器可判定 |
|---|---|
| 给定「完成数 / 总数」，返回一条鼓励语 | ✅ |
| **完成数为 0 时返回的话不含负面措辞**（给一份禁用词表来判定） | ✅ |
| 同一输入连续调用不会连续返回同一条 | ✅ |
| 连续使用天数达到阈值时，返回的话会提及这一点 | ✅ |

> ★ 第二条是这个模块**唯一真正难判定**的地方。需求原话是「也别说风凉话」——
> 这是主观的。把它转成「不含禁用词表里的词」是一次**从主观到可判定的转换**，
> 正是 QA 该做的事。**看 QA 有没有做这个转换，是这个 packet 最值得观察的点。**

### 模块 4 · 前端整合（`src/ui/**`）

依赖前三个模块的契约。判据：三块内容都能在界面上看到并操作。

## 三、★ 埋在需求里的一条跨模块依赖（用来演示 P1 的依赖通道）

鼓励语要「我今天完成得不错的时候夸我一下」—— 这意味着
**鼓励语模块需要读任务模块的完成数据**。

这是一次真实的跨模块依赖请求。期望的正确处理是：

- ❌ **不是**让 encourage 直接 import tasks 的内部实现（那会让两个模块耦合，
  路径锁保证的独立性就白搭了）
- ✅ **而是**通过契约层定义的接口拿数据 —— 由 architect 在契约里加一个只读查询

> P1 期的判据之一是「一次依赖请求被自动策略正确拦截并给出替代」。
> **这条依赖就是那个演示素材，需求里天然带着，不用另造。**

## 四、★ 故意埋的四个模糊点 —— 用来评测 Intake

Intake 是全案公认最薄的一环（§十一 经验性未知第 5 条）。
这份需求里**故意留了四处真实的模糊**，用来看 Intake 会不会问出来。

| # | 模糊点 | 需求原话 | 期望 Intake 的反应 |
|---|---|---|---|
| 1 | **任务是否跨天延续** | 「每天早上我会列一下今天要做的几件事」 | 没做完的任务第二天还在吗？还是每天清空重来？**这直接决定数据模型**，必须问 |
| 2 | **「恰到好处的鼓励」的判定标准** | 「不要那种很假的心灵鸡汤，也别太夸张」 | 主观描述。应追问出可判定的形式（禁用词？长度上限？频率上限？） |
| 3 | **日记与任务是否同屏** | 需求里完全没说 | 界面结构的关键决策。**没问就是漏了**，问了说明它在主动补全需求 |
| 4 | **「连着几天都在用」的阈值** | 「连着几天」 | 3 天？7 天？不问就得自己拍一个，拍了要记进决策日志 |

### 评分方式

- 问出 **≥2 条** → Intake 及格
- 问出 **第 1 条** → 加分（它是四条里唯一会导致返工的，其他三条猜错了改起来便宜）
- **一条都没问，直接开始拆 packet** → 🔴 这正是我们担心的「建错东西」，
  要记进 HistoricTask，不要粉饰

> ★ 这一节的价值超出本样例本身：**它给了 Intake 一个可判定的评测锚点**，
> 而在此之前 Intake 的好坏完全是主观判断。

## 五、不在范围内（wont_have）

停止规则要求「每个方向开工前先写三条 wont_have」。这里写四条：

```
□ 不做用户系统 / 登录 / 多用户 —— 需求明确说了本地、不登录
□ 不做云同步 / 备份 —— 需求明确拒绝了（"不太想传到别人服务器上"）
□ 不做提醒 / 通知 / 日程排期 —— 需求里一个字都没提，是我们容易自己加戏的地方
□ 不做数据分析图表 —— "看到最近一周完成得怎么样"用列表就能满足，
  上图表是范围膨胀。★ 这条特别要盯住，因为它听起来很合理
```

> 最后一条是给我们自己的提醒：**范围膨胀是这个项目已知的最大风险**（非技术类）。
> 「看起来很合理的加法」正是它最常见的形态。
