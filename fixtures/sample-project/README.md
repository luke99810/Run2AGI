# sample-project —— 样例被开发项目

给 Codentum **去开发**的那个软件需求。它是系统的输入，不是系统的一部分。

---

## 选型要求

```
□ 小到能在一次 Demo 里跑完
□ ★ 大到需要多个模块并行
□ 有明确的、机器可判定的验收标准
□ 不依赖外部账号或付费服务（否则冷启动测试跑不了）
□ 领域常见 —— 契约优先的打法在成熟领域最强，Demo 不该同时赌一个陌生领域
```

### ⚠️ 最容易犯的错：选得太简单

单模块的小任务跑通了，**什么都没证明**——路径锁没被争用过，契约冻结没被挑战过，并行调度退化成串行，集成门禁没有东西可拦。

而并行安全恰恰是全案最核心的论证。**样例必须逼出并行。**

判据：**这个需求能不能自然地切成 ≥3 个可并行的模块，且它们之间有真实的契约依赖？** 不能就换一个。

---

## 目录里应该有什么

```
sample-project/
├── REQUIREMENT.md       ★ 人话写的需求 —— 这是 Intake 的真实输入
├── ACCEPTANCE.md        期望的验收标准（用来对照 QA 生成的对不对）
└── expected/            （可选）参考实现，用于对比而非替代
```

**`REQUIREMENT.md` 要用人话写，带着真实需求该有的模糊。**

写得像规格说明书就作弊了——Intake 的价值正是"把人话变成可判定的需求"，给它一份已经可判定的输入，等于把最难的一段跳过去了。而 Intake 端本来就是全案里最薄的一环，不该再被 Demo 掩盖。

---

## ✅ 已定（2026-08-04）：日常规划小工具

**选定需求**：一个本地的每日规划工具 —— 记录每天任务、更新完成情况、写日记，
并根据完成情况给出正向反馈。

| 文件 | 内容 |
|---|---|
| [`REQUIREMENT.md`](REQUIREMENT.md) | ★ **Intake 的真实输入**。人话写的，故意留着四处模糊 |
| [`ACCEPTANCE.md`](ACCEPTANCE.md) | 期望验收 + 期望切分 + 埋的模糊点清单。**不给系统看**，是标尺 |

### 为什么选它

**核心判据是「能不能自然切成 ≥3 个可并行模块」—— 它能，而且切分是需求自带的：**

```
任务模块 src/tasks/  ‖  日记模块 src/journal/  ‖  鼓励语模块 src/encourage/
                三者路径互不相交，共同依赖 architect 先冻结的契约
```

三件事在语义上本来就无关，**一个正常的 Planner 也会这么切** ——
不需要刻意拆分才能并行。用一个"必须刻意拆才并行"的需求，等于在 Demo 里替 Planner 作弊。

另外三条：

- **鼓励语要读任务完成数据** → 天然带一条跨模块依赖，正好是 P1「依赖请求被拦截并给替代」的演示素材，不用另造
- **零外部依赖**（不登录、不联网、本地存储）→ 冷启动复现测试跑得了
- **领域极常见** → 契约优先在成熟领域最强，Demo 不该同时赌一个陌生领域

### 否决的候选

| 候选 | 否决理由 |
|---|---|
| 带认证的记账应用 | 认证要么接第三方（破坏冷启动测试），要么自己造一套（大量与论证无关的噪声）。**它的复杂度落在错误的地方** |
| 团队待办 Web 应用 | 多用户带来权限模型，那是另一个话题；且需要服务端，冷启动链路变长 |
| 纯 CLI 小工具 | 太小，切不出 3 个并行模块 —— 犯的正是上面「选得太简单」那条错 |

### ⚠️ 已知的弱点（写在前面，不等评审问）

**这个需求偏简单**，六条不变量的仪式成本放在这个规模上，比例会显得重。

这正是设计里列的经验性未知之一「最小有效任务尺度」。Demo 时主动讲，
不要粉饰成「刚刚好」。可用的方向：仪式成本固定，项目越大摊得越薄；
小项目上跑通是为了让**流程本身可被完整观察**，不是主张这个规模值得上这套流程。
