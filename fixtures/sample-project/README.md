# sample-project —— 样例被开发项目

给 Codentum **去开发**的那个软件需求。它是系统的输入，不是系统的一部分。

---

## 选型要求

```
□ 小到能在一次 Demo 里跑完
□ ★ 大到需要多个模块并行
□ 有明确的、机器可判定的验收标准
□ 不依赖外部账号或付费服务（否则冷启动测试跑不了）
□ 领域常见 —— 契约优先的打法在成熟领域最强，Demo 不该同时赌一个陌生领域
```

### ⚠️ 最容易犯的错：选得太简单

单模块的小任务跑通了，**什么都没证明**——路径锁没被争用过，契约冻结没被挑战过，并行调度退化成串行，集成门禁没有东西可拦。

而并行安全恰恰是全案最核心的论证。**样例必须逼出并行。**

判据：**这个需求能不能自然地切成 ≥3 个可并行的模块，且它们之间有真实的契约依赖？** 不能就换一个。

---

## 目录里应该有什么

```
sample-project/
├── REQUIREMENT.md       ★ 人话写的需求 —— 这是 Intake 的真实输入
├── ACCEPTANCE.md        期望的验收标准（用来对照 QA 生成的对不对）
└── expected/            （可选）参考实现，用于对比而非替代
```

**`REQUIREMENT.md` 要用人话写，带着真实需求该有的模糊。**

写得像规格说明书就作弊了——Intake 的价值正是"把人话变成可判定的需求"，给它一份已经可判定的输入，等于把最难的一段跳过去了。而 Intake 端本来就是全案里最薄的一环，不该再被 Demo 掩盖。
