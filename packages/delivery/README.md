# delivery —— 交付链路

从"代码写完了"到"用户手里能跑起来"。

---

## 职责

**做什么**：一次性凭证收集（Provisioning）、凭证泄漏扫描、打包、冷启动复现测试。

**明确不做什么**：
- ✗ 不调用模型（凭证相关的路径上出现模型 = 凭证可能进上下文）
- ✗ 不依赖 `desktop`（★ 交付链路必须能在无 GUI 的 CI 里跑通）

**为什么这是 C 的活而不是"顺手加的"**：这是**产品与玩具的分界线**。能跑出代码的 Demo 很多，能把成果交到用户手里、在干净机器上一次跑通的很少。

| 目录 | 职责 |

---

## 冷启动复现测试是什么

在一个**干净容器**里，只拿交付产物 + Provisioning 收集到的凭证，从零跑到能用。

它验的不是代码对不对，是**"能不能交付"**。绝大多数"在我机器上是好的"死在这一步：漏装的依赖、写死的本机路径、没记录的环境变量、手工执行过但没写进脚本的那一步。

容器定义在 `docker/cold-start/`。

## 完成定义

```
□ Provisioning 表单能收集凭证并本地加密存储；★ 磁盘上抓不到明文
□ secret-scan 能扫出：工作区 + ★ git 历史 里的密钥
□ secret-scan 在测试仓库上：真密钥全中，假阳性可接受范围内
□ ★ 打包产物在干净容器里冷启动跑通，全程零手工步骤
□ ★ 整条链路在无 GUI 环境跑通（不依赖 desktop）
```

---

## 硬约束

1. **secret-scan 是不可豁免的门禁。** 没有 `--force`，没有 `--skip`，没有"这次先过一下"。
   **一旦可豁免，它在最需要它的那天一定会被豁免。**

2. **凭证本地加密存储，永不上传。** 不进日志，不进上下文，不进证据文件，不进错误堆栈。

3. **★ 我们自己推送前也必须过 secret-scan——包括 git 历史，不只是工作区。**
   自己的产品自己先用。历史里的密钥不会因为你后来删了文件就消失，需要 `git filter-repo` 或 BFG 才能清掉。
   > 推 Gitee 之前务必先扫一遍——这个项目组之前踩过这个坑。

4. **这个 package 里不调用模型。** 凭证经过的路径上不能有模型。

5. **冷启动测试不许"手工先装一下再跑"。** 那样它就什么都没验到了。
