# desktop —— 桌面控制台

Electron 应用。★ **对系统状态零写权限——状态纯读端。** 本地需求草稿和附件引用
manifest 写入 Electron `userData` 私有目录；附件内容保留在用户选择的原位置，不复制到
应用目录。两者都不写项目的 `.codentum`，也不绕过控制平面。

---

## 职责

**做什么**：订阅状态，做投影。让人看见 Agent 团队在干什么、卡在哪、花了多少钱。

**明确不做什么**：
- ✗ **不写任何系统状态**。所有写入走控制平面的正式动作，不从 UI 抄近路
- ✗ 不含业务逻辑（判定在 `control-plane/gates`，UI 只渲染判定结果）
- ✗ 不调用模型

**为什么是纯读端**：Console 挂掉，系统照常跑。这是架构属性，也是**这个 package 的 owner 犯错不会传播**的原因——C 拿桌面端不是因为它简单，是因为它爆炸半径最小。

## 归属

| | |
|---|---|
| owner | **C** |
| 评审 | B |
| 依赖 | `contracts`（类型） + `fixtures/golden-state/`（数据） |

### ★ 不依赖 control-plane 的实现

C **第一天就能开工**，不用等 A 把调度跑起来。靠的是 `fixtures/golden-state/` 里的状态快照。

这是系统里"前端依赖 mock 不依赖实现"的同一招——**前后端并联的原则同样适用于人**。

> 没有这个解耦点，C 会空等两周，然后在最后一周被压着赶工。
> **这是三人团队最常见的死法。**

## 完成定义

```
□ ★ 在 3 个 golden-state 快照上渲染结果与预期截图一致
□ ★ 空 graph.json / 半截状态 / 超大图 三种边界输入不崩
□ ★ grep 全目录：无任何对系统状态文件的写操作
□ mock 数据源与真数据源实现同一接口，切换只改一处配置
□ 上面八个模块各有可用页面（可以先接 mock）
□ 无模型调用
```

> 注意"渲染结果与预期截图一致"这种写法——**完成定义必须机器可判定**。
> "看板做得好"不是完成定义。

---

## 硬约束

1. **零写权限。** 所有写入走控制平面的正式动作。
   从 UI 直接改状态文件，会绕过准入校验和审计链——**六条不变量全部失效**。
   本地未派单草稿不属于系统状态；它只能写应用私有目录，派单时必须走正式引擎命令。

2. **崩溃不能影响系统。** 主进程挂掉，控制平面照常推进。

3. **不重新实现判定逻辑。** 门禁怎么判是 `control-plane/gates` 的事，UI 只渲染结果。
   在 UI 里"顺手也判一下"会出现两套判定，且不一致时以哪个为准说不清。

4. **mock 与真实必须同接口。** 不同接口 = 接真数据时全部重写。

5. **成本显示用货币。** 分词器差异 ~30%，异构路由下 token 数不可比。
