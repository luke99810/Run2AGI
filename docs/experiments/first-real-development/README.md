### 模型实际做了什么

```
轮 1  write_file(workspace/subscriptions.py)      → 已写入 195 字节
轮 2  write_file(workspace/subscriptions.py)      → 已写入 249 字节（自己改进了一版）
轮 3  run_tests(["python","-m","pytest","workspace"]) → 退出码 5，没收集到测试
轮 4  read_file(tests/test_subscriptions.py)      → 文件不存在（如实返回）
轮 5  （无工具调用）承认没有测试文件，收尾
```

★ 这五轮里有三件事值得看：

1. **它写完之后自己去跑测试** —— 不是被要求的那一步，是工具面给了它这个能力
2. **测试失败后它去读文件确认** —— 对失败作出了反应，而不是宣布成功
3. **文件不存在时工具如实返回**，它据此承认了缺口，没有编造

## 不能夸大的三点

**① 模型只完成了规格的一半。** 需求要两个文件（实现 + 测试），
它只写了实现。第 5 轮它自己承认了这一点 —— 这是**模型引导**的问题，
不是平台能力的问题，但产物确实不完整。

**② packet 仍然被 `accepted` 了。** 因为验收标准是引擎生成的占位
（`kind: manual`，Intake 尚未实现），只要有真实证据就通过。
**「写了 1 个文件」和「完成了需求」之间的差距，当前的验收判据还判不出来。**
这正是 §二十二 说的那件事的下一层。

**③ 没有 Planner。** 一个需求仍然只产出一个 packet，
谈不上「拆解给多个 Agent 并行」。多 Agent 协同目前体现在
角色隔离与工具面派生上，不体现在任务拆分上。

## 途中修掉的三个缺陷

| # | 缺陷 | 现象 |
|---|---|---|
| 1 | 空 `arguments` 被判畸形 JSON | 模型调无参数工具（`list_files`）时整轮会话打成 `model_error`。**一次本该成功的开发因为解析器过严而判失败** |
| 2 | `request_help` 返回 ok=True | 等于告诉模型「求助成功了，你继续」→ 它每轮重复求助，12 轮烧完、0 文件。已改为**终止循环**：求助的语义是「我需要人来决定」 |
| 3 | 发了 `content=""` 的 assistant 消息 | 百炼连续两次返回 500 internal_error，都在多轮的第 2–3 轮。补上工具调用摘要后不再复现 |

★ 第 2 条是设计错误，不是编码错误 —— 我把「求助」当成了一次普通工具调用。
