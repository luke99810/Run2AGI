# 「验收通过了，而验收标准是空的」—— 2026-08-12 实测

这两个文件是**模型真实写出来的**，未编辑。

## 发生了什么

一句需求 → 工具循环 → 两个文件落盘 → 验收谓词 `python -m pytest workspace -q`
**退出码 0** → packet 被判 `accepted`。

日志原文：

```
wp-6cda2edec6ce: review → accepted（门禁 'review' 通过：验收通过：
`python -m pytest workspace -q` 退出码 0
.                                        [100%]
1 passed in 0.01s）
```

看起来一切正常。直到你打开那个测试文件：

```python
def test_example():
    assert True
```

**实现是对的。测试什么都没验证。而验收通过了。**

---

## 这是那条线的第五层

| 日期 | 缺陷 |
|---|---|
| 08-09 | 拿控制面自己的簿记当证据 |
| 08-10 | 门禁层同一个洞 |
| 08-11 | 说完成了但一个文件没改 |
| 08-12 上午 | 改了文件，但没达到验收标准 |
| **08-12 下午** | **达到了验收标准，但验收标准是空的** |

前四层都能靠「看有没有 X」解决。这一层不能 ——

> **任何「检查测试内容」的做法都是模式匹配**：`assert True` 能查出来，
> `import x` 之后再 `assert True` 就查不出来，而模型总能绕过。

---

## 解法：把实现移走，测试必须变红

```
1. 验收谓词跑一遍  → 必须绿
2. 把实现文件临时移走
3. 再跑一遍        → ★ 必须红
4. 还原（在 finally 里）
```

这是**因果检验**，不是模式匹配：测试若真的在验证实现，实现没了它必然红。绕不过去。

★ 它恰好是本项目那句口号的可执行版本：

> **「如果它坏了，哪条测试会变红？」**

用模型真实写出的这份 `assert True` 跑一遍新门禁：

```
★ 门禁判决：拒绝

验收未通过：**验收测试是空的**。
把实现（subscriptions.py）移走之后，验收谓词仍然退出码 0 ——
说明这些测试根本没有验证实现。

★ 判据是「如果它坏了，哪条测试会变红」。现在的答案是：一条都不会。
```

复现：`pytest packages/engine/tests/test_acceptance.py -q -k vacuous`

---

## 局限（必须说清楚）

**① 只在实现与测试分文件时有效。** 两者写在同一个文件里时这一层不生效。

**② 更深的问题没有被解决：验收标准仍然是执行者自己写的。**

契约的 I2 说「验收的作者不能是执行者自己」，而门禁检查的是
`packet.acceptance.authoredBy != packet.role` —— 那是一个**元数据字段**。
实际写测试文件的仍然是 coder。

> **不变量在名义上满足，在实质上被绕过。**

真正的解法是结构性的：QA 必须在 coder 之前、在独立的 packet 里出题。
那需要 Planner（一个需求 → 多个 packet），而 Planner 还没有。

**这个缺口记在案，不假装它不存在。**
