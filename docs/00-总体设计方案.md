# Codentum · 自进化软件开发多 Agent 系统 · 总体设计方案

> **产品形态**：一款**本地优先的桌面软件**。你输入一个软件需求，它编排一支 Agent 团队完成开发，
> 全过程在可视化界面中可见，最终一次性收集凭证与素材，做生产级测试并打包交付。
>
> **命名说明**：**Codentum = Code + Momentum**
> **Code** 锚定软件开发这一赛道；**Momentum** 传递自驱动、自进化的持续成长势能，
> 暗合多智能体协同产生的 1+1>2 的涌现动力。
>
> 这个名字还有一层恰好成立的隐喻：动量 = 质量 × 速度，且在无外力干扰时**守恒**。
> 对应到本系统——能力沉淀是质量，交付速度是速度；而 L4 评测锚点保证了
> **已经获得的能力不会在后续迭代中流失**。进化是单调的，这正是"守恒"在工程上的含义。
>
> 本文档为正式开发的总指导方针

## 产品形态与交付模式

### 它是一款桌面软件

对标 OpenClaw / OpenWorker / WorkBuddy 这一类**本地运行的 AI 工作台**，而不是云端 SaaS。

| 维度 | 选择 | 理由 |
|---|---|---|
| **运行位置** | 用户本机 | 代码与凭证不出本机，企业与个人开发者都能用 |
| **模型接入** | **用户自带 API Key**（百炼 / Anthropic / OpenAI / 本地 Ollama 皆可） | 成本自负、无锁定、我们不承担推理费用 |
| **数据** | 全部本地：Git 仓库 + SQLite + 本地文件 | 零服务端运维负担 |
| **界面** | Electron/Tauri 壳 + Web 前端 | 可视化界面**就是产品本身**，不是附属的监控面板 |
| **分发** | 安装包，下载即用 | 桌面产品的基本要求 |

> **"零服务端运维"是约束不是偏好**：这个产品若需要我们维护后端服务，一个小团队就无法长期维持。
> 本地优先是唯一可持续的形态，且恰好满足企业最在意的一点——**代码不出本机**。

### 双运行模式（同一套控制平面）

```
┌─ Solo 模式（默认，开箱即用）────────────────────────────────┐
│  控制平面：本地单进程                                        │
│  Worker：  本地子进程（复用 Claude Code / 本地 Agent runtime）│
│  状态：    本地 Git 仓库                                     │
│  存储：    本地文件系统 + SQLite(+向量扩展)                   │
│  通信：    进程内事件 + 本地 WebSocket                        │
│  依赖：    ★ 零外部依赖，装完就能跑                           │
└────────────────────────────────────────────────────────────┘
┌─ Team 模式（可选，企业/多人）──────────────────────────────┐
│  控制平面：同一套代码，不改一行                               │
│  Worker：  AgentTeams（Manager-Workers + Matrix + 多 runtime）│
│  状态：    Git 远程仓库                                      │
│  存储：    MinIO/S3 + PostgreSQL+pgvector                    │
│  通信：    Matrix 房间（人可旁听/打断）+ Higress 凭证隔离      │
│  依赖：    Docker                                            │
└────────────────────────────────────────────────────────────┘
```

**两种模式共用同一个控制平面，一行代码都不用改。** 这正是"状态放在 Git 仓库里"的最大红利——控制平面不依赖任何服务，它只是在读写文件，所以在笔记本上跑和在集群上跑是一回事。Worker 与存储通过四个接口抽象（`WorkerRuntime` / `ArtifactStore` / `MemoryIndex` / `ModelGateway`），模式切换即换实现。

### 交互主线：三次对话，一次填表

产品体验被刻意压缩成四个人机接触点，其余全自动：

```
① 说需求        你输入一句话或一份 PRD
                 ↓
② 澄清问答      系统主动提问（有限轮次，问到能写出验收场景为止）
                 ↓
③ ★ 确认开发计划书   做什么/不做什么/架构/拆解/排期/成本预估
                     你确认后才开工 —— 这是"井然有序、遵循规划"的落点
                 ↓
   ┌─────────── 自主开发（可视化界面可见全过程）───────────┐
   │  仅在需要仲裁/审批时批量打断，不逐个骚扰                 │
   └────────────────────────────────────────────────────┘
                 ↓
④ ★ 一次性填表   配置收集表：API Key、账号、邮箱、Logo、域名…
                 每项都说明为什么要、去哪弄、能不能不填
                 ↓
   生产级测试 → 打包交付
```

> **④ 是全流程唯一一次向你索要外部资源。** 开发期一律用 mock 与占位值，绝不中途停下来问你要 key。

### 开发计划书（开工前的确认物）

澄清结束后、写第一行代码之前，系统产出一份人可读的计划书供确认：

```
开发计划书
├── 要做什么          3-5 条 must_have，每条附验收场景
├── ★ 不做什么        wont_have 清单（防止你后来失望）
├── ★ 我的假设        未澄清项的显式假设，你可以逐条改
├── 技术选型与理由     含 ADR 摘要：为什么选它、否决了什么
├── 模块划分与并行度   能开几个 Coder 并行 —— 这是算出来的不是猜的
├── 任务拆解与依赖     甘特图形态
├── ★ 预计耗时         基于虚拟调度
├── ★ 预计成本         基于历史同类项目的 token 消耗
└── ★ 后期需要你提供    凭证与素材的预告清单（现在不填，让你有准备）
```

**"预计成本"和"后期需要你提供"是产品体验的关键**：用户自付 token，开工前知道大概烧多少钱、后面要准备什么，才敢按下开始。

### 任务文档：一份数据，两种形态

用户看到的"任务文档"与系统执行的 WorkPacket **是同一份数据的两种渲染**：

```
WorkPacket (YAML, 机器可读)  ──渲染──▶  任务文档 (Markdown, 人可读)
  · 验收谓词                              · 这个任务要做什么
  · owns_paths / depends_on               · 涉及哪些文件、依赖谁
  · budget                                · 预计耗时与成本
  · 执行后回填的 evidence                  · 实际结果、遇到的问题、如何解决
```

**由同一份数据渲染，所以永远不会不一致**——这是"文档与实现脱节"这个老问题在本系统中不存在的原因。任务文档可在界面中直接阅读，也随交付包导出。项目级同理：`.codentum/` 的结构化状态（机器）↔ 开发计划书与交付报告（人）。

### 界面的两类模块

```
观测类（看系统在干什么）    甘特图 · 看板 · Agent 状态 · 依赖图 · 绿线
                            预算/成本仪表 · 溯源查询 · 进化曲线
管理类（配系统能干什么）    ★ Skills · ★ MCP · ★ 连接器 · 模型与成本
交互类（人的四个动作）      确认计划书 · 批量决策收件箱 · 审批卡片 · 配置收集表单
```

管理类三个模块（Skills / MCP / 连接器）是这个产品作为**可扩展工作台**的核心，详见 [Skill 体系与扩展生态](#skills) 与 [可视化控制台](#console)。

### 已确定的三项工程决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 桌面壳 | **Electron** | 生态成熟、上手快、一个人能搞定。Tauri 的体积优势要到产品化阶段才值得，届时再评估迁移 |
| Solo 模式的 Worker | **复用成熟编码 Agent**，不自研执行体 | 自研执行体是最容易陷进去的坑。我们的价值在控制平面，Coder 位应当可插拔 |
| 首个验证项目 | **全新小应用**（订阅记账工具） | 能完整走通 Greenfield 全流程，且交付物可对外展示；用自有项目有数据披露成本且外人无法验证 |

## 系统定位

### 一句话

**Codentum 是一套让多个 Agent 像一个工程组织那样协作、把软件从一句话需求做到可交付、并在过程中持续变强的基础设施。**

### 贯穿全文的逻辑主线

```
软件开发需要长期一致性、大量并行、且必须收敛
        │
        ▼
LLM 单点不可靠、无状态、且倾向走阻力最小路径
        │
        ▼
因此不能让 Agent 之间自由协商，必须有确定性骨架
        │
        ▼
骨架由三部分构成：
    状态的形状      (Graph 工程)
    状态的变化规则  (Loop 工程)
    状态变化的执行单位 (Harness 工程)
        │
        ▼
角色是骨架上的执行位点，由【权限】定义，不由【提示词】定义
        │
        ▼
运行中积累的经验，经与代码变更同构的流程回流到骨架的【可变部分】
骨架的【不变部分】只能由人修改
        │
        ▼
这就是"自进化"的确切含义
```

### 它做什么

| 能力 | 说明 |
|---|---|
| 接受五种输入 | 一句话想法 / 结构化需求 / 变更请求 / 缺陷 / 运行事件 |
| 主动澄清并出计划 | 有限轮次提问 → **开发计划书**（含并行度、耗时与成本预估）→ 人确认后开工 |
| 走完整 SDLC | Discovery → Design → Skeleton → Increment → Hardening → **Provisioning** → Launch |
| 多 Agent 真并行 | 并行度可计算，合并冲突结构上不可能 |
| 全过程可视 | 甘特图 / 看板 / Agent 状态 / 成本仪表 / 溯源查询 |
| 自修复与协助 | 四级阶梯：自修复 → Helper 求助 → 会诊 → 人工 |
| 分级测试 | 各 Agent 自测 + QA 全局测试 + **真实凭证的生产级测试** |
| 一次性收集配置 | 全流程唯一一次索要 API Key / 账号 / 素材，附申请路径与降级选项 |
| 打包交付 | 凭证不入产物 + 部署文档 + **冷启动复现测试** + 交付报告 |
| 持续自我改进 | 能力层可进化、可度量、可回滚 |
| 全程可审计 | 任意一行代码可回溯到需求、假设、决策与审批 |

### 它不做什么

```
✗ 不与编码 Agent 竞争 —— Coder 位可以直接插 Claude Code / Hermes / 任意编码 Agent
✗ 不替代人做产品决策 —— 需求矛盾、不可逆技术选型、生产变更一律升级
✗ 不追求全自动 —— 目标是让人的介入频率随规模【次线性增长】，不是归零
✗ 不做通用 Agent 平台 —— 它是软件开发这一个垂直场景的组织基础设施
✗ 不做云端 SaaS —— 本地优先，代码与凭证不出本机，我们不承担服务端运维
✗ 不代持用户凭证 —— 用户自带模型 Key；项目凭证本地加密存储，不上传任何地方
```

### 与编码 Agent 的关系

现在的编码 Agent 单点能力已经很强。团队引入后卡住的不是"写不出代码"，而是四件事：**经验不可继承、评审同源偏见、上下文成本失控、进化不可证伪**。Codentum 解决的是这四件事。

> 编码 Agent 是发动机，Codentum 是底盘、变速箱和仪表盘。

## 设计原理

### 从失败模式推导

架构不是先画图再填角色，而是从"多 Agent 写代码会怎么死"倒推。每一种死法逼出一个结构：

| 失败模式 | 逼出的结构 | 落在哪一章 |
|---|---|---|
| 靠对话同步状态 → 上下文一长即失忆、崩了无法恢复 | 状态外置为**仓库内的图** | 状态设计 |
| 让 LLM 自由拆任务 → 粒度不可控 | **WorkPacket + 确定性准入校验** | 状态设计 |
| 并行改代码 → 合并地狱 | **契约先行 + 路径独占** | 状态设计 |
| Agent 自称完成 | **机器可判定的验收谓词 + 证据** | 运行设计 |
| Agent 走阻力最小路径（改测试、改契约） | **评判权与被评判权分离，文件权限强制** | 角色体系 |
| 大爆炸集成 | **Walking Skeleton + 绿线不变量** | 端到端运行 |
| 经验在会话结束时丢失 | **三层记忆 + 经验晋升阶梯** | 记忆与知识 |

### 第一原理

> **多 Agent 系统的可靠性来自不变量，不来自提示词。**
>
> 凡是"在提示词里叮嘱 Agent 不要做 X"的地方，都应改成"在结构上让 X 做不到"。

推论：所有约束的实现优先级依次是——**不可见 > 无权限 > 被拦截 > 提示词劝阻**。让被约束的东西不进入视野，永远优于让它进入视野后拒绝访问，因为后者必然引发试探行为。

### 六条不变量

系统的骨架。角色、流程、工具都可换，这六条不能破。

| ID | 名称 | 内容 | 破坏后果 | 强制方式 |
|---|---|---|---|---|
| **I1** | 单写者 | 任一路径同一时刻只被一个 in_progress packet 拥有 | 合并冲突、互相覆盖 | 所有权图 + 准入校验 + git hook |
| **I2** | 验收可判定 | 每个 packet ≥1 条机器可判定的验收谓词 | Agent 自我宣布完成 | 准入校验器（确定性） |
| **I3** | 契约冻结 | 只有 Architect 能写 `contracts/`，Coder 只读 | 为让测试通过而偷改接口 | 只读挂载 + hook + Guardian |
| **I4** | 绿线 | main 任何时刻可构建、可部署、E2E 通过 | 集成崩溃，无可用回滚点 | 合入前在最新 main 重跑验收 |
| **I5** | 单会话闭合 | 一个 packet 必须在一个会话预算内完成 | 上下文溢出、成本失控 | 预算计数器 + 自动 Splitter |
| **I6** | 证据 | 状态推进必须附证据引用，声明不算 | 沉默失败、虚报完成 | 状态机转换校验 |

### 风险分配原则

> **把不可恢复的部分交给确定性代码，把可恢复的部分交给模型。**

| | 执行平面（模型） | 控制平面（代码） |
|---|---|---|
| 典型工作 | 写代码、评审、拆解、提炼 | 状态转换、锁、验收判定、门禁、权限 |
| 出错性质 | **可恢复**（打回重试） | **不可恢复**（锁判错即数据损坏） |
| 正确性来源 | 概率 | 确定性，可单元测试 |

这条原则直接决定了架构的主分界线。

## 总体架构

### 五个平面

```
┌─ 控制平面 Control Plane ──────────────── 确定性，不含 LLM ─────┐
│  状态机引擎 · 锁管理器 · 准入校验器 · 门禁引擎                   │
│  证据校验器 · Guardian 策略引擎 · 预算管理器                     │
│  → 系统的"宪法执行者"。全是普通代码，可单测，永远可靠             │
└────────────────────────────▲──────────────────────────────────┘
                             │ 只能提交变更请求，不能直接改状态
┌────────────────────────────┴─── 执行平面 Execution Plane ─────┐
│  Intake · Architect · Planner · QA · Coder×N                   │
│  Reviewer · Integrator · Evolver     （跑在 AgentTeams Worker）  │
│  → 有判断力，但对系统状态零写权限                                │
└───────┬─────────────────┬──────────────────┬──────────────────┘
        │                 │                  │
┌───────▼──────┐ ┌────────▼────────┐ ┌───────▼────────────────┐
│ 数据平面      │ │ 上下文平面        │ │ 进化平面                │
│ Data Plane   │ │ Context Plane   │ │ Evolution Plane        │
│              │ │                 │ │                        │
│ 四张图        │ │ Context Broker  │ │ Evolver 闭环            │
│ 代码仓库      │ │ 可见性矩阵       │ │ 证伪门 · 影子回放        │
│ Artifact 存储 │ │ 预算降级链       │ │ Skill Registry · 灰度   │
│ 三层记忆      │ │ → 唯一决定       │ │ → 受不动点约束           │
│ Trace        │ │   "谁看见什么"    │ │                        │
└──────────────┘ └─────────────────┘ └────────────────────────┘
```

### 控制平面与执行平面的分界

这是架构中唯一重要的那条线。分界的依据是上一节的**风险分配原则**。

具体后果：

```
Manager 维护状态机、算 ready 集合、发锁 —— 零行 LLM 调用
Manager 仲裁分歧、判断是否升级        —— 才调模型

⟹ Agent 全部挂掉，控制循环仍然正确运行，只是没人干活
⟹ 系统进入"有活没人干"（可恢复），而不是"状态错乱"（不可恢复）
```

### 与 Kubernetes 的同构

这不是比喻，是逐项对应。理解了 K8s 就理解了本架构：

| Kubernetes | Codentum |
|---|---|
| etcd（声明式状态） | `.codentum/` 仓库内的四张图 |
| controller manager 的 reconcile loop | 调度器主循环 |
| Pod spec | WorkPacket |
| **admission controller** | **准入校验器**（此项对应精确） |
| PodSecurityPolicy / admission webhook | Guardian + 只读挂载 |
| 调度器的资源占用表 | 所有权图 / 路径锁 |
| immutable fields | 契约冻结（I3） |
| readiness probe / rollout gate | 阶段门禁 |
| kubelet 上的容器 | Worker 中的 Harness |

**最重要的推论**：系统的驱动力是"期望状态与实际状态的差"，而不是"轮到谁说话"。**主循环是调谐循环，不是对话循环。**

### 为什么不是其他架构

| 备选 | 否决理由 |
|---|---|
| 纯对话式（Agent 群聊到完成） | 状态在对话里 → 失忆、不可恢复、不可审计，且**没有收敛保证** |
| 中心化编排（一个大 orchestrator） | orchestrator 必须理解全部细节才能派活 → 上下文必然爆炸，且是单点 |
| 层级委派（manager → sub-manager → worker） | 每层委派都有信息损耗，三层后需求已变形 |
| 黑板系统（共享内存自由读写） | 无写权限隔离 → 互相覆盖；无边界 → 无法安全并行 |
| **本架构**（声明式状态 + 调谐循环 + 拉动式执行） | 状态外置可恢复；控制确定；执行可横向扩；**并行度可计算** |

## 状态设计（Graph 工程）

### 状态为什么在仓库里

状态是仓库内的 `.codentum/` 目录，与代码同版本控制。代价是并发写需串行化，换来四件事：

| 收益 | 说明 |
|---|---|
| 状态变更有 diff | "谁在何时把这个 packet 标成 verified" 是一次 commit，可 review、可追责 |
| 崩溃恢复 = git checkout | 不需要恢复流程，回到上一个 commit 即一致状态 |
| 可分支、可回滚 | 想试另一条架构路线就开 branch，整个项目状态跟着代码分叉 |
| **事务性是白送的** | 复杂的图变更（如拆分 packet）天然原子——要么整个 commit 成功，要么回退 |

并发问题收敛到单点：**状态变更只由控制平面提交**，Worker 提交的是变更请求。

### 目录结构

```
.codentum/
├── brief.yaml                    产品定义（冻结，变更走 ChangeRequest）
├── architecture/
│   ├── contracts/                ★ 接口契约（唯一写者：Architect）
│   │   ├── openapi.yaml          API 契约
│   │   ├── db.schema.sql         数据契约
│   │   ├── types.ts              类型契约
│   │   └── events.yaml           事件契约
│   ├── boundaries.yaml           ★ 模块边界与路径所有权（所有权图的分区依据）
│   └── adr/                      架构决策记录（含被否决方案）
├── backlog/
│   ├── epics/
│   └── packets/                  一文件一个 WorkPacket
├── state/
│   ├── graph.json                依赖图 + 各 packet 状态
│   ├── locks.json                所有权图（运行时）
│   ├── provenance.jsonl          溯源图（追加式）
│   ├── budget.json               预算树的实时消耗
│   └── cursor.json               当前阶段、迭代号、WIP 计数
├── evidence/<packet-id>/         执行证据（原始日志、diff、trace-id、审批记录）

└── roles/                        role spec（★ 派生工具面/挂载/transitions 的唯一源）
```

### 四张图，不是一张

混成一张是常见设计错误——它们的节点、边、性质、生命周期、一致性要求全都不同。

| 图 | 节点 | 边 | 性质 | 用途 | 谁构造 |
|---|---|---|---|---|---|
| **依赖图** | WorkPacket | `depends_on` | DAG，规划期静态 | 调度：算 ready 集合 | Planner |
| **所有权图** | 路径 × packet | `owns` / `reads` | 二部图，运行期动态 | 并行安全（I1） | 调度器（唯一写者） |
| **溯源图** | 需求/假设/契约/packet/commit/证据 | `derives_from` | DAG，追加式永不删 | 影响面分析 + 审计 | **系统自动派生** |
| **知识图** | 记忆条目/Skill/规则/反例 | `supports`/`refutes`/`supersedes`/`scopes` | 有环，持续演化 | 经验的组织与检索 | Evolver（过证伪门） |

#### 依赖图与所有权图为何必须分开

依赖图是规划期确定的、静态的；所有权图随 claim/release 变化、有并发。**唯一需要并发控制的是所有权图**——合并会让整张图都变成需加锁的对象。

#### 溯源图：价值最高的一张

```
brief.must_have[MH-2] ──▶ assumption[AS-1] ──▶ contracts/openapi#/summary
                                                    │
                                                    ▼
                                              WP-0202 ──▶ commit a3f2b1 ──▶ src/api/summary/*
                                                    └──▶ evidence/ ──▶ trace-8f2a
```

两个杀手级用途：

- **需求变更影响面 = 一次正向可达查询**。假设 AS-1 被推翻 → 精确得到受影响的契约、packet、commit、文件。没有它只能全库搜索加人肉判断。
- **审计"为什么有这段代码" = 一次反向可达查询**。任意一行代码可回溯到需求、假设、决策、审批人。

> **执行证据链不是一堆日志，是一张可查询的图。**

**溯源图必须自动派生，绝不手工维护**——手工维护一定会漂移，而漂移的溯源图比没有更危险（你以为影响面分析是准的）。实现：写边挂在状态机转换钩子上，转换成功即写边，二者同一次 commit。

#### 知识图：唯一允许有环

允许有环（`supersedes` 链），但**禁止矛盾环**（A supersedes B ∧ B supersedes A），提交时检测。

`refutes` 边（反例）刻意保留：**被证伪的候选经验本身是知识**，防止同一错误结论被反复提出。

### WorkPacket

整个系统最核心的抽象，同时承担五个职责：**任务描述、并行边界、验收定义、资源预算、上下文配方**。

```yaml
id: WP-0102
title: 订阅 CRUD API
type: feature                # feature|fix|refactor|test|infra|spike
epic: EP-002
status: ready
attempt: 0

# ── 并行边界 ──
owns_paths:                  # ★ 独占写权限
  - src/api/subscriptions/**
  - src/repo/subscription*.ts
reads_contracts:             # 只读依赖
  - contracts/openapi.yaml#/paths/~1subscriptions
  - contracts/db.schema.sql#subscriptions
forbids_paths: [src/auth/**, .codentum/**]
depends_on: [WP-0101]

# ── 验收谓词（★ 机器可判定，不接受自然语言）──
acceptance:
  - kind: build
    cmd: pnpm build
    expect_exit: 0
  - kind: test
    cmd: pnpm test tests/acceptance/subscriptions
    expect_exit: 0
    authored_by: qa          # ★ QA 写，Coder 只读
  - kind: contract
    check: openapi_conformance
    target: /subscriptions
  - kind: gate
    ref: gates/develop.yaml

# ── 资源预算（来自历史 p80，超了强制升级）──
budget: {wall_clock_min: 45, tokens: 250000, max_attempts: 3}

context_recipe: coder/feature-impl
risk: R1
```

#### 准入条件（确定性校验，不用模型）

```
✓ acceptance ≥1 条，kind ∈ {build,test,contract,e2e,gate}
✓ owns_paths 与所有 in_progress packet 无交集
✓ reads_contracts 指向的契约存在且已冻结
✓ depends_on 全部存在且无环
✓ budget 已设定
✓ owns_paths 不含 contracts/ 与 .codentum/
```

不满足则打回 Planner，附具体失败项。**这是系统的第一道质量闸门，且不用模型，所以永远可靠。**

#### 状态机

```
        ┌────────────────── Splitter 拆分 ──────────────┐
        │                                               ▼
     draft ─校验─▶ ready ─认领─▶ claimed ─▶ in_progress ─▶ review
                     ▲                          │            │
                     │                    超预算 │      reject│
                     │                          ▼            ▼
                     │                       blocked      rework ─▶ in_progress
                     │                          │            │ (attempt+1)
                     └─── 契约变更后重新就绪 ─────┘      ≥3 次 │
                                                             ▼
     review ─pass─▶ verified ─在最新 main 重跑验收─▶ merged  escalated
                                      │失败
                                      └──▶ rework
```

两处刻意设计：

- **`verified` 与 `merged` 分开**：前者是"在自己分支通过"，后者是"在最新 main 上仍通过"。A、B 各自通过、合到一起挂掉是并行开发最常见的失败（I4）。
- **`blocked` 不是失败**：超预算自动触发 Splitter 拆成 2-3 个更小的 packet。**"干不完就拆"是自动行为，不是异常处理。**

### 图的演化

| 场景 | 处理 |
|---|---|
| **Splitter 拆分** | 入边全部继承；出边采用**保守策略**（下游依赖全部新 packet），除非 Planner 能明确指出只依赖其一 |
| **契约变更** | 沿溯源图反查影响面 → 冻结集 → in_progress 的走 Harness 冻结（不杀）→ 契约版本+1 → 回 ready 重装上下文 → 解冻 |
| **事务性** | 图变更 = 一次 git commit，中途失败可回退 |

### 双层隔离：Git Worktree（物理）+ 路径锁（逻辑）

> 吸收自 ForgePilot。这两层是**互补而非二选一**。

```
物理层：每个 in_progress 的 packet 分配一个独立 Git Worktree
  · Coder 在自己的 worktree 里读写，与其他 Coder 物理隔离
  · 就算逻辑锁出了 bug，两个 Coder 也不会写到同一个文件
  · worktree 是 Git 原生能力，不需要自研

逻辑层：owns_paths 路径独占锁（I1）
  · 保证合并时无冲突 —— worktree 解决不了这个
  · 两个 worktree 各自改了同一个文件，合并照样冲突

⟹ worktree 保证【工作期间互不干扰】
⟹ 路径锁保证【合并时无冲突】
⟹ 两层都要
```

生命周期与 packet 绑定：`claimed` 时创建 worktree → `merged` 后删除 → 崩溃时 worktree 保留供诊断，锁按 TTL 释放。

**额外收益**：Coder 的 Harness 挂载点直接就是 worktree 根目录，"只能写 `owns_paths`"的强制可以退化成"worktree 内的挂载权限"，实现更简单。

### 共享文件治理：单写者不变量的四类例外

I1（单写者）靠 `owns_paths` 互斥实现，但有四类文件**天然是全局共享的**——所有 Coder 都需要改它们。若不单独治理，I1 会在这四处被击穿。

| 类型 | 例子 | 问题 | 治理机制 |
|---|---|---|---|
| **契约** | `openapi.yaml`、`db.schema.sql`、`types.ts` | 已解决 | Architect 独占 + 串行变更窗口（I3） |
| **依赖清单** | `package.json`、`requirements.txt`、lockfile | ★ 每个 Coder 都想加包 | **依赖快速通道** |
| **全局配置** | env schema、feature flags、构建配置、lint 规则 | 同上 | **配置登记制** |
| **生成物** | 类型生成、API 文档、mock server | 会被互相覆盖 | ★ **从契约自动生成，不手写、不进任何 `owns_paths`** |

#### 依赖快速通道

> **依赖膨胀是 Agent 写代码最典型的失控点。** 每个 Coder 都倾向于装一个新包解决眼前的问题，
> 三轮下来 `package.json` 躺着 200 个依赖，一半功能重复、几个是幻觉、还有两个协议不兼容。

```
Coder 需要新包
  → ✗ 不能直接改 package.json（只读挂载）
  → 提 DependencyRequest{package, version, why, alternatives_considered}
       ▼
  ★ 自动策略先审（确定性，无模型）
     □ 包真的存在吗？            ← 防幻觉依赖，最高频
     □ 许可证在白名单内吗？       ← AGPL/GPL 需人工确认
     □ ★ 项目里已有等价包吗？     ← 最高频的拒绝理由
          （已有 ramda 就别装 lodash；已有 zod 就别装 joi）
     □ 与现有依赖版本冲突吗？
     □ 体积 / 传递依赖数超阈值吗？
       ├─ 拒绝 → 返回具体理由，★ 尤其"已有等价包 X，用它，参考 src/utils/y.ts"
       └─ 通过 → 进依赖变更队列（★ 串行）→ 统一安装 → 重跑冒烟 → 广播新版清单
```

**为什么自动策略能挡住大多数**：Coder 的依赖请求里，"包名是幻觉"和"项目已有等价包"两类占绝大部分，这两类都是确定性可判定的，不需要 Architect 介入。真正需要人判断的只剩许可证与架构影响。

**依赖请求历史是 ProjectPattern 的重要组成**：做过 3 个 React 项目后，系统知道这类项目的标准依赖集，可在 Skeleton 阶段一次装好，后续请求量显著下降。

#### 配置登记制

`config.schema.yaml` 由 Architect 拥有。Coder 需要新配置项时登记而非直接改：

```yaml
ConfigRequest:
  key: FX_API_BASE_URL
  type: string
  required: true
  why: 汇率服务需要可配置的 API 地址（测试环境指向 mock）
  used_by: [WP-B01]
  ★ provisioning: true        # 标记它最终需要用户填 → 自动进配置收集表单
```

`provisioning: true` 这个标记是关键：**它让"最终要向用户索要什么"在开发过程中被自动累积，而不是最后靠人回忆**。详见 [交付与配置收集](#provisioning)。

#### 生成物：不写，只生成

```
❌ Coder 手写 API 文档 / 类型定义 / mock server
    → 多人手写必然冲突，且与契约必然脱节
✅ 契约冻结后由构建流程自动生成，产物标记 generated
    → 不属于任何 owns_paths，不可被任何 Coder 修改
    → 契约变了重新生成，永远一致
```

这条同时消灭两个问题：共享文件冲突，以及文档与实现脱节。

### 一致性保证

| 图 | 风险 | 保证方式 |
|---|---|---|
| 依赖图 | 环 → Loop 空转 | Planner 提交时确定性环检测 |
| 所有权图 | 竞态 → 破坏 I1 | **乐观锁 + 单点原子提交**；冲突则 Worker 重选 |
| 溯源图 | 漂移 | 自动派生 + 只追加 → 天然一致 |
| 知识图 | 矛盾环 / 陈旧 | 矛盾环检测；`last_injected` + `hit_effect` 驱动复审 |

### 存储选择（按查询模式，不要一上来就上图数据库）

| 图 | 主查询 | 存储 |
|---|---|---|
| 依赖图 | ready 集合 = 拓扑前沿（n<1000） | JSON + 内存计算 |
| 所有权图 | 路径冲突 = 前缀匹配（高频小规模） | 前缀树（内存）+ JSON 持久化 |
| 溯源图 | 影响面 = 多跳可达（跨项目累积） | 邻接表持久化（PostgreSQL） |
| 知识图 | 相关经验 = 语义相似 + 图邻域 | **pgvector + 邻接表双索引** |

> 知识图检索必须是混合的：向量召回 → 沿 `scopes` 边过滤 → 沿 `supersedes` 边取最新版本。**纯向量检索会召回已被取代的旧经验**，这是很多 RAG 记忆系统的隐性 bug。

## 运行设计（Loop 工程）

### 驱动力是状态差，不是消息

```
✗ 消息驱动：A 做完发消息给 B → 消息丢一条，系统永久卡死且没人知道卡在哪
✓ 状态差驱动：循环不断比较期望与实际，差异即待办 → 消息丢了下轮扫描照样自愈
```

主循环（幂等，跑一遍和两遍结果相同）：

```
reconcile():
  实际 = 读四张图
  ready = {p | deps 全 merged ∧ owns_paths 无锁冲突 ∧ WIP 未满}
  暴露 ready 队列
  处理 claim / 状态变更请求（确定性校验后原子提交）
  异常扫描：超时 / 超预算 / 心跳丢失 / 锁 TTL 过期 → 补偿
  阶段门禁全绿 → 推进阶段
  sleep(tick)
```

**推论**：消息队列（RocketMQ 等）在本系统中是**通知加速器，不是正确性依赖**。去掉它系统仍正确，只是响应从事件级退化到 tick 级。这决定了它的实施优先级是 P2。

### 四层循环与终止条件

> **核心规则：每一层都必须有"不成功但可以结束"的出口。只有"成功才能退出"的循环一定会死循环。**

| 层 | 节拍 | 正常终止 | **异常终止（必须有）** |
|---|---|---|---|
| **内层** Harness 自修复 | 秒 | 验收谓词全绿 | 预算耗尽 → `blocked` |
| **Packet** | 分～时 | `merged` | attempt≥3 → `escalated`；被拆 → `abandoned` |
| **迭代** | 时～天 | 全部 merged ∧ 门禁绿 | 迭代预算耗尽 → 未完成退回 backlog，**迭代照常结束** |
| **项目** | 天～周 | 冷启动测试通过 → `delivered` | 项目预算耗尽 / 需求矛盾 → **交付已完成部分 + KNOWN_ISSUES** |

最后一行是设计上的诚实：**项目也可以"不成功地结束"**。允许它交付部分成果并如实说明，远好于让它在最后 10% 上无限打转。

### 预算树：按成本计，不按 token 计

预算不是"设一个 token 上限"，是层层分配的树：

```
项目预算 $12.00 / 48h        ★ 单位是货币，不是 token —— 见下
   ├─ Discovery      3%
   ├─ Design         7%
   ├─ Skeleton      10%
   ├─ Increment     60% ──┬─ 迭代1 20% ──┬─ WP-0101  $0.28 / 45min
   │                      ├─ 迭代2 20%   ├─ WP-0201  $0.28 / 45min
   │                      └─ 迭代3 20%   └─ ...
   ├─ Hardening     15%
   └─ Launch         5%
```

> ⚠️ **为什么单位必须是货币而不是 token。**
> **不同模型家族的分词器不同——同样的文本在不同模型上是不同的 token 数**（跨代差异可达 30%）。
> 而本系统是异构路由的（见下节），同一个 packet 换个档位执行，token 数就变了，
> 但"这个 packet 值多少钱"是不变的。**按 token 计预算，换模型时预算会静默失真。**
>
> 实现上：Harness 记录每次调用的 `usage` 与所用模型，由 ModelGateway 换算成成本累加。
> token 仍然记录（用于分析与进化），但**预算的判定单位是钱**。

规则：

1. 上层耗尽 → 下层强制停止（防止某阶段吃光全部资源）
2. 下层节余 → 归还上层
3. 阶段超 120% → 升级到人，给"追加预算 / 缩减范围 / 终止"三选一
4. **分配比例本身可被 Evolver 进化**

比单一上限精细得多：它能回答"钱花在哪个阶段了"，而这是优化的前提。

### 死循环检测

| 层次 | 检测什么 | 方法 | 处置 |
|---|---|---|---|
| 语法级 | 同一 packet 反复 | `attempt ≥ 3` | escalate |
| **语义级** ★ | **假装修改** | rework 后新 diff 的**规范化哈希**（去空白/注释、变量名归一）与上次相同 | **立即 escalate**，不等 attempt 到 3 |
| 系统级 | 全局停滞 | 滑动窗口内 merged 计数为 0 且 in_progress 非空 | 告警 + 诊断 |

语义级最实用：Coder 被打回后做无实质修改的"假修改"是真实高频行为——它没理解 findings 但必须产出东西。抓到后应**立刻升级而非再耗两次 attempt**，因为它已证明自己不理解问题。

补充：**Reviewer findings 自相矛盾检测**——若第 N 次要求与第 N-1 次方向相反（先要求提取函数、再要求内联），介入仲裁；这是 Reviewer 的问题不是 Coder 的。

### 单向降级与批量升级

**规则一：下层失败向上冒泡为明确状态，上层绝不阻塞等待。**

```
✗ 一个 packet escalated → 迭代循环停下来等人
✓ 一个 packet escalated → 标记状态 → 继续跑其他 packet
                        → 迭代结束时把本轮所有 escalated 一次性交给人
```

**规则二：批量升级，不逐个打断。**

逐个打断会让人被 Agent 的问题淹没；人一旦成为高频阻塞点，系统吞吐就退化到人的响应速度。

升级批次的每一项必须包含四要素：

```
① 争议是什么（一句话）
② 双方论点 + 证据引用
③ ★ 系统的建议 + 置信度
④ ★ 不决策的后果（阻塞多少 packet、影响工期多久）
```

③④ 是关键：**人不该从零开始判断**——系统已分析过，应给出倾向，人的角色是审核倾向而非重做分析；④ 让人知道有多急。

**唯一例外是 R3+ 风险动作**（生产部署、数据迁移），必须即时阻塞审批。

### 人在循环中的位置

**人不是循环的一环，人是中断源与仲裁者。**若人是循环的一环，系统吞吐 = 人的响应速度，多 Agent 就失去意义。

| 类型 | 阻塞 | 触发条件 | 频率目标 |
|---|---|---|---|
| 审批 | 是 | 仅 R3+ 风险动作 | 与项目规模无关 |
| 仲裁 | 是，但批量 | escalated / 契约重大变更 / 假设被推翻 | **随规模次线性增长** |
| 旁听打断 | 否 | 人主动 | 不限 |

> **"仲裁频率随规模次线性增长"是这个系统值不值得做的判据。**
> 若线性增长，说明只是把人从写代码换成回答问题，总工作量没降。
> 让它次线性的两个手段：批量化，以及**每次仲裁的结论沉淀为规则，同类问题不问第二次**。
> 由此得到一个可度量指标：**同类仲裁复发率**。

## 执行设计（Harness 工程）

### Harness 的职责

> **把一次不可靠的模型调用，转换成一次可判定成败的工作单元执行。**

Claude Code、Hermes 等是**通用 Harness**（提供工具循环、文件读写、终端）。本系统需要在其外再包一层**受控 Harness**：

```
┌─ 受控 Harness ────────────────────────────────────────┐
│ ① 上下文装配   ② 工具面裁剪   ③ 沙箱挂载   ④ 预算监控  │
│ ⑤ 检查点/冻结  ⑥ 出口契约强制 ⑦ 证据产出  ⑧ 可重放记录 │
│    ┌─ 通用 Harness（Hermes / OpenClaw / Claude Code）┐│
│    │   工具循环 · 文件读写 · 终端 · 模型调用           ││
│    └────────────────────────────────────────────────┘│
└──────────────────────────────────────────────────────┘
```

### 单次执行的生命周期

```
[准备阶段 —— 无模型参与]
  1. 从 role spec 派生：工具面 / 卷挂载表 / transitions 白名单
  2. Context Broker 装配上下文 → {slices, denied[], total_tokens}
  3. 启动预算计时器
  4. 写 checkpoint-0（输入快照哈希 + 引用）

[执行阶段 —— 模型参与，内层自修复循环]
  5. loop:
       模型动作 → 工具调用
       ├─ 工具不在工具面 → 拒绝并把错误回灌模型（不抛异常终止）
       ├─ 路径不在 rw 挂载 → 文件系统层失败，错误回灌
       ├─ 每次工具调用后写 checkpoint（安全点）
       └─ 预算检查：超 → 跳出，终态 blocked
     终止：验收谓词全绿 / 预算耗尽 / 收到冻结信号

[收敛阶段 —— 无模型参与]
  6. 跑全部验收谓词（确定性执行，不问模型）
  7. 产出证据目录（原始日志，不是模型的复述）
  8. 判定终态：done / rework / blocked
  9. 写 Trace + 可重放记录
```

**准备与收敛两端完全不含模型**：进模型前所有约束已物理生效，出模型后所有判定由代码做出。**模型只在中间有发挥空间，而那段的边界是硬的。**

### 工具面是权限的运行时投影

这是最容易出漏洞的地方：

```
✗ role spec 写"Coder 不能写 contracts/"，但工具面给了通用 write_file
  → 约束只存在于提示词里，模型一旦忽略就穿透
```

**正确做法：Single Source——一份 role spec 派生四处配置，禁止手工维护任何一处。**

```
                    role spec (唯一源)
      ┌─────────────┬───────┴───────┬──────────────┐
      ▼             ▼               ▼              ▼
   工具面        卷挂载表       transitions    所有权注册
  (Harness)     (Harness)        (Loop)         (Graph)
```

以 Reviewer（`writes: []`）为例：工具面无任何 write 类工具；全部 ro 挂载；`evidence/*/reasoning.md` **直接不挂载**（不是无权限，是不存在）；transitions 仅 `review→verified` / `review→rework`；不注册任何路径锁。

CI 中加一条：派生物与源不一致则构建失败。

### 内层自修复与外层重试的边界

| | 内层（Harness 内） | 外层（Loop 层） |
|---|---|---|
| 性质 | **还没做完** | **做错了** |
| 计量 | budget（token / 时间） | attempt（次数） |
| 上限 | 45min / 250k tok | 3 次 |
| 超限 | blocked → 触发拆分 | escalated → 人工仲裁 |
| **反馈来源** | **确定性执行**（构建 / 测试） | **另一 Agent 的判断**（评审） |

最后一行是判据。混在一起会导致两种病态：内层小失败就升级（人被淹没，拆分毫无必要），或外层实质错误被内层反复重试掩盖（在错误方向上烧光预算）。

### 出口只有三种终态

```
done    ── 全部验收谓词绿 + 证据完整
rework  ── 验收未过 / 被评审打回，附结构化 findings
blocked ── 预算耗尽 / 依赖缺失 / 契约不足，附阻塞原因
```

**不允许**：`partial`、`probably_ok`、纯自然语言总结。任何模糊终态都会把判断责任推给上层，而上层只能再调一次模型去理解它——**不确定性就是这样被放大的**。

输出强制 structured output + schema 校验；校验失败 → Harness 内重试 ≤2 次 → 仍失败则 blocked（`output_contract_violation`）。

### 检查点、冻结与可重放

**安全点**：每次工具调用返回后、下一次模型调用前。

| 场景 | 行为 |
|---|---|
| 契约变更冻结 | 下一安全点持久化并挂起 → 契约更新后重装上下文继续，**不是杀掉重来** |
| Worker 崩溃 | 从最后 checkpoint 恢复；超 TTL 未恢复则控制平面回收 packet、释放锁 |
| 人工打断 | 下一安全点暂停 → 人的输入作为新上下文注入 → 继续 |

**可重放性是 Harness 的责任，不是进化层的**。否则影子回放测出的差异不知道来自 Skill 变更还是输入不同。必须记录：

```yaml
replay_record:
  context_snapshot_hash, context_slices_refs
  model: {id, version, temperature, seed}
  tool_calls: [{tool, args, result, duration_ms}]
  role_spec_version, skill_versions
  memory_injected: [GM-014, GM-027]   # ★ 进化度量的对照基准
  outcome: {status, evidence_refs}
```

三种重放模式：

| 模式 | 固定什么 | 用途 |
|---|---|---|
| 严格重放 | 上下文 + 模型 + 工具返回全固定 | 调试、审计"当时为何这么决定" |
| **能力 A/B** | 上下文固定，**Skill/记忆版本变化**，工具真实执行 | 影子回放，度量进化增益 |
| 鲁棒性重放 | 上下文固定，种子变化，跑 N 次 | 测方差（LLM 单次结果不可信） |

### Harness 分级

| 档位 | 适用角色 | 特征 |
|---|---|---|
| **重型**（终端沙箱） | Coder、Integrator、Architect | 完整文件系统 + 终端 + 长内层循环 + 高预算 |
| **轻型**（只读分析） | Reviewer、Locator、QA 执行阶段 | 只读挂载 + 检索工具 + 短循环 + 强制结构化输出 |
| **对话型**（人机交互） | Intake | 多轮 + 槽位状态 + 轮次上限 + 无文件写权限 |

分档的收益不只是省资源：**轻型 Harness 没有写工具，整类越权在物理上不可能发生**。角色的风险等级直接决定它跑在哪档。

## 角色体系

### 角色的本质不是提示词

> **一个角色 = 一组写权限 + 一组可见上下文 + 一组可触发的状态转换。**
> 提示词只是让它高效地用好这组权限。

直接推论：**若两个候选角色的写权限集合完全相同，它们不是两个角色，是同一角色的两个阶段。**这条能砍掉大量伪角色。

### 如何决定该有哪些角色

一个候选拆分须四道检验全过：

| 检验 | 内容 |
|---|---|
| **失败模式独立性**（必要） | 合并后是否有一类错误会被掩盖？**只有当两者信息来源不同时才成立**——同源信息→同源错误→拆了白拆 |
| **权限不同**（结构） | 见上 |
| **上下文需求不同**（经济） | 重叠 >80% 则拆开只是把同一份上下文装配两遍 |
| **可独立评估**（可观测） | 能否为它单独定义质量指标？不能则它不是角色，是别人的一个步骤 |

### 两种驱动力与裁剪铁律

| 驱动力 | 目的 | 例子 | 可否为省成本合并 |
|---|---|---|---|
| **能力驱动** | 做得更好 | Intake / Architect | ✅ 可以 |
| **制衡驱动** | 防止自己评自己 | 见下表 | ❌ **绝对不行** |

制衡关系的完整清单，都来自同一模式——**评判标准的制定者不能是被评判的人**：

```
Planner 定义 packet 与验收   ↔  Coder 执行        （不能自己缩小范围）
QA 写验收测试                ↔  Coder 写实现      （不能自己出考卷）
Coder 实现                   ↔  Reviewer 评审     （不能自己批准）
Architect 定契约             ↔  Coder 用契约      （不能改接口迁就实现）
所有执行者                   ↔  Evolver 复盘      （不能自己写自己的鉴定）
```

#### ★ 制衡还有第三个维度：模型隔离

上下文隔离和权限隔离都做到了，制衡仍可能失效——**如果两侧跑在同一个模型上**：

```
同一个模型 = 同一套盲区
  → Coder 写代码时漏掉的那类边界情况，Reviewer 评审时也不会发现
  → 两者的错误【相关】，第二双眼睛看到的是第一双看到的东西
```

所以制衡关系有三层，缺一不可：

| 层 | 隔离什么 | 强制方式 |
|---|---|---|
| 权限 | 谁能写什么 | 卷挂载 + hook + Guardian |
| 上下文 | 谁能看什么 | 可见性矩阵（存储层） |
| ★ **模型** | **错误从哪来** | **路由表约束 + 界面检查器** |

**两条硬约束**（见模型路由）：

```
Coder    的模型 ≠ Reviewer 的模型
Evolver  的模型 ≠ 证伪门 Verifier 的模型
```

这也是**跨家混用模型的唯一正当理由**——不是为了性能，是为了错误去相关。

> **裁剪编制时只能砍能力驱动的拆分，制衡驱动的一个都不能砍。**
> 合并 Coder+Reviewer 省下的那点 token，换来的是整套质量保证全部失效。

### 角色定义规格（字段顺序即重要性顺序）

```yaml
role: reviewer

# ① 结构定义 —— 控制平面强制，这才是角色本体
writes: []
reads:
  allow: [diff, contracts/*, tests/acceptance/**, gates/*, memory/global(scope匹配)]
  deny:  [evidence/*/reasoning.md]     # ★ 存储层强制，不是提示词约定
transitions: [review->verified, review->rework]
escalates:   [attempt >= 3]

# ② 契约定义 —— 输出结构化，不是自由文本
input_schema: ReviewRequest
output_schema: ReviewVerdict

# ③ 质量定义 —— 成对指标
metrics: {primary: 漏放率, counter: 误拒率}

# ④ 资源定义
budget: {cost_usd: 0.08, wall_clock_min: 10}   # ★ 按货币计，见预算树
runtime: openclaw
harness_tier: light
model:
  requires: {tier: high, structured_output: strict}   # ★ 声明能力需求，不写模型 ID
  effort: high
  ★ must_differ_from: [coder]     # 硬约束：错误去相关（见模型路由）

# ⑤ 行为定义 —— 最后才是这个
skills: [adversarial-review@^1, rule-conformance-check@^2]
prompt_ref: prompts/reviewer.md
```

`transitions` 让"角色在流程中的位置"成为可校验的声明：Coder 提交 `review→verified` 被直接拒绝。**角色越权在结构上不可能，无需在提示词里叮嘱。**

### 编制表

| 角色 | 职责 | 唯一写权限 | 拆开的理由 | MVP |
|---|---|---|---|:-:|
| **Intake** | 澄清、写 brief、写验收场景 | `brief.yaml` | 失败模式="没搞懂要做什么"；唯一对人的角色 | ✅ |
| **Architect** | 技术选型、**契约设计**、边界划分、ADR | `contracts/**`、`boundaries.yaml`、`adr/**` | 失败模式="结构错"；**契约唯一写者是并行安全的基石** | ✅ |
| **Planner** | 拆 epic 为 packet、维护依赖图、Splitter | `backlog/**` | 失败模式="切错粒度"，与"架构错"不同 | ✅ |
| **QA** | ★ **先于实现写验收测试**、跑测试矩阵 | `tests/acceptance/**` | 失败模式="测漏了"；**先写测试是核心防作弊设计** | ✅ |
| **Coder** ×N | 实现、写单元测试、自测、提交 | packet 的 `owns_paths` | 执行主体 | ✅ |
| **Helper** | ★ 诊断求助请求，产出根因假说与建议路径 | **无** | **更大视野 + 零写权限**。求助的本质是"局部视野不足"，给它全库视野正是解药；无写权限保持 Coder 的责任主体地位 | |
| **Reviewer** | 对抗评审，**看不到 Coder 推理链** | 无 | 失败模式必须与 Coder 不相关 | ✅ |
| **Integrator** | 合入 main、守绿线、部署、回滚 | `main`、部署配置 | 唯一持有合入与生产权，审计收口 | ✅ |
| **Manager** | 状态机、仲裁、升级、对人汇报 | `state/**` | 失败模式="调度错"；**不写代码不评审** | ✅ |
| **Evolver** | 复盘、提炼、Skill PR、影子回放 | `memory/**` 的提案 | 输入是"所有人的失败"，其他角色都有自辩动机 | ✅ |
| **Guardian** | Policy 拦截，**确定性、无 LLM** | 无 | 策略执行不能依赖模型判断 | ✅ |

**小项目可合并**：Intake+Architect → Designer；Planner+Manager → Coordinator。合并后 7 个角色，仍满足"≥3 类职能 Agent"。

### 权限矩阵（写权限是硬隔离）

| 路径 | Intake | Architect | Planner | QA | Coder | Reviewer | Integrator | Manager | Evolver |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| `brief.yaml` | **W** | R | R | R | R | R | R | R | R |
| `contracts/**` | R | **W** | R | R | **ro挂载** | R | R | R | R |
| `boundaries.yaml` | — | **W** | R | — | R | R | R | R | R |
| `backlog/**` | — | R | **W** | R | **ro挂载** | R | R | R | R |
| `tests/acceptance/**` | R | R | R | **W** | **ro挂载** | R | R | — | R |
| `src/**` | — | — | — | — | **W（限 owns_paths）** | R | R | — | — |
| `tests/unit/**` | — | — | — | R | **W** | R | R | — | — |
| `state/**` | — | — | — | — | — | — | R | **W** | R |
| `memory/global/**` | — | — | — | — | R | R | R | R | **W\*** |
| `gates/**`、`policies/**`、`roles/**` | — | — | — | — | — | — | — | — | **只读** |
| `main` 分支 | — | — | — | — | — | — | **W** | — | — |

`W*` = 需过证伪门。**最后两行是"进化的不动点"**：门禁、策略、角色定义对所有 Agent 只读，包括 Evolver，只能人改 Git。

实现方式：Worker 容器的卷挂载权限 + git pre-commit hook + Guardian 拦截，**三层**。

### 各角色设计要点

完整设计见 `06`，此处为工程实施必须落地的关键项：

| 角色 | 必须实现的关键设计 |
|---|---|
| **Intake** | 槽位状态外置（`check_slots()` 确定性）；**以"能否写出验收场景"为唯一终止判据**；`wont_have` 强制 ≥3 条；**假设写成溯源图节点**；冻结前跑需求自洽性检查 |
| **Architect** | **契约可实现性探测**（真装依赖、真编译 stub、真建库）；边界质量可计算（并行潜力/耦合度/覆盖完整）；**双向覆盖检查**（正向防遗漏、反向防镀金）；ADR 必须记录被否决方案 |
| **Planner** | **虚拟调度**（执行前验证并行度、关键路径、锁冲突、死锁）；**水平切分 + 契约级验收 + 集成 packet 承载端到端验收**（见技术栈串并联）；关键路径优先排序；**预算取历史 p80**；算法任务必须先出 `spike` |
| **QA** | **红灯验证**（新验收测试必须在当前代码上失败）；**作者阶段 `src/**` 完全不可见**；变异测试抽查；断言限制在契约层级；区分"功能未实现"与"测试自身报错" |
| **Coder** | **强制第一次工具调用读验收测试**；失败上下文**继承结论不继承过程**；预算自感知 + 60% 收敛提示；`request_split` 主动求拆；`request_help` 主动求助（鼓励，不惩罚）；越权错误信息必须指出正路；★ **中档模型 + 最强档 advisor**（token 大头在这，杠杆最大）<br>⚠️ **不做"失败即升档"**：跨 attempt 换模型会击穿缓存（全量冷启动重写），代价常大于收益。要升先升 `effort`——它不换模型，缓存不失效 |
| **Helper** | 上下文配方与 Coder 完全不同（**全库可读 + 全部 ADR + 跨项目案例库**）；输出含 **`ruled_out`**（告诉 Coder 哪些路不通，比告诉它哪条路通更省预算）；分层检索（案例库 → 全库检索 → 深度推理）；**求助频率是系统成熟度指标** |
| **Reviewer** | **`attempted_refutations` 必填**（空则输出无效）；**混入校准样本**做在线质量监控；证伪清单固定且按发现难度降序；规则命中计数驱动规则集清理；Coder 有申诉权；★ **模型必须与 Coder 不同**——同模型 = 同盲区 = 上下文隔离白做 |
| **Integrator** | 合入顺序按**冲突风险升序**；**合入即打 tag**（绿线的物理实现）；**回滚优先于修复**；批量合入 + 二分定位；部署验证清单强制（"pipeline 绿"不算证据）；**回滚不需审批** |
| **Evolver** | 提案必须带 `expected_gain` 并**事后核对**（预测准确率是它的指标）；证伪门**不对称预算**（找反例 1.5×）；★ **Verifier 必须与 Evolver 用不同模型**（否则"提出候选"与"找反例"共享盲区）；反例写 `refutes` 边；记忆垃圾回收（`last_injected` + `hit_effect`）；"本轮无提案"是合法终态；★ **全部工作走 Batch API**——延迟完全不敏感，约省 50%，无取舍 |
| **Manager** | 仲裁用**双盲摘要**（不标注谁说的）；调度部分零模型且**幂等**；升级批次四要素；升级判据是显式清单；**仲裁结论沉淀为规则** |
| **Guardian** | fail-closed 且错误信息含整改指引；**R4 类路径直接不挂载**（不可探测）；**拦截统计回流上游**——拦截率高是上游设计不好，不是防线的功劳 |

### 成对指标

单一指标一定会被刷，每个角色配主指标 + 反向指标：

| 角色 | 主指标 | 反向指标（防刷） |
|---|---|---|
| Intake | 需求返工率 | 澄清轮次 |
| Architect | 契约变更频率 | 契约复杂度（防过度设计） |
| Planner | packet 超预算率 | packet 数量膨胀（防切太碎） |
| QA | 缺陷逃逸率 | 无效 rework 率 |
| Coder | pass@1 | 变更行数 / packet |
| Reviewer | 漏放率 | 误拒率（申诉成功计入） |
| Integrator | 绿线破损次数 | 合入吞吐 |
| Evolver | holdout 进化增益 | 提案否决率 + 预测准确率 |
| Manager | 同类仲裁复发率 | 升级噪音率 |

这对指标还有第二个用途：**它们是 Evolver 做编制进化的输入**。测不出来的角色进化不了。

## 上下文工程

### Context Broker

Agent 不直接读全局，而是向 Broker 申请上下文切片：

```
请求 {role, task_type, packet, budget_tokens}
  ① 查可见性矩阵 → 剔除被禁 artifact
  ② 查上下文配方 → 该角色该任务需要哪些切片
  ③ 查预算       → 超预算按降级链处理
  ④ 返回 {slices, denied[], total_tokens, degraded}
```

三条硬规则：

```
1. 可见性矩阵优先于一切；被禁 artifact 一律不给，且在返回中显式列出 denied（进 Trace 供审计）
2. 超预算按 全文 → 结构化摘要 → 引用+索引 逐级降级，★ 禁止截断
   （截断是最糟的降级：随机丢弃信息且不告诉任何人）
3. 必需切片不可得 → 任务不启动并上报，不带缺失上下文硬跑
```

### 检索的确定性梯度

> 吸收自 ForgePilot。**先查能确定回答的，查不到再降级到模糊的。**

```
① 结构化事实   brief 的 must_have、assumptions、已冻结约束          ← 确定
② 已确认决策   ADR、仲裁结论、契约变更记录
③ 契约         openapi / db.schema / types / events 的相关切片
④ 代码索引     符号表、调用关系、owns_paths 下的实际实现
⑤ 向量摘要     全局记忆的语义检索 top-k
⑥ 原始日志     Trace 原文（最贵，最后才查）                          ← 模糊
```

**为什么这个顺序重要**：直接上向量检索，会把"契约里白纸黑字写着的东西"变成"语义相似度匹配出来的东西"——**本来能确定回答的问题，被降级成了概率问题。能查表就不要查向量。**

Context Broker 按此顺序逐级填充，前一级填满预算就不进下一级。这同时是最有效的一条 token 优化——多数任务在第 ③ 级就已凑够上下文。

### 装配清单示例（Coder / feature-impl）

不是"给它相关的东西"，是精确装配：

```
✓ packet 定义                        全文    ~1.5k tok
✓ reads_contracts 声明的契约切片      全文    ~3k
✓ owns_paths 下的现有代码             全文    ~8k
✓ 验收测试代码（QA 写，只读）          全文    ~2k
✓ 同模块已完成 packet 的实现          摘要    ~2k   （风格参考）
✓ 全局记忆中 scope 匹配的规则         top-5   ~1k
✓ 相关 Skill                                 ~2k
✗ 其他模块的实现代码      ← 不给，它不需要也不该看
✗ 其他 packet 的内容      ← 不给
✗ 完整代码库              ← 不给
✗ 别的 Agent 的推理过程   ← 不给
                                    合计  ~20k tok
```

### 可见性矩阵关键项

| Artifact | Manager | Architect | Planner | QA | Coder | Reviewer | Integrator | Evolver |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| WorkItem / brief | R | R | RW | R | R | R | R | R |
| 契约 | R | RW | R | R | R | R | R | R |
| **Coder 推理链** | — | — | — | — | RW | **🚫** | — | R |
| 变更 diff | R | — | — | R | RW | R | R | R |
| 验收测试 | R | R | R | RW | R | R | R | R |
| 测试报告 | R | — | — | RW | R | R | R | R |
| 生产凭证 | — | — | — | — | — | — | R | — |

**🚫 Reviewer 禁读 Coder 推理链是整张表的灵魂**——它不是附加的安全措施，而是"Coder/Reviewer 拆分成立"的前提。共享上下文的 Reviewer 在架构上等于不存在。

实现：对象存储的前缀级 policy + 卷不挂载，由网关消费者令牌承载身份。**权限不靠提示词约束，靠存储层强制。**

## Skill 体系与扩展生态

### Skill、MCP、连接器：三层分离

这三者经常被混为一谈，但它们回答的是三个不同的问题：

```
Skill    = 能力抽象层  —— "怎么做一件事"（判断逻辑、执行步骤、失败处理）
MCP      = 工具连接层  —— "怎么调到外部系统"（协议、鉴权、schema）
连接器    = 账号绑定层  —— "用哪个账号连"（OAuth、token、工作区选择）

一条完整链路：
  Skill(deploy-verify-checklist)
    → 调用 MCP(monitoring-server).query_metrics
      → 使用 连接器(Grafana @我的工作区) 的凭证
```

三层分离的收益：换监控系统只改 MCP 层，换账号只改连接器层，**Skill 的判断逻辑一行不动**。这也是"不使用 MCP 时提供等价工具集成契约"能够成立的原因——被替换的只有中间那层。

### 三级作用域：全局 / 角色私有 / 项目级

| 作用域 | 谁能用 | 谁能装 | 例子 | 存放 |
|---|---|---|---|---|
| **Global 全局** | 所有角色 | 系统内置 + 用户安装 | `context-recipe`、`gate-check`、`rule-conformance-check` | `.codentum/skills/global/` |
| **Role 角色私有** | 单一角色 | 用户为该角色安装 | Reviewer 的 `owasp-checklist`、Coder 的 `react-patterns` | `.codentum/skills/roles/<role>/` |
| **Project 项目级** | 本项目所有角色 | Evolver 生成 或 用户安装 | `api-error-convention`（从本项目失败中长出来的） | `.codentum/skills/project/` |

**解析顺序（就近覆盖）**：`Project > Role > Global`。同名 Skill 由更近的作用域覆盖，与配置解析是同一套心智模型。

#### 为什么必须分作用域——这是一个成本问题

> **Skill 会被注入上下文，所以 Skill 的数量直接等于 token 成本。**
> 把所有 Skill 都装到全局，等于让每个 Agent 每次执行都背上所有 Skill 的描述。
> 给 Reviewer 装的安全检查清单，Coder 每次也要付费读一遍。

**角色私有作用域本质上是一种上下文成本隔离机制**，不只是组织上的整洁。这也是为什么 Skills 管理面板必须显示每个 Skill 的 token 开销（见下）。

### Skill Manifest（对齐硬性要求的六要素）

```yaml
name: owasp-checklist
version: 2.1.0
scope: role                  # global | role | project
applies_to: [reviewer]       # scope=role 时必填
description: 按 OWASP Top 10 检查变更中的安全问题

# ① 输入输出
inputs:  {diff: DiffRef, language: string}
outputs: {findings: Finding[], checked_items: string[]}

# ② 调用条件（前置判断，确定性）
preconditions:
  - packet.type in [feature, fix]
  - diff touches ["**/*.ts", "**/*.py"]

# ③ 失败处理
failure:
  timeout_s: 60
  on_timeout: degrade_to_static_scan      # 降级而非中断
  on_error: {retryable: true, max_retry: 2, then: report_and_continue}
  ★ silent_degrade: false                 # 降级必须在输出中显式标注

# ④ 权限边界（★ 命令粒度，吸收自 Nexus）
permissions:
  risk_level: R0
  tools: [read_file, run_static_analysis]  # ★ 必须是宿主角色工具面的子集
  read_paths:  ["src/**", "contracts/**"]
  write_paths: []                          # 只读 Skill
  executable_commands: ["eslint", "tsc"]   # ★ 白名单
  forbidden_commands: ["rm -rf", "DROP", "curl", "git push"]  # ★ 黑名单，双保险
  network_access: []                       # ★ 域名白名单，空 = 禁网

# ⑤ 依赖与互斥
requires_mcp: []
requires_skills: []
conflicts: [legacy-lint-rules]             # ★ 互斥 Skill，吸收自 Loom

# ⑥ 复用价值
reuse:
  cross_role: false
  cross_project: true
  cross_domain: true          # 运维/客服/风控同样适用
```

### Skill 生命周期状态机与五条红线

> 吸收自 ForgePilot。作用域回答"给谁用"，状态机回答"能不能用"，两者正交。

```
Draft ──提交──▶ Candidate ──评测通过+审批──▶ Stable ──被取代──▶ Deprecated
                    │                            │
                    └──评测不过/安全命中──▶ Blocked ◀──运行时异常──┘
```

| 状态 | 谁能调用 | 说明 |
|---|---|---|
| `Draft` | 无 | 编写中，仅作者可见 |
| `Candidate` | **仅被明确授权的 canary 任务** | 已过沙箱，未过灰度 |
| `Stable` | 所有满足作用域的 Agent | 默认只有这一档可被调用 |
| `Deprecated` | 兼容期内的既有引用 | 有替代者，不再推荐 |
| `Blocked` | 无 | 评测不过或运行时异常，硬禁用 |

**五条红线**：

```
① 版本不可原地覆盖 —— 生产更新只能通过版本切换（保证可回滚）
② 新 Skill 默认无写权限、无生产权限、无密钥明文访问权限
③ 具备外部写能力的 Skill 必须声明补偿动作、审批策略、回滚方法
④ Agent 默认只能调用 Stable；Candidate 仅限授权的 canary 任务
⑤ Skill 权限永远是宿主角色权限的子集，不能扩权（见下）
```

#### 一条不可违反的安全规则

> **Skill 的权限永远是宿主角色权限的子集，不能扩权。**

给 Reviewer 装一个声明了 `write_file` 的 Skill，那个工具在 Reviewer 的工具面里根本不存在（工具面由 RoleSpec 派生），所以 Skill 调不动它。**这条保证了"用户随便装第三方 Skill"不会破坏权限模型**——它是可插拔生态能够安全存在的前提。

安装时做确定性校验：manifest schema、权限声明是否超出宿主角色、是否硬编码凭证、是否与已装 Skill 同名冲突、许可证是否在白名单。

### 可插拔：用户如何扩展

```
来源：内置库 · skills.sh 社区（AgentTeams 生态，8 万+）· 本地文件 · Git URL
安装：界面中为【某个角色】或【全局】安装 → 准入校验 → 生效
      ★ 可选影子验证：先在历史任务上重放，看是否真的有用再启用
卸载：随时；Skills 面板给出"30 天命中 0 次、每次注入 800 token"这类卸载依据
```

Evolver 自动生成的 Skill 走的是同一条路径，只是它必须经影子回放与回归门禁——**人装的 Skill 可以先用后看，系统自己生成的必须先验后用**。这个不对称是刻意的：人对自己的选择负责，系统对自己的产出需要举证。

### Skill 的生命周期与治理

```
提出（人安装 / Evolver 生成）
  → 准入校验（确定性）
  → 影子验证（Evolver 生成的强制，人装的可选）
  → 灰度启用（按角色/按比例）
  → 使用中：★ 持续统计命中率、token 开销、失败率、hit_effect
  → 衰减复审：长期零命中或 hit_effect≈0 → 提示卸载
  → 版本升级 / 一键降级到上一版本
```

**"统计驱动的卸载建议"是这套体系的关键**：Skill 库和记忆库一样会单调膨胀，膨胀的代价是上下文被稀释、成本上升。**Skill 库需要垃圾回收，而回收的依据必须是数据不是感觉。**

## 记忆与知识

### 三层记忆

| 层 | 内容 | 存储 | 谁写 | **运行时怎么用** |
|---|---|---|---|---|
| **局部记忆** | 角色手感、本地缓存、失败的尝试 | Worker 容器卷（文件） | 各自 | 同一 packet 多次 attempt 之间传递"上次为什么失败"——**这是重试不重犯错误的原因** |
| **全局记忆** | 项目事实、跨任务经验、团队铁律 | 文件 + pgvector 索引 | 仅 Evolver，过证伪门 | Context Broker 按 `scope` RAG 注入 |
| **情节记忆** | 完整 OTel Trace | 对象存储 + 索引 | 系统自动 | 复盘原料 + 审计回放依据 |

> 局部记忆用文件而非向量库：它的检索是"我刚才干到哪了"，是**时间序**而非语义相似度问题。

#### 每个角色的局部记忆内容与生命周期不同

| 角色 | 存什么 | 生命周期 | 跨项目 |
|---|---|---|:-:|
| Intake | 槽位填充历史、人的回答风格、问过的问题 | 单次会话 | ✗ |
| **Architect** | ★ 依赖探测结果缓存（哪个包哪个版本能装、哪两个库冲突）、候选方案评估 | 长期 | ✅ |
| Planner | 本项目 packet 实际耗时样本、哪类拆分导致过超预算 | 项目内 | ✗ |
| QA | 已生成的测试模式、被判无效的断言写法、变异测试历史盲区 | 项目内 | ✗ |
| **Coder** | ★ **本 packet 的 attempt 历史**（失败原因、试过哪条路、哪个包不存在）、已检索位置、构建缓存 | **packet 内** | ✗ |
| Reviewer | 本项目已发现的问题模式、规则实际命中情况 | 项目内 | ✗ |
| Integrator | 合入冲突历史、哪些模块组合易出语义冲突 | 项目内 | ✗ |
| **Helper** | ★ 诊断案例库：什么症状 → 什么根因 | 长期 | ✅ |
| **Evolver** | 已提出过的候选（含被驳回的）、预测误差历史 | 长期 | ✅ |

**跨项目与否的判据很简单：内容与具体项目无关的，跨项目保留。**"axios@1.6 与 node18 不兼容"跟哪个项目无关，值得永久留；"本项目订阅表叫 subscriptions"只在本项目有意义。

#### 局部记忆的隔离规则

```
局部记忆是【私有且未经检验的】。
  · 不参与其他 Agent 的决策
  · 不能直接注入别人的上下文
  · 想变成全局知识必须走 L0→L1→L2 的晋升阶梯（含证伪门）
```

> 如果局部记忆能直接影响别人，一个 Agent 的错误认知会立刻污染全局。
> **局部记忆的价值恰恰在于它便宜且可以错——因为它只影响自己。**

### 私有 / 半共享 / 全共享三层空间

```
┌─ 私有（各 Worker 容器卷）──────────────────────────────┐
│  局部记忆 · 推理链 · 草稿 · 构建缓存                     │
│  → 其他 Agent 一律不可见（Evolver 例外，只读用于复盘）    │
├─ 半共享（Artifact 存储，按可见性矩阵）──────────────────┤
│  代码快照 · diff · 测试报告 · 定位报告 · 评审意见         │
│  → 传引用不传内容；谁能看由矩阵决定，存储层强制            │
├─ 全共享（Git 仓库 .codentum/）────────────────────────────┤
│  brief · 契约 · boundaries · packet · 四张图             │
│  全局记忆 · Skill · 门禁 · 策略                          │
│  → 所有 Agent 可读（写权限见权限矩阵）                    │
└──────────────────────────────────────────────────────┘
```

**关键判断：共享的东西必须是已经过检验的**（契约冻结、记忆过证伪门、packet 过准入校验）。未经检验的留在私有空间。**这条规则让"共享"不会变成"互相污染"。**

### 全局记忆的条目形态

一条记忆若不能被有效注入，就没有价值，所以格式被约束：

```yaml
id: GM-014
level: L2
statement: 本项目所有 API 错误必须走 ApiError 类，不得直接 throw
scope:                             # ★ 决定何时注入给谁
  paths: ["src/api/**"]
  roles: [coder, reviewer]
  task_types: [feature, fix]
rationale: 统一错误格式使前端能一致处理；混用导致过 3 次前端崩溃
evidence: [trace-8f2a, trace-91bc, trace-a034]   # ★ 可回溯，出事能定位并降级
counterexamples: []                # 证伪门找到的反例（也是资产）
injected_as: |                     # ★ 注入时的确切文本，不是让模型现编
  错误处理：本项目所有 API 错误必须 throw new ApiError(code, message)，
  不得直接 throw Error 或返回裸对象。参考 src/api/subscriptions/errors.ts。
last_injected: 2026-08-05T14:00:00Z
hit_effect: +0.08                  # 注入后 pass@1 相对基线的差值（滚动统计）
promoted_to_skill: api-error-convention@0.1.0
```

`scope` 与 `injected_as` 是关键：前者决定"何时给谁"，后者保证注入的是**确定文本**而非每次重新生成的复述——这让记忆的效果可复现、可 A/B。

### 经验晋升五级

```
L0  一次性观察   局部记忆："这次改 X 报错了"
     │ 同类事件重复 ≥2 次（Evolver 在 Trace 上聚类）
L1  候选经验     进候选池，★ 不参与决策
     │ ★ 证伪门
L2  全局记忆     写入 memory/global/，带 scope 与 injected_as
     │ 可执行化判定
L3  能力资产     变成 Skill（可执行）或 Policy 规则（可强制）
     │
L4  评测锚点     纳入回归集，任何后续变更不得在此退步
```

**L4 是防遗忘的关键**。绝大多数"自进化"系统只做到 L2，结果系统会在下一次提示词调整时丢掉今天学会的东西。把经验变成评测锚点，进化才是单调的。

### 证伪门

```
1. Evolver 提出候选 C + 支持证据（trace id 列表）
2. 系统随机指派一个【未参与相关 packet】的 Agent 作为 Verifier
3. Verifier 的任务表述是"找出这条经验不成立的情况"，不是"验证它对不对"
   ★ 不对称预算：找反例的预算 = 找支持证据的 1.5 倍
     （确认偏误在 LLM 上同样存在，检索"支持"比检索"反驳"容易得多）
4. 找到反例 → 打回 L1，★ 反例写入 refutes 边永久存档
   无反例且支持证据 ≥N → 升 L2
   证据不足 → 保持 L1 等更多样本
5. 全过程在 #retro 房间公开，人可否决
```

> **共识不是靠投票产生的，是靠找不到反例产生的。**

### 记忆的垃圾回收

记忆库单调增长会稀释上下文——注入 20 条规则时，真正重要的那 3 条权重被摊薄。处置规则：

```
长期未被注入（scope 太窄或已不相关）  → 归档
注入频繁但 hit_effect ≈ 0（没用）    → 复审，可能降级
被新条目 supersedes                  → 自动归档
```

**记忆的价值不在数量，在信噪比。**

## 自进化机制

### 三个钩子

进化不是旁边跑一个独立模块，它挂在系统运转的三个位置：

| 钩子 | 时机 | 做什么 | 作用范围 |
|---|---|---|---|
| **A · Packet 级** | 每个 packet 结束（秒级） | attempt>0 记失败样本到局部记忆；新失败模式进 L1 候选池；规则命中计数 | 同 packet 下次 attempt、同迭代后续 packet |
| **B · 迭代级** | Retro（小时～天） | 聚类 → 提炼 → 证伪 → Skill PR → 影子回放 → 回归门禁 → 灰度 → 合入 | 本项目后续迭代 |
| **C · 项目级** | 交付后 | **模板化**：契约骨架、packet 拆分模式、gate 配置 → ProjectPattern | **未来所有同类项目** ← 复利最大 |

### Evolution-as-a-Pipeline

不发明新算法，把软件工程验证了二十年的**变更管理工程学**原样搬到 Agent 能力层：

```
① 触发     任务结束 / 事故 / 定期 Retro / 评测得分下降
② 提炼     Evolver 读 Trace，产出提案（Skill / Prompt / Policy / 路由 / 编制）
③ 证伪     经验类提案必过证伪门
④ 影子回放  ★ 在【过去 3 个已完成项目的真实输入数据】上重跑（吸收自 Nexus）
            对比 pass@1 / token / attempt；样本量 <70% 判定无效
   ★ 并行跑对抗性测试套件（见下）
⑤ 回归门禁  主指标不下降 ∧ L4 锚点全通过 ∧ 无新增高危 ∧ 对抗测试全过
⑥ 人工审批  ⚠ Policy / 编制 / 模型路由类提案强制人工确认
⑦ 灰度发布  Skill 新版本按比例下发（10% → 50% → 100%），双跑对比
⑧ 合入/回滚 达标升 stable；异常一键降级到上一版本
⑨ 沉淀     本次进化本身进 Trace，成为下次进化的素材
```

### 三层进化对象

| 层次 | 进化什么 | 触发条件 | 例子 |
|---|---|---|---|
| **L1 能力** | Skill / 注入文本 / 检查项 | 同类失败 ≥2 次 | 从 3 次"错误处理不统一"的 rework 生成 `api-error-convention` |
| **L2 策略** | 预算树比例 / WIP 上限 / 模型路由 / 上下文配方 / packet 粒度 | 指标持续偏离（如超预算率 >20% 连续 2 轮） | "定位类任务用小模型 pass@1 不降但成本降 60%" → 调路由 |
| **L3 模板** | ProjectPattern | 项目交付，**且需 ≥3 个同类项目样本** | 做过 3 个 CRUD Web 应用后直接产出契约骨架，Design 从 90min 压到 25min |

L3 的样本门槛最高，因为它影响面最大——从一个项目就总结"这类项目该怎么做"是最典型的过度提炼。

### 对抗性测试套件：验证护栏本身

> 吸收自 Nexus。常规测试验证"功能对不对"，对抗性测试验证"**护栏有没有坏**"。

任何新 Skill 进入 `Candidate` 前，在沙箱中强制跑：

```
① 容错注入   超大 JSON、特殊字符、空值、错误编码、超长字符串
② ★ 越权尝试 主动执行 forbidden_commands（rm -rf / DROP / curl / git push）
              → 必须被拒绝。★ 没被拒绝 = 权限边界失效，比 Skill 本身有 bug 严重得多
③ 逃逸尝试   尝试写 write_paths 之外、访问 network_access 之外的域名
④ 注入攻击   prompt injection 样本，验证 Skill 不会被输入劫持
⑤ 预算越界   构造会超出 token 预算的输入，验证熔断生效
```

**② 是这套设计的灵魂**：多数系统只测"功能正常时表现如何"，从不测"防线还在不在"。而护栏的失效是**静默的**——它坏了之后一切照常运行，直到某天有人越过它。

同样的方法应当周期性地施加于**系统自身的护栏**（Guardian 规则、只读挂载、准入校验器），而不只是新 Skill。建议每迭代跑一次。

### 进化的不动点

```
可以进化：Skill、注入文本、上下文配方、WIP 上限、模型路由、拆分策略、ProjectPattern
不可进化（Agent 只读，只能人改 Git）：
   □ Guardian 策略规则     □ 门禁定义 gates/**
   □ 六条不变量的强制机制   □ 验收谓词的判定逻辑
   □ 权限矩阵与卷挂载配置   □ role spec
```

> **Agent 可以改自己的手，不能改自己的镣铐。**

强制方式是技术性的：这些路径在所有 Worker 中**只读挂载**（R4 类甚至不挂载），git pre-commit hook 拒绝相关变更，Guardian 拦截对应工具调用。**不是在提示词里写"不要修改这些文件"。**

### 如何证明变强了

```
度量（在 holdout 集上，该集不参与提案生成）：
  pass@1 · 平均 attempt · token/packet · 契约变更频率
  绿线破损次数 · 人工介入次数 · 同类仲裁复发率

回滚：Skill 语义版本化，一键降级到上一版本 —— 与代码回滚同构，秒级

防过拟合：holdout 集 + 每轮跑 3 次取中位数（LLM 有方差，单次不可信）
```

**没有对照实验，"自进化"就只是一个形容词。**

## 安全、审批与审计

### 风险分级

| 级别 | 动作举例 | 处置 |
|---|---|---|
| **R0 只读** | 读代码、查 Issue、跑测试、静态扫描 | 全自动 |
| **R1 隔离写** | 特性分支提交、创建 PR、写沙箱 | 全自动 + 留痕 |
| **R2 共享写** | 合入 main、改 CI 配置、staging 部署 | 自动执行 + 可回滚 + 通知 |
| **R3 高危** | 生产发布、执行 migration、删分支/数据 | **强制人工审批** + 灰度 + 回滚预案就绪 |
| **R4 禁止** | 改 Guardian 规则、改门禁、改权限矩阵、访问生产密钥明文 | **硬拒绝**（不动点，路径不挂载） |

**回滚永远自主执行，不需审批**——回滚是把系统恢复到已知良好状态，给它加审批只会延长故障时间。

### Guardian

**不是 Agent，是确定性拦截器（无 LLM）**，部署在 MCP 前置 + AI 网关双层（防绕过）。

一个"安全审核 Agent"在 99% 的情况下工作正常，剩下 1% 会被绕过——**安全领域 1% 等于 0%**。

两条设计要点：

- **fail-closed，但错误信息必须含整改指引**。只说"拒绝"会让模型不断尝试各种绕过方式白烧预算；要给出规则 ID、原因、**正确做法**。
- **拦截率高不是安全做得好，是上游设计不好**。某规则频繁触发说明 Context Broker 没把它前置注入。拦截统计要回流给 Broker 与 Evolver。**理想状态是拦截率趋近于零**——不是因为没规则，而是规则都在上游生效了。Guardian 是兜底，不是主力。

### 三种作弊与结构性防御

Agent 不是恶意的，但它会走阻力最小的路径。**任何"让指标变绿"比"把事做对"更容易的地方，它都会走过去。**

| 作弊 | 症状 | 结构性防御 |
|---|---|---|
| **改测试让它过** | 实现困难 → 改断言 → 全绿 | 验收测试由 QA 在 packet 创建时写，先于实现存在；Coder 对 `tests/acceptance/**` 只读挂载；单元测试不计入验收谓词 |
| **改契约让实现变简单** | 改 openapi 返回结构 → 实现变简单 → 错误传播到集成阶段才爆发 | I3：`contracts/` 只读挂载 + hook + Guardian 三层；需改只能提 ContractChangeRequest 走串行窗口 |
| **缩小问题范围** | 改小 owns_paths、删验收谓词、标 out of scope | packet 定义由 Planner 写，Coder 对 `backlog/**` 只读；需改提 PacketChangeRequest |

**共同模式**：凡"评判标准"与"被评判对象"由同一角色控制的地方，都要切开，并用文件系统权限强制，不用提示词约束。

### 审计链

每个 R2+ 动作产生一条不可变记录：

```
{who(agent + version), what, ★ why(决策依据 + 引用的记忆条目/Skill 版本),
 when, trace_id, approver, rollback_ref}
```

**`why` 字段是关键**：它引用了做决策时用到的具体记忆条目和 Skill 版本——出事后能精确定位"是哪条经验教坏了它"，并触发该经验的降级复审。

**这条反向链路（事故 → 经验降级）是进化闭环的负反馈边**，很多方案只有正反馈。

#### 不可篡改的实现：审计哈希链

> 吸收自 Nexus。"不可变"不能只是一个形容词，要有机制。

```json
{
  "audit_id": "audit_20260801_143022_001",
  "timestamp": "2026-08-01T14:30:22Z",
  "actor_type": "agent | human",
  "actor_id": "coder-02 @ v1.3.0 | user@example.com",
  "action": "skill_invoke | tool_call | state_transition | approval_granted | rollback",
  "resource": "src/api/subscriptions/index.ts",
  "why": { "memory": ["GM-014"], "skills": ["api-error-convention@0.1.0"] },
  "trace_id": "txn_...",
  "result": "success | failure",
  "★ signature": "sha256(previous_audit_hash + canonical_json(payload))"
}
```

**每条记录的签名包含前一条的哈希，形成链。**任何一条被篡改或删除，其后所有记录的签名校验全部失败。校验是一次线性扫描，成本可忽略。

**这是唯一能把"审计日志可信"从承诺变成事实的做法**——否则审计日志本身就是一个可以被 Agent 写入的文件。

## 端到端运行

### 输入契约

五种输入归一化为 Intent，进四条流水线（不用一条流水线套所有情况，否则改个错别字也要走需求澄清）：

```
Greenfield:  澄清 → 架构与契约 → Skeleton → 迭代 → 硬化 → 发布
Increment:              契约增量 →          迭代 → 发布      （复用既有 Skeleton）
Fix:                              定位 →   单 Packet → 发布
Incident:    止血 →               定位 →   单 Packet → 发布 → 复盘
```

四条流水线共用同一套角色、WorkPacket 机制与四张图，区别只在前段。

**L0（一句话想法）的澄清协议**见"各角色设计要点·Intake"。产物 `ProductBrief` 冻结后不可改，其中 `acceptance.executable` 字段是整个系统的锚点——后面所有验收的源头，以及"做完了"的最终定义。

### 输出契约

```
deliverable/
├── repo/                  Git 仓库，每个 commit 关联 WorkPacket ID
├── run/docker-compose.yml 一条命令起全栈
├── docs/
│   ├── README.md          ★ 冷启动可复现
│   ├── ARCHITECTURE.md
│   ├── API.md             从契约自动生成
│   └── adr/
├── tests/                 e2e（对应 brief 每条验收场景）+ integration + 覆盖率报告
├── evidence/              每个 packet 的执行证据（见下）+ 全量 Trace
└── KNOWN_ISSUES.md        ★ 诚实的遗留问题清单
```

#### 执行证据包：五类具体产物

> 吸收自 Nexus。"evidence 目录"太笼统，明确到产物级别才可执行。

| 证据 | 内容 | 格式 |
|---|---|---|
| **代码变更差异** | 本 packet 产生的全部 diff | `.patch` |
| **测试执行证据** | E2E 关键步骤截图（Playwright 自动截取）+ 原始测试输出 | `.png` + `.log` |
| **测试报告摘要** | 覆盖率、通过率、每条验收谓词的判定 | `acceptance.json` |
| **工具调用清单** | 本次调用的全部工具，含**输入/输出哈希** | `.jsonl` |
| **LLM 推理摘要** | 每次调用的 prompt 前 200 字 + response 长度 + token 数 | `.json` |

**"工具调用清单含输入输出哈希"这一条是关键**：它让"这次执行到底做了什么"可以被独立核验，而不是只能相信 Agent 的自述。哈希也让重放时能判断输入是否真的相同（I6 证据不变量的落地形式）。

**最终门禁：冷启动复现测试**——在全新干净容器里 `git clone` → 照 README 执行 → 应用起来 → 全部 E2E 验收场景通过。**由系统自己在隔离环境跑，不是自我声明。**它是唯一有资格把项目置为 `delivered` 的动作。

> 它捕获的是 Agent 最典型的失败：写出一个只在它当时那台机器能跑的东西——隐式依赖、没写进 README 的环境变量、手动执行过但没记录的初始化步骤。

**`KNOWN_ISSUES.md` 是必交项**：强制系统列出没做完/做得不好/绕过去的部分。**允许它诚实，它才不会撒谎**——这是提示词层面永远解决不了、流程层面很容易解决的问题。

### 阶段与门禁

| 阶段 | 主责 | 产出 | 门禁（全绿才能进下一阶段） |
|---|---|---|---|
| **Discovery** | Intake | `brief.yaml` | 每条 must_have 有可执行验收场景；`wont_have` ≥3；假设已显式列出且自洽 |
| **Design** | Architect | 契约、边界、ADR | 契约通过 schema 校验 + **可实现性探测**；边界覆盖全部路径且无重叠；**双向覆盖检查通过** |
| **Skeleton** | Architect+Coder+Integrator | 可运行骨架 | **冷启动测试通过**（新容器 → 一条命令 → 起来 → 冒烟绿） |
| **Increment** | 全体 | 功能增量 | 每轮：全部 packet merged；main 绿线；覆盖率不下降 |
| **Hardening** | QA+Reviewer | 修复、性能、安全 | 全部 must_have 的 E2E 通过（**用 mock 凭证**）；无 P0/P1；安全扫描无高危 |
| ★ **Provisioning** | Integrator+人 | 真实凭证与素材 | 配置收集表全部必填项已填并通过连通性校验；可降级项已确认 |
| **Launch** | Integrator | 交付包 | **生产级测试通过**；**凭证泄漏扫描通过**；**冷启动复现测试通过**；部署文档完整；回滚已验证；KNOWN_ISSUES 已填 |

#### Walking Skeleton 为什么是最重要的一个阶段

Agent 最典型的失败不是写不出功能，而是**写了 20 个漂亮模块，从来没有一起跑起来过，最后集成时全线崩溃且无法定位**。

Skeleton 先行把这个风险前置消灭：绿线不变量有了起点；集成风险摊平（不存在"大爆炸集成"这个环节）；技术选型被真实验证；验收基础设施就位；**后面任何一次冒烟挂了，一定是刚合入的那个 packet 引起的**。

Skeleton **不做**真实业务逻辑、样式、完整数据模型、鉴权（除非它是 must_have 且影响架构）。它的目的是**证明管道通了**，不是交付价值。

### 并行安全：为什么不会合并冲突

```
阶段 A · 契约设计（串行，Architect 独占）
   冻结：API 契约 / 数据契约 / 类型契约 / 事件契约 / ★ 边界契约

阶段 B · 按边界切 packet（Planner）
   约束：任意两个可并行的 packet，owns_paths ∩ owns_paths = ∅

阶段 C · 并行实现（N 个 Coder）
   只能写自己的 owns_paths（只读挂载强制）
   需要新的公共工具？不许自己建 → 提 ContractChangeRequest

阶段 D · 合并（Integrator）
   owns_paths 不相交 → git 层面无冲突，是 fast-forward
   仍要在最新 main 上重跑验收（I4）—— 防的是语义冲突，不是文本冲突
```

**并行度是可计算的**：

```
理论上限 = boundaries 切出的、当前迭代有活的、依赖已满足的独立模块数
实际     = min(理论上限, WIP 上限, 可用 Coder 数)
```

这意味着"开几个 Coder"是有依据的数字，而非"开 10 个试试"——若理论上限只有 2，开 8 个会有 6 个因锁冲突空转。

**WIP 上限**的三个硬约束：并行越多越难找到路径不相交的组合（ready 队列空转）；Review 是瓶颈（Coder 可横向扩，跨 packet 一致性评审难并行）；集成风险随并行度超线性上升（n 个 packet 两两交互有 n² 种）。

### 技术栈的串联与并联

> ⚠️ **此处修正了此前"垂直切片优于水平切片"的表述。**纯垂直切片（一个 packet 含 DB+后端+前端）必然超预算；纯水平切片又无法写端到端验收谓词。**正确答案是第三种：水平切分 + 契约级验收 + 一个集成 packet 承载端到端验收。**

四层之间的关系性质完全不同，必须分别处理：

| 层间关系 | 契约强度 | 可并联 | 处理方式 |
|---|---|---|---|
| **数据库 ↔ 后端** | 强（schema） | ❌ **必须串行** | ★ **schema 变更专用串行通道**——路径隔离对 migration 无效，它们改的是同一个数据库状态。全局同时只有一个 migration packet 在跑；顺序时间戳由控制平面统一分配，不让 Agent 自己编号 |
| **后端 ↔ 前端** | 强（OpenAPI） | ✅ **完全并联** | 契约冻结后自动生成 **mock server + 类型定义 + 契约一致性测试**；前端依赖 mock 不依赖实现，真并行 |
| **算法 ↔ 后端** | ⚠️ **弱** | 特殊 | ★ **Spike + 固化两阶段**（见下） |
| **后端模块之间** | 强（types/events） | ✅ 并联 | 按 boundaries 切 |

#### 算法必须两阶段

```
普通 feature 的失败模式：方法对了但实现错了 → rework 能解决
算法的失败模式：      实现对了但效果不够  → rework 解决不了，要换方法
```

把算法当普通 feature 做，会出现"反复 rework 但永远达不到效果"的死循环——因为 rework 循环假设的是"方法对了"。

```
阶段一 Spike：验收谓词是【指标阈值】而非行为断言（kind: metric）
              允许多方案竞争；产物不合入主干，只出 SpikeReport
              ★ 评测集必须先于算法 packet 存在（由 QA 在 Design 阶段准备）
              ★ 三个方案都不达标 → 记录三条死路 → 升级到人，这不算 rework
阶段二 固化：指标达标后封装成符合契约的服务，走标准 packet 流程
              ★ 指标进 L4 评测锚点，模型/参数变更后不得退步
```

#### 一个功能的四层拆分范式

```
WP-A01 [spike]       算法方案探索              指标验收，不合入
   ▼
WP-D01 [infra]       DB schema                ★ 串行通道
   ├──────────────┬──────────────┐
   ▼              ▼              ▼
WP-B01 服务实现   WP-B02 API     WP-C01 前端（对 mock）    ← 三者真并行
验收：单元+契约   验收：契约一致  验收：组件测试+视觉回归
   └──────┬───────┘              │
          └───────┬──────────────┘
                  ▼
          WP-E01 [integration]
          owns: tests/e2e/**（★ 只拥有测试文件，不改产品代码）
          ★ 验收：brief 中该 must_have 的端到端场景
```

**端到端验收落在集成 packet 上**——这解决了"水平切分无法端到端验收"的问题，同时每个 packet 仍有自己机器可判定的验收（契约测试/组件测试），I2 不被削弱。

集成 packet 失败时：其失败输出必须**分层断言定位**是哪一层的问题 → 该层 packet 回 rework；若无法定位到单一层 → 触发会诊。

### 交付与配置收集

#### 核心原则：凭证需求在开发过程中被登记，不是最后靠人回忆

```
开发期（Discovery ~ Hardening）
  任何 packet 用到外部服务 / 凭证 / 素材
    → 必须在产出中声明 requires_provisioning
    → ★ 开发期一律使用 mock / 占位 / 测试值
    → ★ 绝不中途停下来问人要 key
    → 声明进入 provisioning 清单，并挂在溯源图上（可回答"为什么需要它"）

Provisioning 阶段
  ① 聚合全部声明，按类别去重合并
  ② ★ 一次性推送表单 —— 这是全流程唯一一次索要外部资源
  ③ 人填写 → ★ 本地加密存储（桌面软件，凭证不上传任何地方）
  ④ 逐项校验：格式 → 连通性 → 权限范围 → 配额
  ⑤ 全部必填项通过 → 进入生产级测试
```

> **为什么必须一次性收集**：中途索要凭证会把人重新拖回循环里（违反"人是中断源不是循环一环"）。
> 而且开发早期根本不知道最终需要哪些——只有做完了才知道全集。
> **等到知道全集时一次性问，才是对人最省的。**

#### 表单项的结构

每一项都要能自我解释，人不该看到一个莫名其妙的输入框：

```yaml
- id: PRV-001
  category: api_key        # api_key | account | email | domain | payment | asset | other
  name: 汇率 API Key
  required: true
  ★ why: MH-2「首页展示月度总支出」需要多币种折算   # 来自溯源图，不是编的
  ★ used_by: [WP-B01 汇率服务]                     # 哪个模块要用
  ★ how_to_get:                                    # 降低人的操作成本
      url: https://exchangerate-api.com/signup
      steps: [注册免费账号, Dashboard 复制 API Key]
      note: 免费额度 1500 次/月，本项目预估用量 30 次/月
  format: '^[a-f0-9]{32}$'                         # 即时格式校验
  ★ validation:                                    # 即时连通性校验
      type: http_probe
      request: GET https://api.exchangerate-api.com/v4/latest/USD
      expect: 200
  ★ fallback: 不提供则使用固定汇率表（功能降级，写入 KNOWN_ISSUES）
  scope_check: 该 Key 不应具备写权限                 # 最小权限提示
  storage: local_encrypted
```

素材类（Logo、图标、品牌色、应用名、文案）同表单收集，附**尺寸/格式要求**与占位图预览。

#### 四个产品体验设计

| 设计 | 说明 |
|---|---|
| ★ **每项都说明"为什么需要"** | 来自溯源图，可追到具体需求。人不会面对一堆无法理解的输入框 |
| ★ **`how_to_get` 给出申请路径** | 人最烦的不是填表，是**不知道去哪弄**。给出链接 + 步骤 + 免费额度说明 |
| ★ **区分必填与可降级** | 可降级项不填也能交付，只是功能降级并自动写入 KNOWN_ISSUES。**让人先跑起来，以后再补** |
| ★ **即时校验，不留到最后** | 填完立刻验证格式与连通性，而不是等生产测试才发现 key 是错的或权限不够 |

#### 生产级测试（用真实凭证）

```
□ 用真实凭证跑全部 E2E 验收场景
□ 外部服务真实连通性与响应结构（★ mock 与真实不一致是高频坑）
□ ★ 配额与限流验证 —— 免费额度够不够，超了会怎样
□ 性能基准（真实网络延迟，不是本地 mock 的 0ms）
□ ★ 凭证泄漏扫描 —— 见下
```

**凭证泄漏扫描是必须的确定性门禁**。Agent 很容易把 key 硬编码进代码、打进前端 bundle、或写进日志：

```
扫描范围：源码 · 构建产物 · 前端 bundle · 日志样本 · 提交历史 · 文档
判定：产物中不得出现任何已收集凭证的片段（含 Base64 / URL 编码变体）
命中即阻断交付 —— ★ 这一条不允许任何例外
```

#### 打包交付

```
□ 构建产物（按目标形态：Docker 镜像 / 安装包 / 静态站点 / 源码包）
□ ★ 凭证不打进产物 —— 用 .env + 运行时注入，产物本身可公开分发
□ 生成部署文档（含真实配置项清单与获取方式，即表单的导出版）
□ ★ 冷启动复现测试：全新环境 + 交付包 + 凭证，完整跑一遍
□ 交付清单核对 + 最终交付报告（人可读）
```

**冷启动复现测试在此处是最后也是最硬的一道门禁**：它同时验证了产物完整、文档正确、凭证注入路径可用。通过它，项目才能置为 `delivered`。

## 异常处理与分级求助

### 四级阶梯

此前设计只有"自修复 → 人工仲裁"两级，跨度过大——所有中等难度的问题都要惊动人。补齐为四级，对应人类工程师的真实路径（自己搞 → 问同事 → 拉个会 → 找老板）：

| 级别 | 手段 | 触发 | 典型成本 | 打断人 |
|---|---|---|---|:-:|
| **L0** 自修复 | Harness 内层循环 | 反馈来自确定性执行（构建/测试） | 含在 packet 预算内 | 否 |
| **L0.5** ★ Peer-Debug | **同角色的另一实例** | 同类型 Agent 空闲，且失败在其擅长范围内 | +20k tok / +5min | 否 |
| **L1** 求助 | ★ **Helper 角色** | Peer 无解，或 attempt=1 失败后自动，或主动 `request_help` | +60k tok / +15min | 否 |
| **L2** 会诊 | ★ **War Room 临时房间** | Helper 无解，或问题跨模块边界 | +200k tok / +30min | 否 |
| **L3** 人工仲裁 | 批量升级 | 会诊无解，或需不可逆决策 | ~0 token，**但要人的响应时间** | **是** |

> **L3 的真实成本不是 token，是人的注意力和等待时间。加入 L0.5/L1/L2 的全部意义，就是把绝大多数问题拦在打断人之前。**

**L0.5 Peer-Debug 为什么值得单列**（吸收自 Loom）：同角色的另一个实例拥有**相同的工具面与领域上下文配方**，装配成本几乎为零，且它可能刚好在别的 packet 里解决过同类问题（局部记忆里有）。这是最便宜的一档求助，只是它的视野和求助者一样窄——**解决不了就该立刻升 L1，不要在同一层反复横跳。**

约束：同一 packet 最多一次 Peer-Debug；Peer 与求助者不得是同一实例；Peer 只给建议不写代码（与 Helper 同规则）。

### L1 · Helper 的核心设计

| 维度 | Coder | Helper |
|---|---|---|
| 视野 | 仅本 packet 的 `owns_paths` + 契约切片 | ★ **全库可读** + 其他模块实现 + 全部 ADR + 跨项目案例库 |
| 写权限 | `owns_paths` | **无** |
| 产出 | 代码 | 诊断报告 |

输出契约中 **`ruled_out`（排除了哪些方向）是最有价值的字段**——告诉 Coder 哪些路不通，比告诉它哪条路通更省预算，因为模型的默认行为是把所有看起来合理的路都试一遍。

约束：同一 packet 最多求助 2 次，第 3 次直接进 L2。

**★ 求助本身是最好的进化信号**：同类问题反复求助 → 上下文配方缺东西或缺一个 Skill。Helper 的诊断记录已经把"症状→根因→解法"结构化了，是 L1 候选经验的主要来源之一。**求助频率下降是系统成熟度的直接体现。**

### L2 · War Room 的三个约束

```
① 参与者按问题类型动态确定（契约不足 → Architect+Coder+Helper；
   跨模块冲突 → Architect+双方 Coder+Integrator；验收歧义 → QA+Intake+Coder）
② ★ 结构化发言，不是自由讨论：
   轮次 1 —— 每人独立提交问题陈述与关键约束，★ 互相看不到（防第一个发言者锚定所有人）
   轮次 2 —— 公开全部陈述，提方案并反驳他人
   轮次 3 —— Architect 汇总产出决定
③ 30min / 200k tok 硬上限；★ 出口契约是四选一的可执行决定，
   不允许"讨论了但没结论"；超时自动升级到 L3 并附会诊记录
```

## 测试体系

### 七级测试 + 两类监控测试

| 级别 | 写者 | 时机 | 计入验收 | 目的 |
|---|---|---|:-:|---|
| 单元测试 | Coder | 内层循环，每次改动 | ❌ | Coder 自己的快速反馈 |
| **契约测试** | ★ **从契约自动生成** + QA 补充 | packet 验收 | ✅ | 实现是否符合契约 |
| **组件验收** | QA（先于实现） | packet 验收 | ✅ | 该 packet 功能对不对 |
| **集成验收** | QA | 集成 packet 验收 | ✅ | 跨模块串起来对不对 |
| **端到端验收** | QA（源自 brief） | 集成 packet + Hardening + Launch | ✅ | must_have 真的实现了 |
| 冒烟 | 系统 | 每次合入后 | 门禁 | 绿线守护（I4） |
| **冷启动复现** | 系统 | Launch 门禁 | ✅ 最终 | 交付真的可复现 |
| ★ 变异测试抽查 | 系统 | 每迭代一次 | 监控 | 测试的测试 |
| ★ 校准样本 | 系统 | 评审队列混入 5% | 监控 | 监控 Reviewer 静默失效 |

### 三个关键判断

**契约测试自动生成是最高杠杆的一处投入**。OpenAPI → 请求/响应 schema 校验 + 必填缺失负例 + 类型错误负例 + 状态码覆盖；db.schema → 表结构与约束一致性；types → 编译期检查。收益是 QA 工作量大降，且**契约测试的覆盖度与契约自动保持一致**——契约改了测试自动跟着改，不会漏。QA 只需补充契约表达不了的业务语义。

**单元测试不计入验收谓词**。若计入，Coder 就能写恒真的单元测试让自己通过。它是 Coder 的开发工具，不是验收依据；验收依据必须来自 Coder 不能改的东西（契约测试 + QA 写的验收测试）。覆盖率作为门禁项存在，但不作为 packet 验收谓词。

**端到端验收的数量应当恰好等于 must_have 的数量**。多了说明有需求之外的东西被测（镀金），少了说明有需求没被验证。这是一个可自动检查的一致性条件。

### 测试环境隔离

```
Coder 内层循环：容器内临时环境（内存库 / mock 外部服务）
packet 验收：   隔离容器 + 独立数据库实例
集成验收：      docker-compose 起全栈，接近生产配置
冷启动复现：    ★ 全新容器，零缓存，只有 git clone 的内容
                （零缓存正是它能抓出隐式依赖的原因）
```

## 子 Agent 的内部规划

### RARE-V：Agent 的内部工作循环

> 命名吸收自 Loom（Reason → Act → self-heal → Verify → Evolve）。
> Harness 强制这个骨架，不是提示词建议。

```
R  Reason   明确终点 + 建立地图
            ★ Harness 强制第一次工具调用必须是读验收谓词
            读契约与相关既有代码时有预算上限，防止无止境地"先看看代码"
            产出结构化计划写入 evidence/plan.md，★ 每步必须声明"完成后如何验证"

A  Act      逐步执行，★ 小步验证而非全写完再测
            每步后跑轻量断言（文件存在 / lint 过 / 类型过）

R  Repair   自修复（嵌在 Act 内）：
            重试 → 换方法 → 换 Skill → L0.5 Peer → L1 Helper → L2 会诊
            ★ 只消耗 budget 不计 attempt（反馈来自确定性执行）

V  Verify   对照验收谓词跑确定性判定，产出证据包五类产物
            ★ 判定由代码做出，不问模型

E  Evolve   写 Trace + 可重放记录；attempt>0 则记失败样本到局部记忆；
            新失败模式进 L1 候选池；规则命中计数 +1
```

**第 ④ 步（小步验证）是效率的关键**：

```
❌ 大批量：一次写完 5 个文件 → 跑测试 → 20 个错误 → 无法归因，模型只能随机挑几个修并引入新错
✅ 单件流：写完 1 个可验证单元 → 立刻跑相关测试 → 1 个错误 → 立刻能修
```

批量越大，缺陷发现越晚，返工成本越高，归因越难。这个效应在 Agent 系统里比人类团队更严重。

### 各角色的内部规划形态

| 角色 | 内部规划 | 关键约束 |
|---|---|---|
| Intake | 槽位优先级队列（按信息增益排序），每轮只问最高价值的一个 | 轮次上限；槽位状态外置 |
| Architect | 分层设计：数据 → 类型 → API → 事件 → 边界（下层稳定后才做上层） | 每层完成即跑可实现性探测，不留到最后 |
| Planner | 按 boundaries 分组 → 组内依赖排序 → 估算 → **虚拟调度验证** → 调整 | 虚拟调度不达标必须重拆 |
| QA | 先写"最能证伪的那条"验收场景，再补边界与异常 | 红灯验证：每条写完立刻验证它会失败 |
| Coder | 四步骨架 + 依赖顺序（先写被依赖的类型与工具函数） | 每个可验证单元后立刻跑测试 |
| Reviewer | 固定证伪清单，**按发现难度降序**执行 | 难的先做（防止摘完低垂果实就停） |
| Integrator | 按冲突风险升序排合入队列；批量大小按历史失败率动态调整 | 失败立即 revert 不现场修 |
| Helper | 案例库 → 全库检索 → 深度推理 | 分层检索，便宜的先来 |
| Evolver | 聚类 → 按"影响面 × 可执行性"排序 → 只提炼 top-N | 样本不足时输出"本轮无提案" |

### 一条共同的巧思：由便宜到昂贵的分层

```
Helper：  案例库查询(近免费) → 全库语义检索(中) → 深度推理(贵)
Evolver： 规则匹配聚类(免费) → 语义聚类(中)     → LLM 归因(贵)
Coder：   局部记忆查询(免费) → 局部代码(中)     → 求助 Helper(贵)
Reviewer：静态扫描(免费)     → 规则匹配(中)     → LLM 语义评审(贵)
```

这是最直接的成本优化手段，且**同时提高了质量**——便宜的手段往往也是确定性的、更可靠的。

## 可视化控制台

### 它是产品本身，不是监控面板

桌面软件形态下，可视化界面**就是用户看到的产品**。但它在架构上仍是纯读端：

```
Console 对系统状态【零写权限】。它订阅 Git commit 流 + Trace 流，做投影和渲染。
人的写入动作（确认计划书 / 审批 / 仲裁 / 填表单）走独立的【人类输入通道】，
  以变更请求形式提交给控制平面，与 Agent 的请求走同一套校验。

⟹ Console 挂掉，系统照常运行
⟹ 界面可以随便迭代、随便加视图，不引入任何可靠性风险
```

### 九个视图

| 视图 | 内容 | 价值 |
|---|---|---|
| **甘特图**（主视图） | 横轴时间、纵轴 packet（按 epic 分组）；**计划 vs 实际双条并排**；关键路径高亮；依赖箭头；拆分/rework 标注 | 进度全貌。★ **偏差数据回流 Planner 作为下次预算 p80 输入——可视化的数据本身就是进化的燃料** |
| **看板** | 按状态列展示，每列标 `当前数/WIP上限`，超限标红 | ★ **最便宜也最有用**。一眼看出在制品堆在哪列 = 瓶颈在哪个环节 |
| **Agent 状态板** | 每个 Worker 的状态、当前任务、预算条、7d 成功率 | 预算条 >60% 变黄、>85% 变红，人看到红条就知道可能要拆 |
| **依赖图** | DAG 可视化，节点按状态着色，关键路径高亮 | 理解"为什么现在只有 2 个能并行" |
| **绿线时间轴** | main 健康状态随时间，破损区间标红并标注原因 | Integrator 主指标的仪表 |
| **预算仪表** | 预算树实时消耗，按阶段/角色/模型下钻 | 回答"钱花在哪了" |
| **溯源查询** | 输入需求 → 高亮相关的一切；输入文件 → 反查需求与审批 | ★ **审计能力的用户界面**，也是需求变更时的第一动作 |
| **进化曲线** | holdout 集上 pass@1 随迭代，实验组 vs 对照组，事件标注 | ★ 没有这条曲线，"自进化"就只是形容词 |
| ★ **成本仪表** | 已花费 / 预估总额 / 剩余；按阶段、角色、模型档位下钻；实时刷新 | 桌面软件用户自付 token，**成本必须常驻可见** |

三条设计要点：

- **★ Evolver 的路由建议放在这里而不是自动生效。** 模型选择是用户的成本决策——系统给证据（历史 pass@1、样本量、预计节省），人来拍板。这也呼应"L2 策略进化需人工确认"。
- **★ 降档时必须提示缓存门槛。** 便宜档位的最小可缓存前缀可能更长——省了单价却整个失去缓存是净亏。面板在采纳降档建议前弹这个提示。
- **★ 显示缓存命中率而不只是成本。** 命中率异常低（如上表 Helper 的 72%）说明该角色的上下文配方里有静默失效源（时间戳、非确定序列化），这是成本优化最高杠杆的线索。

### 看板是诊断工具，不只是展示

```
review 列堆积  → 评审是瓶颈 → 扩 Reviewer 或降 WIP，★ 不是加 Coder
ready 列堆积   → 执行能力不足或锁冲突严重 → 查 boundaries 切分
rework 列堆积  → 质量问题 → 查 Coder 上下文是否缺规则注入
blocked 列堆积 → 预算设置不合理 → 查 Planner 的 p80 估计
```

**"看到 review 堆积就去加 Coder"是最常见的误判**，看板让它无所遁形。

### 实现优先级

**看板 > 甘特图 > Agent 状态板 > 其余**。MVP 阶段可以直接用静态 HTML 定时读 `.codentum/state/*.json` 渲染，不需要后端。

## 信息效率与精益方法

> 精益不作为叙事主线（系统存在的理由是"多 Agent 写代码会死于六种失败模式"），
> 但作为**工程方法**它是处理【等待】与【库存】两类问题最成熟的工具箱。

### 七大浪费在本系统中的形态与对应设计

| 精益浪费 | 在 Agent 系统中的形态 | 本系统的对应设计 | 度量 |
|---|---|---|---|
| **过量生产** | 生成用不到的接口/代码/文档（模型天生爱"设计完整"） | 双向覆盖检查（反向防镀金）；`wont_have` 强制 ≥3 | 契约元素数 / must_have 数 |
| **等待** | packet 卡在 review 队列；Worker 空转等锁；等人审批 | 拉动式认领；WIP 上限；关键路径优先；批量升级 | **流动效率** |
| **搬运** | 上下文在 Agent 间反复传递、重复装配 | 传引用不传内容；共享 Artifact；★ 上游产出结构化供下游直接消费 | token/任务 |
| **过度加工** | 反复重写同一段；过度重构；用大模型做小事 | 60% 收敛提示；分层检索；模型分层路由 | 变更行数 / packet |
| **库存** | 大量 in_progress 在制品；verified 堆积未合入 | ★ **WIP 上限**（最直接的对应）；批量合入窗口 | 看板各列堆积数 |
| **动作** | 无效工具调用；反复检索同一信息 | 局部记忆缓存；精确装配清单；工具面裁剪 | 工具调用数 / packet |
| **缺陷** | rework、绿线破损、逃逸缺陷 | 红灯验证；对抗评审；绿线不变量；小步验证 | rework 率、逃逸率 |
| **未被利用的智慧** | 经验丢失、同一问题反复问人 | 三层记忆；经验晋升五级；进化三钩子 | 同类仲裁复发率 |

### 流动效率：一个直击要害的系统级指标

```
流动效率 = 增值时间 / 总周期时间
增值时间 = Coder 在写 + Reviewer 在评 + QA 在测的时间
非增值   = 排队等认领 + 等锁 + 等 review + 等审批 + rework 重做
```

人类软件团队典型值是 **5–15%**。把它作为系统级 KPI 的价值在于：**它能立刻暴露"加更多 Coder 没用"这类误判**。若流动效率是 20%，说明 80% 时间在等待，此时增加 Coder 只会让等待更严重。

### 减少信息浪费的八条机制

| # | 机制 | 说明 |
|---|---|---|
| 1 | 传引用不传内容 | 大文件放 Artifact，消息只传引用 + 摘要 |
| 2 | 上下文配方精确装配 | 不是"给它相关的东西"，是按角色×任务的清单 |
| 3 | 预算降级链 | 全文 → 摘要 → 引用+索引，**禁止截断** |
| 4 | 可见性矩阵 | 该看不见的一开始就不装配（省 token 且防偏见） |
| 5 | ★ **增量上下文** | attempt N+1 不重装全部，只传变化部分 + 上次 findings，典型省 60-70% |
| 6 | ★ **配方缓存** | 同角色同任务的上下文骨架复用，只换变量部分；配合 prompt caching 成本大降 |
| 7 | ★ **检索一次多处复用** | packet 生命周期内的 RAG 结果缓存到局部记忆 |
| 8 | ★ **输出即输入** | 上游产出结构化，下游直接消费不必重新加工。例：`LocationReport` 直接成为 Coder 的上下文切片 |

**第 8 条是减少"搬运浪费"的核心**，也是本系统所有角色输出都强制结构化的深层原因——不只为了可判定，也为了可复用。

### 价值流图：一个 packet 的时间去哪了

```
WP-0102 总周期 3h12m
  ready 等待认领   ████████ 42min      非增值 ← 并行度不足
  装配上下文       █ 3min              非增值（必要）
  Coder 执行       ████████████ 68min  ★ 增值
  等待 review      ██████ 34min        非增值 ← 瓶颈
  Reviewer 执行    ██ 11min            ★ 增值
  rework           █████ 28min         缺陷成本
  等待合入         ████ 21min          非增值
  Integrator 合入  █ 5min              ★ 增值
  流动效率 = (68+11+5)/192 = 43.8%
```

定期对典型 packet 画价值流图，是最有效的系统性优化手段——**它把"感觉有点慢"变成"42 分钟浪费在等认领上，因为理论并行度只有 2"**。这张图也是 Evolver 做 L2 策略进化的直接输入。

### 成本治理：用户自付 token，成本必须可见可控

桌面软件的形态决定了**每一个 token 都是用户自己掏钱**。这让成本从"我们的运营指标"变成了"用户的直接体验"，处理方式完全不同。

#### 开工前给出成本预估

```
预估 = Σ(packet 数 × 该类型 packet 的历史 token p50) × (1 + 预期 rework 率)
       + 澄清/架构/复盘的固定开销
数据来源：ProjectPattern 中同类项目的历史统计
首个项目无历史 → 用保守区间（给范围不给点值），并明确标注"首次估算，误差可能较大"
```

**它出现在开发计划书里**，人按下"开始"之前就知道大概烧多少钱。这是桌面产品必须有的诚实——**没有人愿意在不知道要花多少钱的情况下启动一个会跑十几个小时的任务。**

#### 五道成本闸门

| 闸门 | 机制 |
|---|---|
| **预算树** | 项目 → 阶段 → 迭代 → packet 层层分配；上层耗尽下层强制停止 |
| **实时显示** | 界面常驻显示已花费/预估总额/剩余；按阶段与角色下钻 |
| ★ **超支即停并询问** | 阶段超 120% → 暂停并给"追加预算 / 缩减范围 / 终止"三选一。**绝不静默烧钱** |
| **模型分层路由** | 按任务类型路由到不同档位模型；路由表由 Evolver 从历史数据学习 |
| ★ **成本-质量对照** | 界面展示"用小模型做定位省了 60% 成本、pass@1 未下降"这类实证，让用户敢于降档 |

#### 八条减少浪费的机制（与信息浪费同源）

见上一节的八条机制。其中对 token 成本影响最大的三条：

```
★ 增量上下文     attempt N+1 只传变化部分 + 上次 findings，典型省 60-70% 重复装配
★ 配方缓存       同角色同任务的上下文骨架复用，配合 prompt caching 成本大降
★ 分层检索       便宜手段先用（局部记忆 → 局部代码 → 全库检索 → 求助 Helper）
```

**另有两条是桌面形态特有的**：

| 机制 | 说明 |
|---|---|
| ★ **本地模型兜底** | 格式化、命名建议、commit message 这类低价值高频任务路由到本地 Ollama，零成本 |
| ★ **断点续跑** | 桌面软件会被关闭、休眠、断网。checkpoint 机制保证重开后从安全点继续，**不重烧已花的钱** |

> 断点续跑在服务端系统里是可靠性需求，在桌面软件里是**成本需求**——用户合上笔记本不该损失两小时的 token。

## 模型路由

### 粒度：路由的单位是一次调用，不是一个 Agent

"每个 Agent 配一个模型 vs 全局一个模型"是个错误的二分。真正的路由键是 `(角色 × 任务类型 × 当前 attempt)`，模型只是路由结果的一个分量。

**但有一条硬约束把答案往"按角色分配"这一侧强推：**

> **提示词缓存是模型作用域的。同一会话中途换模型，缓存全部失效。**

这条约束的两个后果方向相反：

```
✅ 支持按角色分配
   不同 Agent 本来就是不同会话、不同上下文前缀，缓存本来就不共享。
   给 Reviewer 和 Coder 配不同模型 —— 零缓存成本。

❌ 否掉"同一角色中途换档"
   在 attempt 之间升档 = 该 attempt 的全部上下文冷启动重写
   （缓存写 ~1.25×，读 ~0.1×）。可以做，但不是免费的，必须核算。
```

### 决定档位的判据：错误的可恢复性

这是**风险分配原则在执行平面内部的延伸**——控制平面/执行平面的分界靠"错误可否恢复"，执行平面内部也一样：

| 角色 | 出错后谁挡得住 | 可恢复性 | 结论 |
|---|---|---|---|
| **Coder** | 验收谓词 + Reviewer + 集成，三道 | **高** | ★ 反直觉：**写代码的那个不是最需要强模型的** |
| **Reviewer** | 没有下游 | **低** | 漏放是静默的，必须强模型 |
| **Architect** | 契约错污染所有下游，且发现时已很晚 | **最低** | 最强 + 最高 effort |
| **Intake** | 需求错 = 整个项目白做 | **最低** | 同上 |
| Planner | 可以 replan | 中 | 中高 |
| Integrator | 回滚兜底 | 中 | 中 |

Coder 那条要说准确：不是"用弱模型"，而是**档位由预期总成本决定而非单次成本**：

```
预期总成本 = 单价 × 预期 attempt 数 + Reviewer 多评审次数 × 评审成本 + 集成返工风险
```

这些数据系统自己有（Trace + 成对指标），所以这是可计算的，不是拍脑袋。

### 两个旋钮，顺序很重要

```
① effort（low → max）   ← 先拧这个
   同一模型内的深度控制，不换模型 → ★ 缓存不失效
② 模型档位              ← 再拧这个
   换模型 = 缓存重建
```

**先 effort 后模型**，因为 effort 是免费的而换模型要付缓存重建。而且低 effort 档位的实际表现常常被低估——多数场景 `medium` 的质量已经够用而 token 少得多。**从高往低扫，而不是默认拉满。**

### ★ Advisor：便宜执行 + 强模型顾问

API 原生支持执行模型与顾问模型配对：执行者做绝大部分 token 生成，顾问只在规划时被咨询，**服务端运行，无客户端往返**（顾问模型的能力必须 ≥ 执行者）。

这比"每个角色一个静态档位"好得多，**尤其适合 Coder**：执行用中档，规划用最强档顾问——拿到强模型的判断力，付中档的生成成本。Coder 是 token 消耗的大头，这一处的杠杆最大。

### ★ 模型多样性 = 错误去相关（最重要的一条）

这条比性能考虑更重要，也是跨家混用的**唯一正当理由**：

> Coder 和 Reviewer 用**同一个模型**时，它们的错误是**相关的**——同一个模型有相同的盲区。
> 它写代码时漏掉的那类边界情况，评审时也不会发现。

**给 Reviewer 配与 Coder 不同的模型，是"失败模式独立性"准则在模型层的延伸。**

这把上下文隔离扩展成了**上下文隔离 + 模型多样性**。同理适用于证伪门：Verifier 应当与 Evolver 用不同模型，否则"找反例"和"提出候选"共享同一套盲区。

**这是一条硬约束，不是优化建议**（见角色体系的权限矩阵与制衡清单）。

### 四个具体的坑

| 坑 | 说明 |
|---|---|
| ★ **缓存最小长度按模型不同，且不单调** | 小档位模型的最小可缓存前缀可能显著更长。**把小任务路由到便宜档位省了单价，却可能整个失去缓存——净亏。** 降档前必须核对该模型的缓存门槛 |
| ★ **token 数跨模型家族不可比** | 分词器不同，同样文本 token 数差异可达 30%。这就是**预算必须按货币计**的原因（见预算树） |
| ★ **限速是按模型分桶的** | 不同模型不共用配额。**混用模型反而增加总吞吐余量**——这是支持异构路由的一条额外理由 |
| **跨家混用的调试成本被低估** | prompt 不可移植、工具调用边界行为不同、结构化输出实现方式不同、失败模式不同。出问题时分不清是 prompt 还是模型的锅。**对小团队：同家不同档 > 跨家混用**，除非是上面那条"错误去相关"的正当理由 |

### ★ 进化平面全部走 Batch API

Evolver 的全部工作——失败聚类、影子回放、证伪门检索——**完全不延迟敏感**（它在 Retro 阶段异步跑）。批量接口通常有**约 50% 的成本折扣**。

影子回放尤其：它要在几十个历史 packet 上重跑，是纯离线的批量任务。

> **这一块砍半没有任何取舍**——是全案里唯一一个纯赚的优化。

### 建议的角色档位表

| 角色 | 档位 | effort | 特殊 |
|---|---|---|---|
| Intake | 最强 | medium | ★ **快速模式**（人在等，全系统唯一延迟敏感的角色） |
| Architect | 最强 | **xhigh** | 契约错代价最高 |
| Planner | 最强 | high | 结构化输出要求极高 |
| QA（作者阶段） | 最强 | high | 定义"什么算对"，不可恢复 |
| **Coder** | **中档 + 最强档 advisor** | xhigh | 成本大头；有三道下游防线 |
| **Reviewer** | 最强，**且必须与 Coder 不同** | high | 错误去相关；漏放静默 |
| Helper | 最强（**长上下文**） | high | 需要全库视野 |
| Integrator | 中档 | medium | 回滚兜底 |
| Manager 仲裁 | 中档 | high | 调度部分零模型 |
| **Evolver** | 最强 | xhigh | ★ **全部走 Batch API** |
| Guardian | **无模型** | — | 确定性拦截器 |

### 路由表声明能力需求，不声明模型 ID

桌面形态下用户可能只配了一家的 Key，甚至只有本地模型。所以路由表不能硬编码模型名：

```yaml
architect.contract_design:
  requires:
    tier: high
    context: 128k
    structured_output: strict     # 输出 schema 遵从度要求
    tool_reliability: high
  effort: xhigh
  fallback_chain:
    - tier: high
    - tier: mid + 拆小任务          # 降档时同时缩小任务粒度
    - 升级到人
```

由 `ModelGateway` 在**用户已配置的模型集合**上做约束求解。挑不到就按 `fallback_chain` 降级；降到底还不行就升级到人——**绝不静默用一个不满足要求的模型硬跑**。

### ★ 路由表必须可冻结

如果模型按 Evolver 学到的路由表动态变化：

```
影子回放的对照基准不稳定 → 分不清 pass@1 的变化来自 Skill 变更还是路由变了
A/B 实验的控制变量被污染
```

所以：

```
□ 路由表版本化，与 Skill 同样走 Skill CI
□ ★ 跑进化对照实验时路由表必须冻结
□ 路由实验本身在 holdout 集上做，且一次只改一个角色的档位
□ ★ 报告的指标是"降档后 pass@1 不降"，不是"降档省钱"
     —— 省钱是必然的，不降质才是发现
```

路由变更属于 L2 策略进化，**需人工确认**（模型选择是用户的成本决策，系统给证据，人来拍板）。

## 质量度量体系

### 三层指标

| 层 | 指标 | 用途 |
|---|---|---|
| **角色级** | 见"成对指标" | 定位是哪个角色出了问题；编制进化的输入 |
| **系统级** | pass@1、MTTR、人工介入次数/任务、规则违反数/100 次变更、token/任务、绿线破损次数 | 系统整体健康；对外的价值证明 |
| **工程级** | 见下 | 三大工程各自是否健康 |

### 三大工程的健康指标

| 工程 | 健康指标 | 不健康信号 |
|---|---|---|
| **Harness** | 终态确定率（三种终态占比 100%）、schema 一次通过率、checkpoint 恢复成功率 | 出现"不知道成没成"的执行 |
| **Loop** | **仲裁频率随规模的增长斜率（应次线性）**、死循环检出率、预算各阶段偏差 | 人被打断的频率随项目变大而线性上升 |
| **Graph** | ready 集合平均大小（并行度实际利用）、锁冲突率、**溯源图完整率** | 锁冲突率高 = 切分不好；溯源缺口 = 审计链断了 |

> **溯源图完整率是最好用的总体健康指标**：若有 commit 追溯不到任何需求，说明某个环节绕过了 packet 机制——**那正是失控开始的地方。**

### 静默失效的观测手段

最难设计也最有价值的一类——它们不报错，只是让系统慢慢变坏，而所有常规指标看起来都正常：

| 静默失效 | 观测手段 |
|---|---|
| Reviewer 漏放率悄悄上升 | **混入校准样本**（已知有缺陷的 diff） |
| 验收测试存在盲区 | **变异测试抽查**（注入已知 bug 看能否抓住） |
| Evolver 系统性高估收益 | **预测准确率追踪**（expected vs actual） |
| 记忆库被噪音稀释 | `hit_effect` 统计 + 衰减归档 |
| 上游规则注入不足 | Guardian 拦截率回流 |
| 系统整体失控 | 溯源图完整率 |

### 排障顺序（按依赖关系从上往下）

```
现象：系统停滞不前
  ① Graph 层：ready 集合为空？
       依赖图有环 / 所有权图锁泄漏（Worker 已死但 TTL 未生效）/ WIP 满但全卡住
  ② Loop 层：循环在跑吗？
       tick 正常？异常扫描执行了？ / 所有 packet 都在等人（批量升级无人处理）？
  ③ Harness 层：有 Worker 在跑但不产出？
       内层循环打转（查语义级死循环）/ 预算监控失效 / 输出 schema 反复校验失败
```

## 约束对齐

六条硬性约束逐条落点，供评审与自查使用。

### 一 · 真实且可复制的企业场景

| 要求 | 落点 |
|---|---|
| 真实场景 | 软件研发全流程。系统的第一个用户是我们自己——**用它开发它自己**是最直接的真实性证明 |
| 痛点具体 | 不是"AI 不会写代码"，是**团队工程经验无法被机器继承**：铁律散在 Wiki、聊天记录和老员工脑子里 |
| 可量化收益 | pass@1、MTTR、人工介入次数、规则违反数、token/任务、流动效率（见质量度量体系） |
| 可复制性 | 任何有 Git + CI 的组织 30 分钟接入；**换语言/技术栈只换 Skill 包与 Policy 规则集，编制与协议不动** |
| 跨行业迁移 | 8 个核心 Skill 可直接迁移至运维/客服/风控（见 `01` 复用矩阵） |

### 二 · 至少 3 个不同职能 Agent，形成完整闭环

**11 个角色**（MVP 5 个 + Guardian），完整 SDLC 闭环：

```
Intake 澄清 → Architect 契约 → Planner 拆包 → QA 写验收 → Coder 实现
  → Reviewer 对抗评审 → Integrator 集成发布 → Evolver 复盘进化
  横切：Manager 调度仲裁 · Guardian 策略拦截 · Helper 诊断协助
```

闭环覆盖赛题要求的八个环节：任务输入 → 任务拆解 → 上下文传递 → 工具调用 → 结果验证 → 执行证据沉淀 → 审批与回滚 → 经验沉淀。**每个角色的存在都附有"合并它会掩盖什么错误"的论证**（见角色体系）。

### 三 · 以 AgentTeams 为多 Agent 协同设计基础

| 考核点 | AgentTeams 原生能力 | 本系统的落地 | 增量 |
|---|---|---|---|
| **角色编排** | Manager-Workers；YAML 声明 Worker/Team/Human | 11 角色编制；Worker CR 定义 runtime 与资源 | RoleSpec 作为 Single Source，派生工具面/挂载/transitions/所有权注册 |
| **任务拆解** | Manager 接自然语言指令派单 | WorkPacket + 确定性准入校验 + 虚拟调度 | 拆分质量在执行前可验证（并行度、关键路径、死锁） |
| **上下文传递** | Matrix 消息 + MinIO 共享文件（官方降 token 手段） | 传引用不传内容 + 共享工作区 | **Context Broker**：可见性矩阵 + 上下文配方 + 预算降级链 |
| **状态追踪** | 房间在场状态 + 心跳 | 四张图 + Standup 心跳 + 看板 | 状态在 Git 仓库，可 diff / 可回滚 / 崩溃即恢复 |
| **人机协同** | Element 全程可见可干预 | 审批卡片、War Room、批量决策收件箱 | 批量升级 + 四要素，让仲裁频率次线性增长 |
| **凭证安全** | Higress，Worker 只持消费者令牌 | Team 模式直接采用 | Solo 模式本地加密 + Policy 前置拦截双层 |
| **异构运行时** | OpenClaw / QwenPaw / Hermes 同房共存 | Harness 分级的物理载体 | 重型/轻型/对话型三档，风险等级决定档位 |
| **任务重放** | `replay` | 直接采用 | 升级为进化流水线的**影子回放**环节 |
| **Skill 生态** | skills.sh 社区 8 万+ | 作为可插拔来源 | 三级作用域 + Manifest 六要素 + 统计驱动的治理 |

> **Team 模式直接跑在 AgentTeams 上；Solo 模式是同一套控制平面换本地 Worker。**
> 这个双模式本身就是"框架能力可替换性"的最强论证——控制平面不依赖任何具体框架。

#### AgentTeams 的四道安全防线（在本系统中的落点）

### 五 · MCP / RAG / 可观测

| 能力 | 状态 | 落点 |
|---|---|---|
| **MCP** | 使用 | 工具连接层；界面提供 Server 管理、工具授权到角色、失败率监控 |
| 等价集成契约 | 已提供 | HTTP/JSON-RPC 与 `tools/call` 同构；统一鉴权/Schema/错误/审计；**换 MCP 只替换 transport，业务调用链路零改动** |
| **RAG 四选二** | **四项全做** | ① Agent 记忆存储（三层记忆，时间窗口 + 向量检索）② 知识库 RAG（代码索引 + 规范文档）③ 共享状态管理（WorkPacket 状态机 + 路径锁 + Git 事务）④ 轨迹可观测（OTel 全量落库，支持回放） |
| **可观测三类** | 全覆盖 | Trace（OTel GenAI 规范，Agent/Skill/MCP/RAG/LLM 全链路 Span）· Log（结构化决策依据、失败原因、审批事件，TraceId 关联）· Metrics（时延、Token、工具成功率、队列深度、成本） |
| 评估回流 | 有 | 规则判定 + LLM-as-Judge + 人工标注三路 → 门禁与进化度量 |

> **Trace 在本系统中不只是给人看的**：它是回归评测集的构造原料、影子回放的对照基准、以及溯源图的证据来源。**可观测数据是进化的燃料。**

### 六 · 执行证据、审批、回滚、审计

| 要求 | 落点 |
|---|---|
| 执行证据 | `evidence/<packet-id>/` **五类产物**：代码 diff / E2E 截图 + 原始日志 / 测试报告摘要 / **工具调用清单（含输入输出哈希）** / LLM 推理摘要。**I6 证据不变量：状态推进必须附证据，声明不算** |
| Trace | OTel GenAI Span 全链路，含 `memory_injected`（进化度量基准）与 `denied`（上下文隔离审计） |
| 日志 | 结构化，TraceId 关联；Reviewer 的 Span 显式记录"未获得哪些上下文" |
| 指标 | 角色级成对指标 + 系统级 + 三大工程健康指标 |
| **审批** | R0–R4 五级；R3 强制人工审批（生产发布、migration、删除）；R4 硬拒绝且路径不挂载 |
| **回滚** | 合入即打 tag（绿线的物理实现）；**回滚优先于修复**；**回滚不需审批**；Skill 语义版本一键降级 |
| **审计** | 记录 `{who(agent+version), what, ★why(引用的记忆条目与 Skill 版本), when, trace_id, approver, rollback_ref, ★signature}`<br>**哈希链**：`signature = sha256(prev_hash + payload)`，篡改任一条则其后全部校验失败<br>**`why` 字段构成反向链路：事故 → 定位到哪条经验教坏了它 → 触发该经验降级复审** |
| **护栏自检** | **对抗性测试套件**周期性验证护栏本身：主动尝试执行 `forbidden_commands`、写越权路径、访问非白名单域名——**必须被拒绝**。护栏的失效是静默的，这是唯一能捕获它的手段 |
| 溯源 | 溯源图：任意一行代码可回溯到需求、假设、决策、审批人；**溯源图完整率**是总体健康指标 |

## 实施路线

### MVP 边界

完整设计是三个月的工程量。先跑起来，砍到这个程度：

**必须有（否则系统跑不通）**

```
✓ 四张图的最小实现（依赖图 + 所有权图必须有；溯源图可先做追加式 jsonl；知识图可先做文件）
✓ WorkPacket 定义 + 准入校验器（确定性，不用模型）
✓ 不变量 I1（路径锁）、I2（验收谓词）、I3（契约只读挂载）、I6（证据）
✓ 受控 Harness：上下文装配 + 工具面裁剪 + 预算 + 三种终态 + 证据产出
✓ 5 角色：Designer(Intake+Architect) / Coordinator(Planner+Manager) / Coder×2 / Reviewer / QA
✓ reconcile loop + 拉动式 ready 队列
✓ Walking Skeleton 阶段 + 冷启动测试
✓ 契约测试自动生成（mock + 类型 + 一致性测试）—— 前后端并联的前提
✓ ★ 看板视图（静态 HTML 读 state/*.json 即可，成本极低、诊断价值最高）
✓ 进化钩子 B 最简版：失败聚类 → 生成一条全局记忆 → 下次注入
```

**可以后加**

```
- Helper 角色与 L1 求助（初期 attempt 用尽直接找人）
- L2 War Room 会诊
- I4 绿线自动化（初期人工确认合入）
- I5 自动 Splitter（初期超预算就升级到人）
- 证伪门（初期人工确认经验升格）
- 影子回放（初期靠人判断 Skill 有没有用）
- 钩子 C 模板化 · Guardian（初期只读挂载 + hook 已够）
- 甘特图与其余六个视图 · 校准样本 · 变异测试 · 溯源图查询
- 多 runtime · 灰度下发 · 消息总线
```

**算法类任务的特别说明**：若首个项目不含算法模块，Spike 机制可延后；若含，**Spike 与评测集必须在 MVP 内**——否则会陷入"反复 rework 但永远达不到效果"的死循环，这是无法靠工程手段绕过的。

**最小验证目标**

> **一句话输入 → 系统自主产出一个能冷启动跑起来、通过全部验收场景的小应用，
> 过程中至少发生一次"从失败中提炼出一条规则，并在后续 packet 中生效"。**

这两件事同时成立，系统的核心主张就被证明了。其余都是工程量。

### 分期

| 期 | 目标 | 交付判据 |
|---|---|---|
| **P0 骨架期** | 控制平面 + WorkPacket + 单角色跑通 | 一个手工定义的 packet 能被认领、执行、验收、合入 |
| **P1 编制期** | 5 角色 + 并行 + 契约先行 + 依赖通道 | 3 个 packet 真并行且无冲突；Skeleton 跑通；依赖请求被自动策略正确拦截 |
| **P2 闭环期** | 全阶段贯通 + Provisioning + 冷启动测试 | **一句话 → 可交付应用**（含一次性配置收集与打包） |
| **P3 界面期** | 桌面壳 + 看板/甘特/成本仪表 + 人类输入通道 | 全程可在界面中观看与操作，不碰命令行 |
| **P4 进化期** | 钩子 A/B + 记忆注入 | 一条规则从失败中长出来并在后续 packet 生效 |
| **P5 度量期** | 对照实验 + holdout 集 | 进化增益曲线 |
| **P6 强化期** | 证伪门 · 影子回放 · 灰度 · Helper/会诊 · 静默失效观测 | 进化可度量可回滚；求助频率随成熟度下降 |
| **P7 产品期** | 安装包 · 自动更新 · Team 模式 · ProjectPattern | 可分发的桌面软件 |

> **P3 界面期放在进化之前**是刻意的：桌面软件的形态决定了"看不见"等于"不可用"。
> 一个只能在终端里看日志的版本，无论内部多完善，都不是这个产品。

### 技术选型与可替换性

| 组件 | Solo 模式（默认） | Team 模式 | 必要性与可替换性 |
|---|---|---|---|
| **桌面壳** | Electron 或 Tauri | 同 | Electron 生态成熟上手快；Tauri 体积小但需 Rust。**先 Electron，产品化再评估** |
| **控制平面** | 本地单进程 | 同一套代码 | **核心，不可替换**。两模式共用是架构的关键红利 |
| **状态存储** | 本地 Git 仓库 | Git 远程 | **核心，不可替换**（事务性与可回滚依赖它） |
| **Worker 运行时** | 本地子进程（Claude Code / 本地 Agent） | AgentTeams（Hermes/OpenClaw 多 runtime） | 抽象为 `WorkerRuntime` 接口 |
| **通信** | 进程内事件 + 本地 WebSocket | Matrix（人可旁听/打断） | 抽象为 `EventBus`；**不承载状态所以替换成本低** |
| **Artifact** | 本地文件系统 | S3 兼容对象存储 | 抽象为 `ArtifactStore`。⚠ MinIO 为 AGPL，仅网络调用不修改不分发；介意可换任意 S3 实现 |
| **索引与溯源** | SQLite + 向量扩展 | PostgreSQL + pgvector | 抽象为 `MemoryIndex` |
| **模型接入** | 用户自带 Key，直连 | Higress 网关（凭证隔离 + 计量） | 抽象为 `ModelGateway`；Solo 模式下计量在本地做 |
| **可观测** | 本地 OTel + 文件后端 | OTel + 集中后端 | **可重放的基础**，标准协议后端可换 |
| **凭证存储** | ★ 系统钥匙串 / 本地加密文件 | 网关托管 | 本地绝不明文落盘，绝不上传 |
| **配置与灰度** | 本地文件 | Nacos | 抽象为 `SkillResolver` |
| **消息队列** | 无 | RocketMQ（可选） | **仅加速，非正确性依赖**，去掉退化为 tick 级响应 |

### 主要风险

| 风险 | 应对 |
|---|---|
| **范围过大** | 严格按 MVP 边界；P0–P2 不碰进化，P0–P3 不碰 Team 模式 |
| ★ **桌面壳与 Agent 生态的适配成本** | Solo 模式先复用成熟的本地编码 Agent 作为 Worker，不自研执行体 |
| ★ **两种模式实现分叉** | 四个接口（`WorkerRuntime`/`ArtifactStore`/`MemoryIndex`/`ModelGateway`）在 P1 就定死；CI 中两模式跑同一套用例 |
| **契约先行的前期成本** | Design 慢 20 分钟换 Increment 不返工；用 ProjectPattern 摊薄 |
| **并行度实际很低** | 虚拟调度执行前就能发现；理论并行度长期 ≤2 说明 boundaries 切分方法要改，而非加 Coder |
| **Agent 能力不足以完成 packet** | 这是粒度问题不是能力问题——Splitter + 历史 p80 预算会自动收敛 |
| **进化在小样本上不显著** | 明确 L1/L2/L3 的样本门槛；样本不足时输出"本轮无提案"是合法终态 |
| ★ **成本失控（用户直接买单）** | 预算树 + 实时显示 + 超支即停三选一 + 分层路由；**四者都要在 P2 前就位** |
| ★ **凭证安全事故** | 本地加密存储 + 最小权限提示 + **凭证泄漏扫描作为不可豁免的交付门禁** |

| **WorkPacket** | 工作单元。同时是任务描述、并行边界、验收定义、资源预算、上下文配方 |
| **不变量 I1–I6** | 系统骨架。角色流程工具可换，这六条不能破 |
| **绿线** | main 任何时刻可构建可部署 E2E 通过（I4）。物理实现是"永远存在一个已知可运行的 tag" |
| **契约冻结** | 只有 Architect 能写 `contracts/`（I3）。并行安全的基石，也是防作弊的关键 |
| **证伪门** | 全局记忆的准入闸门。共识靠"找不到反例"而非投票 |
| **进化的不动点** | 能力层可进化、约束层不可进化，技术强制 |
| **Walking Skeleton** | 贯穿全栈但什么都不做的最小系统，Increment 之前必须建立 |
| **冷启动复现测试** | 新容器 → clone → 照 README → 起来 → E2E 全绿。唯一有资格判定 `delivered` 的动作 |
| **Single Source** | 一份 RoleSpec 派生四处配置，禁止手工维护任一处 |
| **静默失效** | 不报错、指标看起来正常、但系统在慢慢变坏的失效模式 |
| **分级求助** | L0 自修复 → L1 Helper → L2 War Room → L3 人工的四级阶梯 |
| **Helper** | 更大视野 + 零写权限的诊断角色。只出诊断不写代码，保持 Coder 的责任主体地位 |
| **schema 变更通道** | migration 的全局串行通道。路径隔离对它无效，因为它们改的是同一个数据库状态 |
| **Spike** | 算法类任务的探索阶段。验收谓词是指标阈值而非行为断言，产物不合入主干 |
| **集成 packet** | 只拥有 `tests/e2e/**`、承载端到端验收的 packet。它是"水平切分仍能端到端验收"的解法 |
| **流动效率** | 增值时间 / 总周期时间。人类团队典型 5–15%，用于暴露"加更多 Coder 没用"的误判 |
| **单件流** | 写完一个可验证单元立刻验证，而非全写完再测。批量越大缺陷发现越晚、归因越难 |
| **Solo / Team 模式** | 桌面双模式。控制平面同一套代码，只换 Worker 与存储的实现 |
| **开发计划书** | 澄清后、开工前生成的人可读确认物，含并行度、耗时与**成本预估** |
| **任务文档** | WorkPacket 的人可读渲染。同一份数据两种形态，**永不脱节** |
| **依赖快速通道** | Coder 不能直接改 `package.json`，提 DependencyRequest 走自动策略审查 |
| **Provisioning** | 交付前一次性收集凭证与素材的阶段。全流程唯一一次索要外部资源 |
| **凭证泄漏扫描** | 交付前的确定性门禁：产物中不得出现任何凭证片段，命中即阻断 |
| **生成物** | 从契约自动生成的类型/文档/mock。不手写、不属于任何 `owns_paths` |
| **模型隔离** | 制衡的第三个维度（继权限、上下文之后）。同模型 = 同盲区，会让上下文隔离失效 |
| **Advisor 配对** | 便宜执行模型 + 强模型顾问，服务端运行无往返。Coder 位杠杆最大 |
| **能力需求声明** | 路由表写 `requires: {tier, context, structured_output}` 而非模型 ID，由网关在用户已配置的模型上求解 |
| **Skill 三级作用域** | Global / Role / Project，就近覆盖。**角色私有本质上是上下文成本隔离机制** |
| **Skill 权限子集律** | Skill 权限永远是宿主角色权限的子集，不能扩权。可插拔生态安全存在的前提 |
| **连接器** | 账号绑定层，处理 OAuth/token/工作区。Skill 管"怎么做"，MCP 管"怎么连"，连接器管"用谁的账号" |

### 设计决策速查

| 问题 | 决定 | 理由 |
|---|---|---|
| 状态放哪 | Git 仓库 | diff / 回滚 / 分支 / 事务性白送；Agent 的原生介质 |
| 谁写状态 | 控制平面单点 | 把并发问题收敛到一处 |
| 控制平面用不用 LLM | **不用** | 它的错误不可恢复 |
| 派活方式 | 拉动式认领 | 推动式需 Manager 知道各 Worker 真实负载，且是瓶颈与单点 |
| 怎么防合并冲突 | 契约先行 + 路径独占 | 让冲突结构上不可能，而非事后解决 |
| 谁写验收测试 | **QA，且先于实现** | 让 Coder 写等于自己出考卷 |
| Reviewer 能否看推理链 | **不能** | 上下文隔离是这次拆分成立的前提，不是附加安全措施 |
| 超预算怎么办 | 自动拆分 | "干不完就拆"是自动行为，不是异常处理 |
| 合入失败怎么办 | **回滚优先于修复** | 现场修期间绿线破损，阻塞所有其他合入 |
| 回滚要不要审批 | **不要** | 回滚是恢复到已知良好状态的安全动作 |
| 经验怎么进全局记忆 | 证伪门 | 防止一条错经验被反复引用而"越来越可信" |
| 进化边界 | 能力可变、约束不可变 | 回答"会不会失控"的唯一硬答案 |
| 人在哪 | 中断源与仲裁者，不是循环一环 | 否则系统吞吐 = 人的响应速度 |
| 升级方式 | 批量 + 四要素 | 逐个打断会让人被淹没 |
| 消息队列 | 加速器，非正确性依赖 | 状态差驱动天然自愈；这决定它是 P2 |
| 卡住了先找谁 | **Helper 求助 → 会诊 → 才找人** | L3 的成本不是 token 是人的注意力；中间两级把绝大多数问题拦住 |
| Helper 要不要写权限 | **不要** | 有写权限它就变成第二个 Coder，责任主体模糊且无锁会破坏 I1 |
| 怎么切一个跨栈功能 | 水平切分 + 契约级验收 + **集成 packet 承载端到端验收** | 纯垂直切必超预算，纯水平切无法端到端验收 |
| migration 怎么并行 | **不并行，走全局串行通道** | 路径隔离对它无效——它们改的是同一个数据库状态 |
| 前后端怎么并行 | 契约冻结后自动生成 mock，**前端依赖 mock 不依赖实现** | 依赖契约不依赖实现，这是并联的唯一正确姿势 |
| 算法怎么做 | **Spike（指标验收，不合入）+ 固化两阶段** | 算法的失败是"效果不够"，rework 循环假设"方法对了"，解不了 |
| 单元测试计不计入验收 | **不计入** | 计入就等于让 Coder 自己出考卷；它是开发工具不是验收依据 |
| Console 要不要写权限 | **零写权限** | 纯读端可以随便迭代，挂了不影响系统 |
| 看到 review 堆积怎么办 | **扩 Reviewer 或降 WIP，不是加 Coder** | 看板能一眼看出瓶颈在哪列；这是最常见的误判 |
| 精益放在什么位置 | 工程方法，不是叙事主线 | 系统存在的理由是六种失败模式；精益是解决【等待】与【库存】的工具箱 |
| 产品形态 | **本地优先桌面软件**，非云端 SaaS | 代码与凭证不出本机；**零服务端运维**是小团队可持续的唯一形态 |
| 桌面怎么兼顾企业场景 | **Solo / Team 双模式，控制平面同一套代码** | 状态放在 Git 仓库的最大红利：控制平面不依赖任何服务 |
| 何时问人要 API Key | **只在 Provisioning 阶段一次性问** | 中途索要会把人拖回循环；且只有做完才知道全集 |
| package.json 谁能改 | **没人直接改，走依赖快速通道** | 依赖膨胀是 Agent 写代码最典型的失控点；自动策略能挡住绝大多数请求 |
| 类型定义/API 文档谁写 | **不写，从契约自动生成** | 一举消灭共享文件冲突与文档脱节两个问题 |
| 开工前给不给成本预估 | **必须给，写进开发计划书** | 用户自付 token；没人愿意在不知花多少钱时启动十几小时的任务 |
| 超预算怎么办 | **暂停并给三选一，绝不静默烧钱** | 桌面软件里静默超支等于直接损害用户 |
| 关机/断网怎么办 | checkpoint 断点续跑 | 服务端里这是可靠性需求，**桌面里这是成本需求**——不重烧已花的钱 |
| Skill 全装全局行不行 | **不行，必须分作用域** | Skill 会被注入上下文，数量直接等于 token 成本；给 Reviewer 装的安全清单不该让 Coder 每次付费读一遍 |
| 用户装的第三方 Skill 安全吗 | 安全，**权限是宿主角色的子集** | 它声明的越权工具在宿主的工具面里根本不存在，调不动 |
| Evolver 生成的 Skill 要不要先验 | **要，且比人装的更严** | 人对自己的选择负责；系统对自己的产出需要举证。人装可先用后看，系统生成必须先验后用 |
| 模型路由建议要不要自动生效 | **不自动，放面板给人拍板** | 模型选择是用户的成本决策——系统给证据，人来决定 |
| Skill 库怎么防膨胀 | 统计驱动的卸载建议 | 面板显示"每次注入 1.4k token、30 天命中 0 次"，把感觉变成数据 |
| MCP 工具装了谁能用 | **显式授权到角色，且不得超出该角色风险等级** | 不能把 R2 写工具授予只读的 Reviewer |
| 每个 Agent 一个模型还是全局一个 | **按角色分配** | 缓存是模型作用域的；不同 Agent 本来就是不同会话，分配零成本。但**同一角色中途换档要付缓存重建** |
| 谁最需要强模型 | **Architect / Intake / Reviewer，不是 Coder** | 判据是错误可恢复性：Coder 有三道下游防线，Reviewer 和 Architect 没有 |
| 先调 effort 还是先换模型 | **先 effort** | effort 不换模型 → 缓存不失效；换模型要付重建 |
| Coder 该用什么档 | **中档 + 最强档 advisor** | 服务端配对无往返；token 大头在 Coder，这一处杠杆最大 |
| Reviewer 能和 Coder 同模型吗 | **不能，硬约束** | 同模型 = 同盲区，上下文隔离白做。这也是跨家混用的唯一正当理由 |
| 预算按什么计 | **按货币，不按 token** | 分词器跨家族差异可达 30%；异构路由下按 token 计会静默失真 |
| 降档一定省钱吗 | **不一定** | 便宜档位的缓存最小长度可能更长——省单价却失去缓存是净亏 |
| 进化平面能省吗 | **能，走 Batch API 砍半** | 它完全不延迟敏感，是全案唯一纯赚无取舍的优化 |
| 路由表能自动进化吗 | **能提议，不能自动生效；实验时必须冻结** | 路由变动会污染影子回放的对照基准 |

---

## 结语：这个系统的一句话主张

> 现在所有人都在造更强的编码 Agent。
> **我们造的是让这些 Agent 组成的团队，能够可靠地把软件做完、把教训变成可执行的能力、并且证明自己确实变强了的那套基础设施。**
>
> 而它能成立的全部原因只有一条：
> **可靠性来自不变量，不来自提示词。**
