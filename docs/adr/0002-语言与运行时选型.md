## 决策

**全 TypeScript。** Node 运行时，`strict` 模式，pnpm workspace 单仓。

```
desktop        TypeScript + React + Electron
control-plane  TypeScript (Node)
harness        TypeScript (Node)
delivery       TypeScript (Node)
roles          TypeScript + JSON/YAML 定义
contracts      JSON Schema（真源） → 生成 TypeScript 类型
```

**Python 不作为主干语言。** 确需 Python 生态时，走**「脚本型 Skill」**这一个受控口子：子进程调用，接口在 Skill 契约里定义。**只开这一个口子，不允许在别处引入跨语言边界。**

---

## 理由

### 一、契约不跨语言，就不会漂移

跨语言方案要维护两套类型定义，靠代码生成同步。这套生成工具本身就是要维护的工程，而且**漂移时不报错**——它只是悄悄不一致。

契约冻结（I3）是全案最核心的不变量之一。不该在自己的地基上开这道缝。

### 二、打包复杂度落在经验最薄的成员身上

打包是 C 的活。Electron 已经够烦，再塞一个 Python sidecar 进去，难度是翻倍不是加一点。

### 三、★ 静态类型 = 白送的确定性验证器

这条是决定性的。

系统里所有代码都是 Agent 写的，而全案的立论是**"判定必须机器可做，不能靠模型自觉"**。

`tsc --noEmit` 就是一个**零成本、确定性、一秒出结果**的验收谓词。Agent 写完，编译器先判——类型对不上直接打回，不用等测试、不用等 Reviewer、不花模型钱。它天然属于「收敛阶段【无模型】」的那一段。

Python 没有这个。mypy 是可选的、能绕过的、覆盖不全的——**而"能绕过的约束等于没有约束"是我们自己写在设计里的话。**

### 四、Agent 生态的差距没有想象中大

已定「Solo 模式复用成熟编码 Agent，不自研执行体」——我们是**调**它不是重写它。Anthropic 官方 SDK 两边都有，调 API 这件事 TypeScript 不吃亏。

---

## 否决的方案

| 方案 | 否决理由 |
|---|---|
| **Python 后端 + TS 前端** | 见理由一、二、三。跨语言边界是契约漂移的高发区 |
| **Go 后端 + TS 前端** | 并发优势在这个量级用不上；团队无人熟悉；仍是跨语言 |
| **Rust 后端 + TS 前端** | 时间会全烧在编译器上；15 天到初赛截止，不能赌 |

---

## 后果

**正面**

- 三人一种语言，互相能帮上忙（对 C 尤其重要）
- 契约类型三端复用，无双份定义
- `tsc --noEmit` 成为免费的确定性门禁
- 单一 workspace，一次 `pnpm install` 全装

**代价**

- CPU 密集任务（大图遍历、前缀树）不如原生快
  → 现阶段不构成瓶颈。真到了那天，把单个热点模块换成原生扩展，不影响其余
- 个别场景要走「脚本型 Skill」绕一下 Python

**风险**

- ⚠️ 「脚本型 Skill」这个口子可能被滥用成第二条主干。
  缓解：Skill 契约里显式限定它只能是**无状态、纯函数式**的调用，不许长驻进程、不许持有状态

## 已落地的配套决定

| 项 | 取值 | 为什么 |
|---|---|---|
| 包管理 | **pnpm** workspace | 单仓多包的标准解，硬链接省磁盘 |
| 模块 | **ESM**（`"type": "module"`，`NodeNext`） | Node 的方向；Electron 已支持 |
| target | **ES2022** | Node 20+ 全支持 |
| `strict` | **true**，且开 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` | ★ 这三个开关才是"免费验证器"的真正来源。关掉任何一个，理由三就打折 |
| 类型来源 | **JSON Schema → 生成 TS** | schema 是真源。手写两份必漂移 |
