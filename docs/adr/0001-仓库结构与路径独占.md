# ADR-0001：仓库结构与路径独占

- **日期**：2026-08-02
- **状态**：已接受
- **决策人**：A（队长）

---

## 背景

三人 + Agent 协同开发。如果各写各的然后集成，会撞上合并地狱——而这套系统存在的理由就是消灭那个地狱。

## 决策

**用系统自己的设计来组织仓库。**

### 一、按 package 切分，每个 package 单一 owner

```
packages/contracts/      A    ★ 契约冻结
packages/control-plane/  A
packages/harness/        B
packages/roles/          B
packages/delivery/       C
packages/desktop/        C
```

**没有任何路径有两个 owner** → 合并冲突在结构上不可能，而不是靠沟通协调避免。所有权表记在 `boundaries.yaml`，与系统内部的同名文件同构。

### 二、分工依据是爆炸半径，不是难度

| owner | 爆炸半径 | 理由 |
|---|---|---|
| A | 最大 | 锁判错即数据损坏，不可恢复 |
| B | 中 | 执行错可被打回重试 |
| C | **最小** | Console 对系统状态零写权限，挂掉系统照常跑 |

C 拿桌面端**不是因为它简单，是因为它零写权限** —— 犯错不会传播。这是架构属性，不是照顾。

### 三、`fixtures/golden-state/` 是 C 的解耦点

有了状态快照，C 第一天就能开工，不用等控制平面跑起来。

这是系统里"前端依赖 mock 不依赖实现"的同一招——**前后端并联的原则同样适用于人**。没有它，C 会空等两周然后在最后一周被压着赶工，这是三人团队最常见的死法。

### 四、`tests/contract/` 从 schema 自动生成，任何人不手写

对应系统设计里"生成物不进任何 `owns_paths`"。手写会与契约脱节。

## 否决的方案

| 方案 | 否决理由 |
|---|---|
| **按技术栈分层**（前端/后端/算法各一人） | 层与层之间接口最多、耦合最紧，三个人会天天互相等 |
| **按功能模块分**（每人负责几个 Agent 角色） | 角色实现共享 Harness 和 contracts，路径必然交叉 |
| **不分工，都在 main 上写** | 三个人的 Agent 同时改一个工作区，必然互相覆盖 |
| **docs 复制一份到仓库** | 两份会分叉。文档跟着代码走，同一个 commit 里改 |

## 后果

**正面**

- 合并冲突结构上不可能
- 三人可并行，且 C 从第一天起不被阻塞
- 每个 package 的 README 就是 Agent 读到的约束上下文

**代价**

- 第 0 周必须"只定契约不写代码"，看起来慢
- 契约变更要走串行窗口，比各改各的慢
- **这两个代价是刻意付的**：换 Increment 阶段不返工

**风险**

- ⚠️ 如果 A 成为"谁都在等他"的瓶颈，说明契约没冻死或规则没沉淀。缓解：契约第 0 周冻结；同一类问题被裁决 3 次以上就写成规则
