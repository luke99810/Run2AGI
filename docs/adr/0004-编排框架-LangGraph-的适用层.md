# ADR-0004：编排框架 —— LangGraph 用在执行平面，不用在控制平面

- **日期**：2026-08-03
- **状态**：✅ 已接受
- **决策人**：A（队长）
- **相关**：[ADR-0003](0003-改为-Python-核心引擎.md)（Python 核心引擎）

---

## 背景：一处需要澄清的概念重叠

设计文档里有「**Graph 工程**」，LangGraph 也叫 Graph。**这两个 Graph 不是同一个东西**，混在一起会导致架构层次错位。

| | 是什么 | 例子 |
|---|---|---|
| **本设计的「四张图」** | **数据结构** —— 描述系统状态的拓扑 | 依赖图（哪个 packet 依赖哪个）、所有权图（哪条路径被谁锁着）、溯源图、知识图 |
| **LangGraph 的 Graph** | **控制流图** —— 描述一次执行的步骤走向 | 节点是函数，边是转移，state 是共享字典 + checkpointer |

**依赖图不是可执行的图，它是一张"谁要等谁"的表。** 拿 LangGraph 去表达它是范畴错误。

但反过来，**一次 Coder 执行内部的 plan → edit → test → fix 循环，正是 LangGraph 擅长的控制流图**——这就是设计里的「Loop 工程」和「子 Agent 内部规划」。

---

## 决策

**按平面分层：LangGraph 用在执行平面，控制平面保持自研的确定性调和循环。**

```
┌─────────────────────────────────────────────────────────────┐
│ 控制平面  ❌ 不用 LangGraph                                  │
│                                                              │
│   调和循环（对标 K8s controller manager）· 路径锁 · 准入      │
│   校验 · 门禁 · 预算 · Guardian                              │
│                                                              │
│   状态 = .codentum/ 里的 Git 文件。★ 零 LLM。                │
└─────────────────────────────────────────────────────────────┘
                            ↓  WorkerRuntime.spawn()
┌─────────────────────────────────────────────────────────────┐
│ 执行平面  ✅ 用 LangGraph                                    │
│                                                              │
│   Harness 三段式：                                           │
│     准备【无模型】 → ★ LangGraph 图【有模型】 → 收敛【无模型】│
│                                                              │
│   每个角色一张图：RARE-V 循环 · 分级求助 · 子 Agent 内部规划  │
│   state = 本次执行的临时状态（LangGraph checkpointer）       │
└─────────────────────────────────────────────────────────────┘
```

### 为什么控制平面不用

1. **控制平面零 LLM。** LangGraph 的价值在于编排"带模型的步骤"；一个不含模型的调和循环用它只是徒增抽象。
2. **状态存 Git 文件。** LangGraph 的 checkpointer 想要自己的持久化（SQLite/Postgres）。让它管系统状态 = 直接和"Git 是唯一状态源"打架，而后者是 Solo/Team 双模式共用一套控制平面的前提。
3. **调和循环必须幂等且可崩溃恢复。** 这是几十行确定性代码就能保证的性质，交给框架反而更难论证。

### 为什么执行平面用

1. **Loop 工程本来就需要这些**：检查点与恢复、中断、流式、重试与回退、human-in-the-loop。自己写一遍是纯重复劳动。
2. **子 Agent 内部规划**天然是控制流图。
3. **分级求助（L0 → L0.5 → L1 → L2 → L3）** 就是带条件边的状态机。
4. LangGraph 以 Python 为主语言，与 ADR-0003 一致。

---

## ★ 必须守住的边界（这条最重要）

> **LangGraph 的 state 是【一次执行的临时状态】，永远不会成为系统状态。**

```
   LangGraph state  ──┐
   （临时，随执行销毁）│
                      ├─→ 只有 WorkerOutcome + Evidence 能跨回控制平面
   Harness 收敛阶段  ──┘     （★ 由无模型的确定性代码写出）
                      ↓
              .codentum/ 里的 Git 文件（系统状态）
```

**具体规则：**

| 规则 | 违反的后果 |
|---|---|
| LangGraph checkpointer 只存本次执行的中间态，**不存四张图** | 系统状态出现第二个真源，Git 不再权威 |
| 图的节点**不得直接写 `.codentum/`** | 绕过准入校验与审计链，六条不变量全部失效 |
| 图的出口只有一个：产出 `WorkerOutcome`（含 evidence 引用） | 状态推进失去证据（破坏 I6） |
| 准备阶段与收敛阶段**不在图里** | 三段式塌掉，约束不再"进模型前物理生效" |

**判据：把 LangGraph 整个换掉，控制平面应当一行都不用改。** 做不到，就说明边界已经漏了。

---

## 否决的方案

| 方案 | 否决理由 |
|---|---|
| **全系统用 LangGraph 编排** | 控制平面会被迫接受它的 state 模型，与 Git-as-state 冲突；且给零 LLM 的调和循环套上为 LLM 设计的抽象 |
| **完全不用框架，全部自研** | Loop 工程里的检查点/中断/重试是纯重复劳动。15 天窗口下，自研这部分是浪费 |
| **AutoGen / CrewAI** | 它们的抽象层次是"多个 Agent 对话协作"，而本设计的多 Agent 协同**由控制平面通过 WorkPacket 和路径锁完成**，不靠对话。用它们会出现两套编排互相打架 |

> 最后一条值得展开：**本设计里 Agent 之间不直接对话。**
> 协同发生在控制平面——通过 WorkPacket 的依赖、路径锁的独占、门禁的判定。
> 这是它与"多 Agent 对话框架"的根本分野，也是并行安全能被证明的原因。
> 所以需要的是**单 Agent 内部**的编排（LangGraph 擅长），不是 Agent 间的对话编排。

## 后果

**正面**

- Loop 工程的检查点/中断/重试/流式直接复用，省下可观工作量
- 与 Python 决策一致
- 控制平面保持自研 → 六条不变量的论证不受第三方框架实现细节影响

**代价**

- 多一个需要学习的框架（但团队 Python 熟，成本可控）
- 多一个依赖的版本风险

**风险**

- ⚠️ **最大风险是边界被慢慢侵蚀** —— 某次图节点里"顺手"直接写了 `.codentum/`，之后就回不去了。
  缓解：`packages/control-plane/` 与 `packages/harness/` 互不 import 的规则已在 `boundaries.yaml` 与
  各 package README 里写死；再加一条 CI 检查：**`harness/` 内不得出现对 `.codentum/` 的写操作**。
