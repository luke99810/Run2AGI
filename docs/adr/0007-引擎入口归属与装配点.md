## 一、背景：一个落在三个人边界之间的缺口

到 2026-08-10 为止，链路是这样的：

```
App.tsx:58 → IPC_CHANNELS.engineCommand → PythonEngineClient.ts
           → SidecarGateway → JsonlEngineProxy
                                    ↓
                          ★ 这里没有引擎 ★
                                    ↓
           ReconcileLoop（能跑真 worker，但只被测试调用过）
```

核实方式（任何人都可以重跑）：

```bash
grep -rln "codentum_delivery" --include=*.py . | grep -v packages/delivery
# → 无输出
```

也就是说，全仓库**没有任何非测试代码**引用 delivery。`engine_proxy` 唯一
对话过的「引擎」是 `packages/delivery/tests/_fake_engine.py`，而那个文件
自己的第一行就写着 `never shipped as an engine`。

这个缺口的特别之处在于**它不在任何人的欠账清单上**：

| 谁 | responsibility（原文） | 包含这个缺口吗 |
|---|---|:-:|
| A | 控制平面 + 契约 + 集成仲裁 + 不变量守护 | ✗ |
| B | Harness + 角色实现 + 进化层 | ✗ |
| C | 桌面端 + 交付链路 | ✗ |

08-10 上午的进度分析一度把它记成「C 的交互链路未通」。那是**责任方判定
错误** —— C 侧从 UI 到 Python 协议全部实现完毕。按那个归类走下去，C 会
一直等 A/B 补引擎，A/B 会一直以为 C 在接线，直到录屏那天才发现。

★ 这正是本项目一直在讲的那类问题的团队版本：**缺陷不在任何一个模块里，
在模块之间。** 我们用 `boundaries.yaml` 保证「任一路径只有一个 owner」，
但它保证不了「每一件必须做的事都有 owner」—— 路径可以全覆盖，责任仍然可以
有洞。

---

## 二、决定

1. 新增 `packages/engine/`，owner = **A**，作为**装配点**。
2. 它不引入新的判定逻辑。它只做两件事：
   - 决定**哪些组件被装进 `ReconcileLoop`**
   - 决定**哪些能力对外报为可用**
3. `boundaries.yaml` 相应增加一条 module。

### 为什么归 A

- 它同时要懂 `ReconcileLoop` 的生命周期（A 的模块）与 delivery 的握手/回执
  语义（C 的模块）。B 不熟控制平面，C 不写 Python 引擎侧。
- 它不引入新的跨包写权限：只读 `packages/contracts/**`，其余全是 import。
- 08-10 A 的欠账已清空，是三人中唯一有档期的。

### 为什么它是「装配点」而不是「第四层」

因为它**不做判定**。所有判定仍在原处：状态机、路径锁、门禁、预算、
Guardian 都在控制平面，工具面与模型调用都在 Harness。装配点只选默认值。

但这一层的存在本身是有意义的 —— 见下一节。

---

## 三、这一层为什么必须存在：默认值的选择权

`ReconcileLoop` 的四个安全组件（`transition_table` / `gate_runner` /
`budget_tracker` / `guardian`）**默认全是 `None`**。

对一个库，这是合理的默认（不强加策略）。对一个产品，这是关掉护栏。

08-10 的护栏消融实验量到的数字（`docs/experiments/`）：

| 护栏 | 关掉后被静默放行 | 打开后 |
|---|---|---|
| I1 路径锁 | 8 / 8 | 0 |
| I5 重试上限 | 8 / 8 | 0 |
| 全局预算 | 8 / 8 | 0 |
| 门禁（修复前） | 32 / 32 | 0 |

★ 关键在于：「护栏关」不是人造对照组，**那就是默认配置**。

在有装配点之前，「默认值由谁选」这个问题没有归属 —— 每个调用方各选一次，
测试选了一套，未来的产品入口会选另一套。装配点把这个选择收敛到一个地方，
并且让它可被一条测试盯住。

**这是本 ADR 真正的内容。** 新增一个包只是形式。

## 四、装配点做的三个具体选择（及其反面）

### 4.1 能力表按「按下去会不会真的发生事情」报

`_fake_engine.py` 把 9 个 capability 全报 `true`。真引擎照抄的后果是：
桌面端把「暂停」「从检查点分叉」显示为可用，点下去什么也不发生，
**而不会有任何东西报错**。

现在只有 `requirements` 报 true，其余八个 false。且当模型 Key 缺失时，
连 `requirements` 也报 false —— 因为没有 runner 的话 packet 建出来也不会
被执行，那是最难查的一种「成功」：命令被接受了，状态却永远不动。

这条同时满足 C 在任务书里立的规矩：**未接入的不得显示为已启用。**

### 4.2 `submit_requirement` 回 `accepted`，不回 `applied`

网关的默认请求超时是 8 秒，一个真实模型 packet 要跑 30～180 秒。
假引擎立刻回 `applied` 是因为它什么都没做。

真引擎回 `accepted`（协议里本来就有这个状态），把执行放到后台线程，
桌面端通过监视 `.codentum/` 看进展。

★ 回 `applied` 等于**在结果出来之前宣布结果**。

### 4.3 `stateRevision` 与 `runId` 落盘

假引擎的 `revision` 是进程内变量。真引擎照抄会坏在两处：

- 网关明确检查 `revision < 上一次` 并判 `non_monotonic_state_revision`
  （`gateway.py:219`），进程内计数器一重启就归零；
- runId 每次启动都变的话，桌面端拿着旧 runId 发命令会被判 `run_mismatch`，
  用户看到的现象是「重启之后什么都点不动」。

现在两者都写进 `.codentum/engine-session.json`：**同一个状态目录就是同一次
run，重启是恢复，不是新开一局。**

## 五、否决掉的选项，以及一处需要被反驳的地方

### 否决：把入口塞进 `packages/control-plane/`

控制平面会因此 import `codentum_delivery`，层次反转 —— 内核依赖外壳。
而且控制平面的承诺是「确定性代码，零 LLM，错误不可恢复」，
把进程管理和 stdio 循环放进去会稀释这个承诺。

### 否决：写成 `scripts/` 下的一个脚本

`scripts/**` 的定位是「零第三方依赖的工程脚本，`pip install` 之前就能跑」。
引擎要 import 五个包，不属于这一类。

### ⚠️ 需要被反驳的：先落地后确认

`boundaries.yaml` 抬头写着「改这个文件 = 改团队契约，需三人同意并记 ADR」。
本次是**先改了，再写 ADR，状态标为提议**。

这与 ADR-0006 记录的那次越权是同一形状 —— 那次是 `50bca30` 先改了 5 个
契约文件，ADR 是四天后补的。所以必须说清楚区别与代价：

- **区别**：这次没有触及冻结的 `packages/contracts/**`，只新增了一个
  此前无主的路径；ADR 与代码同时提交，不是事后追记；状态如实标为提议。
- **代价**：如果 B 或 C 不同意归属，要改的是 `boundaries.yaml` 那一条，
  不是代码 —— 代码放在哪个包名下不影响它的正确性。
- **仍然是越权**：距 8.16 只剩 6 天不是绕过流程的理由，只是选择先承担
  这个代价的理由。**这一段留在这里，是为了让否决它变得容易。**

### 由此暴露的流程缺陷（与 ADR-0006 同源）

`check_boundaries` 能查出「新目录没有 owner」（本次正是它先报的错），
但**查不出「boundaries.yaml 的变更有没有经过三人同意」**。

ADR-0006 已经提过一条同族推论：*I3 目前只校验「改 contracts 的人是不是 A」，
不校验「有没有引用 ADR 编号」*。

→ **合并成一条待落地的门禁**：`boundaries.yaml` 与 `packages/contracts/**`
的变更，其 commit message 必须引用一个 ADR 编号，否则拒绝。
这条能被脚本执行，且能同时堵住 0006 与 0007 这两次。

## 六、本 ADR 没有解决的

1. **没有 Planner。** 一个需求 → 一个 packet，不是分解。写死一套假拆分会
   让演示更好看，但那正是本项目一直在抓的东西。分解要等 Planner。
2. **没有 Intake。** 占位验收的署名按优先级退到一个存在的角色（当前是 `qa`），
   并在日志里留痕；B 补上 `intake` 的 RoleSpec 后会自动切回。
   由 `test_acceptance_author_prefers_intake_once_the_rolespec_exists` 钉住。
3. **`WorkPacket` 仍然没有任务描述字段。** 引擎把需求原文经 `context_loader`
   送进 `ContextBundle` —— 那是设计里本来就有的注入点，不是绕过。
   契约层的缺陷仍在，仍需单独走变更窗口（原待发起的 ADR-0007 编号已被本
   ADR 占用，**契约字段那条顺延为 ADR-0008**）。
4. **`transition_table` 默认仍是 `None`**，因为打开会让 coder 的 packet
   永远停在 review：`_try_review_to_accepted` 用 `role=packet.role` 查表，
   而 `review → accepted` 只有 reviewer 声明。表是对的，提问方式不对 ——
   这是控制平面的一处建模问题，不在装配层绕过。
   由 `packages/engine/tests/test_role_transition_gap.py` 的四条测试钉住，
   **修好之后其中一条会变红**，那就是把默认值改成 True 的信号。
5. **缺陷二（worker 自陈干不了仍被验收）没有被这次改动触及。** 仍由
   `tests/e2e/test_real_model_execution.py` 的 `xfail(strict=True)` 钉着。
