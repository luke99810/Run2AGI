# ADR-0010：验收第六层 —— 集成谓词的桩化检验

- **日期**：2026-08-14
- **状态**：✅ 已接受
- **相关**：[ADR-0008](0008-进化层-经验沉淀与判据因果检验.md)（判据的因果检验）

---

## 背景：`vacuity_check` 管不到的那一格

验收判据到目前为止是五层，每一层修的都是上一层漏掉的东西：

| 层 | 修的是 |
|---|---|
| 1 | 拿控制面自己的簿记当证据 |
| 2 | 门禁层同一个洞 |
| 3 | 说完成了但一个文件没改 |
| 4 | 改了文件，但没达到验收标准 |
| 5 | 达到了验收标准，**但验收标准是空的**（`vacuity_check`） |

第五层用的是因果检验：把实现移走，测试必须变红。它抓「测试是空的」很准。

**但它抓不到一个更隐蔽的东西：**

> 集成测试只是把各模块自己的测试又跑了一遍。

多 Agent 并行开发最经典的失败就是「各段都对、合起来不通」。
而集成判据恰恰是最容易造假的一个 —— 写它的人**没有动力让它变红**。
`pytest workspace -q` 跑一遍全部测试、退出码 0，看起来无懈可击；
但它完全没有检验模块之间的接口是不是对得上。

★ 各模块的测试全绿 + 集成谓词全绿 ≠ 集成成立。
  这中间的缺口，前五层一层都判不出来。

---

## 决策：第六层 —— 逐模块桩化

> **把模块 A 的实现掏空，集成谓词必须变红。对每个模块都如此。**
> 如果它照样通过 —— 集成测试根本没测到 A 的参与。

这是把因果检验从**单点**推广到**组合**：

| | 问的问题 |
|---|---|
| `vacuity_check` | 测试有没有在验证实现？（判据的**存在性**） |
| `composition_check` | 集成判据有没有覆盖它声称覆盖的每一个模块？（判据的**作用域真实性**） |

---

## 决策一：桩必须签名保真，不能删文件

删文件会得到 `ImportError`。测试确实变红了，但那是**红对了、理由错了**：

- ImportError 只证明「A 的文件存在」
- 证明不了「集成测试覆盖了 A 的**行为**」
- 一个只写了 `import a` 的集成测试，在删文件时也会红

所以桩化走 AST：**同名函数、同参数、同装饰器，模块级常量与类结构原样保留**，
只有函数体变成 `return None`。这样导入照常成功，
**只有真的调用了 A 的行为的测试才会红**。

```python
class _BodyStubber(ast.NodeTransformer):
    def _stub(self, node):
        self.generic_visit(node)          # 先处理嵌套函数
        node.body = [ast.Return(value=ast.Constant(value=None))]
        return node
```

---

## 决策二：必须同时把该模块**自己的测试**藏起来

**这一步不是优化，是结论成立的前提。**

不藏的话这个算子自己就是空的：

> 集成谓词若是 `pytest workspace -q`（跑全部测试），
> 桩化 A 一定会让 **A 自己的单元测试**变红 ——
> 于是每个模块都显示「已覆盖」，**这个检查永远返回通过**。

★ 那正是它自己要防的那种「零输入的绿灯」，只不过发生在**检查器身上**。
  写一个永远说「一切正常」的检查器，比不写更糟 —— 它会让人以为查过了。

藏掉 A 的自测之后，剩下还会红的必然来自 A 之外，也就是真正跨模块的用例。

`test_module_own_tests_do_not_count_as_integration_coverage` 钉住这一步。
**因果检验过：把「藏自测」那几行去掉，正好是这条测试变红，其余四条不受影响。**

---

## 决策三：模块列表从工作区实际状态推导，不从 packet 声明读

`discover_modules()` 找 `workspace/<module>/src/` —— Planner 的分配约定。

声明会与现实漂移（改了目录忘了改声明），目录不会。
而这一层要判的正是「**实际存在的**模块有没有被集成测试覆盖」。

---

## 决策四：只对集成 packet 生效

`packet.role == "integrator"` 且发现的模块数 ≥ 2 才跑。

对单模块 packet 谈「组合」没有意义，那一层由 `vacuity_check` 守。
不加这条限制的话，每个普通 coder packet 都要付一遍逐模块桩化的代价，
而且会因为「它没集成别的模块」被误拦。

---

## 判据（8 条）

两个方向都必须钉住 —— **一个永远说「全部覆盖」的检查也能跑通**：

| 测试 | 守什么 |
|---|---|
| `..._absent_from_integration_is_reported` | 假集成被拦下（只用了 beta，alpha 被报） |
| `test_real_integration_passes` | **真集成被放行**（否则它只是个永远拦人的门） |
| `..._own_tests_do_not_count_as_...` | 藏自测那一步确实生效（否则检查器自己是空的） |
| `test_stub_is_importable_not_a_missing_file` | 桩签名保真：模块级常量保留、函数体掏空 |
| `test_workspace_is_restored_byte_for_byte` | 逐字还原，且藏起来的自测全部复原 |
| `test_discover_modules_follows_planner_layout` | 模块发现跟随 Planner 约定 |
| `test_gate_rejects_integration_that_skips_a_module` | **门禁端到端真的拦下了** |
| `test_gate_skips_composition_for_non_integration_packets` | 非集成 packet 不跑这一层 |

★ 门禁那两条的断言有个坑，写的时候差点踩进去：
  最初断言的是 `"alpha" in verdict.detail`。
  但**第五层 `vacuity_check` 的失败消息里会列出测试文件路径**
  （`alpha/tests/test_alpha.py`）—— 它同样包含 "alpha"。
  那样的话这条测试可能是被第五层拦下而通过的、**根本没走到第六层**，
  而我们看不出区别。改成断言第六层特有的措辞「集成测试没有覆盖」。

---

## 局限（记在案，不假装没有）

- 只对「模块 = 目录」的拆分方式有效 —— 而 Planner 正是这么分的
- 桩化后若因 `TypeError` 而红，仍算「覆盖到了」。那确实说明集成测试用到了
  A 的返回值，但**不能区分「用到了」与「验证了」**
- 逐模块各跑一遍谓词，代价是 O(模块数 × 谓词耗时)。这是它只对集成 packet
  生效的另一个理由
