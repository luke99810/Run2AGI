# ADR-0011：判据的生命周期 —— 影子档位、资产负债表、缺口报告

- **日期**：2026-08-14
- **状态**：✅ 已接受
- **相关**：[ADR-0008](0008-进化层-经验沉淀与判据因果检验.md)（判据的因果检验）

---

## 背景：判据被当成常量，而它其实是资产

到目前为止，一条判据一旦写进 `DEFAULT_RULES` 就永远生效、永远存在。
没有档位、没有命中统计、没有退役机制。

这带来三个具体问题：

1. **新判据不敢加。** 它一上线就拦人，第一次误拦就会让人把它整条关掉 ——
   **而关掉之后它再也不会被打开。**
2. **旧判据不敢删。** 谁也说不清「这条到底拦过东西没有」。
3. **判据缺陷没有信号。** 编码缺陷会让某条测试变红；
   判据缺陷不会 —— 因为缺的正是那条测试。

这三件事各自的解法不同，但共同的前提是同一个：
**判据要有可观测的状态**。

---

## 决策一：影子档位（`shadow` / `enforcing`）

`shadow` = **评估、记录，但不拦截**。

新判据先在影子里跑，攒够证据再晋级。晋级到 `enforcing` 的条件：

| 条件 | 为什么 |
|---|---|
| 在真实案例上**命中过 ≥1 次** | 从没命中过的判据，和没有这条判据在证据上不可区分 |
| **变异检验能杀死它** | 否则它被改坏了不会有任何信号 |

### 默认是 `enforcing`，不是 `shadow`

这个方向是有意选的：

```
默认 shadow    → 新加的规则不生效，而这件事是**静默的**
                 （它躺在判据集里，实际什么都不拦）
默认 enforcing → 可能误拦，但那是**响亮的**
```

**响亮的失败优于静默的失败。** 要影子就显式登记，
而登记这个动作本身会留下「这条还没准备好」的痕迹。

### 第一条真实的影子判据

`check_predicate_covers_owned_paths` —— 验收谓词的作用域应当与
packet 拥有的路径有关。拥有 `workspace/alpha/` 却去跑
`pytest workspace/beta -q`，谓词会绿，而它验的是**别人写的东西**。

它是启发式的（谓词形态千变万化），所以它正是影子档位该装的东西。

★ 匹配用**路径链关系**而不是字符串包含 ——
  纯 `in` 会让 `workspace` 匹配上 `my-workspace-backup`。

## 决策二：命中账本连「没命中」也记

`AdmissionChecker.recorder` 是**注入**的，控制平面不自己挑路径
（挑了就会和引擎的 `state_dir` 分叉成两处，而两处各自看起来都正常）。

引擎把它写到 `<state-dir>/judgements/hits.jsonl`，每行含
`packet / rule / mode / fired / code`。

★ **连没命中的也记**，因为资产负债表要靠它区分两件完全不同的事：

```
跑过 N 次、一次没命中  → 判据可能多余
根本没人在记录          → **观测本身坏了**，表上所有数字都不可信
```

只记命中的话，两者在账本上都是「没有这条判据的行」。

★ `packet` 字段是必须的：缺口报告要回答「这个 packet 失败之前，
  有没有任何判据 fired 过」—— 没有它，命中记录与失败记录**关联不起来**，
  而那正是「判据缺口」的定义所在。

---

## 决策三：资产负债表把三处信息合起来看

`scripts/judgement_ledger.py` 汇总档位 + 命中 + 变异检验。

单看任何一个都得不出结论，**合起来才有意义**：

| 档位 | 命中 | 变异 | 结论 |
|---|---|---|---|
| enforcing | 0 | 存活 | **★ 建议删除** —— 既没拦过东西，也没人守着 |
| enforcing | 0 | 被杀死 | 留着 —— 有测试守，只是还没遇到坏情况 |
| shadow | >0 | 被杀死 | **★ 够格晋级 enforcing** |
| shadow | 0 | 任意 | 继续影子 —— 晋级无据 |

★ 「建议删除」是这张表存在的主要理由。一条从没命中、也没人守的判据，
  和没有这条判据在证据上不可区分 —— 但它会让判据集**看起来更长**，
  而那是一种廉价的安全感。

★ 没有账本时显示 `未观测` 而**不是 `0`**。把坏掉的管道显示成一个
  看起来正常的数字，比不显示更糟。

### 首轮真实数据

3 次真实的需求提交（准入真跑，模型 Key 无效不影响这一层）：

```
9 条规则 · 各跑过 3 次 · 命中 0 次 · 变异检验全部「被杀死」
→ 全部「留着：有测试守，只是还没遇到坏情况」

check_predicate_covers_owned_paths  shadow  命中 0
→ 「继续影子：还没有命中过，晋级无据」

4 道门禁  → 「未观测」（recorder 目前只挂在 AdmissionChecker 上）
```

★ 影子规则命中 0 次是**诚实的数据**，不是失败：
  说明这 3 个真实 packet 的谓词确实引用了自己拥有的路径。
  它老老实实停在影子里，没有被凑数晋级。

★ 门禁那四行显示「未观测」而不是 0 —— 这是一个**已知缺口**，
  写在表上比藏起来好。

## 决策四：缺口报告只报，不自动写规则

`scripts/judgement_gaps.py` 找的信号是：

> 同一类失败在 ≥N 个不同 packet 里复现，
> 而这些 packet 在准入时**一条判据都没 fired 过**。

反复撞同一堵墙、而事前没有任何东西拦过 —— 那就是一个判据缺口的位置。

### 为什么不自动补规则

自动生成判据是很自然的下一步，技术上也不难。**但它是错的。**

判据是用来判执行者的。让系统根据自己的失败去写判据，
等于**执行者给自己出考题** —— 直接违反本项目自己定的 `mustDifferFrom`。

★ 自进化系统里，**哪一环必须留给外部，是设计问题不是能力问题**。
  这里的边界划在：检测自动化，补规则留给人或独立角色。
  而补上的规则应先进 shadow 档位 —— 那条链路现在已经在了。

### 两条判定细节

**一个 packet 被守住就不算缺口。** 只要有一个 packet 在事前被判据
fired 过，说明系统里已经有东西在管它，只是那一次没拦住 ——
那是判据**强度**问题，与「压根没有判据」是两类完全不同的工作。
混在一起报，会让人去补一条已经存在的规则。

**空结果必须报成「样本不足，未能判定」。** 不能报「没有缺口」——
聚类需要样本，而累计运行还太少。把它读成绿灯，
就是又一个零输入的绿灯。

★ 首轮真实运行的结果正是「样本不足」，而报告如实这么说了。

## 判据

- 影子机制 4 条（`TestShadowJudgements`）：shadow 命中但不拦 ·
  **未登记默认 enforcing 而非 shadow** · shadow 命中被记录 · 没命中的也记
- 影子规则本身 3 条（`TestPredicateScopeShadowRule`）：路径链匹配 ·
  兄弟路径被标记 · 子串相似不算匹配
- 账本落盘 1 条（引擎端到端）
- 报告逻辑 7 条（`tests/test_judgement_reports.py`）：
  缺口判定三条 + 建议逻辑四条，含「未观测不得报成 0」

★ 缺口报告与资产负债表的核心逻辑都抽成了**纯函数**再测 ——
  埋在 `main()` 里只能靠肉眼看输出确认，
  而这两个脚本本身就是用来找「没人守的东西」的，
  它们自己没人守就太讽刺了。
