# 架构决策记录（ADR）

一个决策一个文件，编号递增，**只追加不改写**。

## 为什么要有这个目录

三人 + Agent 开发，最贵的浪费不是写错代码，是**同一个问题被重复讨论**。ADR 让"当时为什么这么定"可查，也让被否决的方案留痕——被否决的方案往往比被采纳的方案更有价值，因为它记录了边界。

这与系统内部的 `decisions.jsonl` 是同一个机制的人类版本。

## 什么时候要写 ADR

| 情况 | 要写吗 |
|---|---|
| 改动影响两个以上 package | ✅ 必须 |
| 变更 `packages/contracts/**` | ✅ 必须（`contract` 类型的提交必须附 ADR 链接） |
| 选型（语言、框架、存储、模型路由） | ✅ 必须 |
| 推翻之前的 ADR | ✅ 必须（新写一篇，把旧的标为「已被 NNNN 取代」） |
| 同一类问题被 A 裁决了 3 次以上 | ✅ 必须——说明该沉淀成规则了 |
| 单个 package 内部的实现选择 | ❌ 不用，写在代码注释里 |

## 格式

```markdown
# ADR-NNNN：标题

- **日期**：YYYY-MM-DD
- **状态**：提议中 / 已接受 / 已被 ADR-NNNN 取代 / 🔴 待决
- **决策人**：

## 背景
（是什么问题逼着我们做这个决定）

## 决策
（定了什么）

## 否决的方案
（★ 别省这一节——它记录的是边界）

## 后果
正面 / 代价 / 风险
```

**状态只往前走，不回退。** 一个 ADR 被推翻时，不删不改，标注「已被 ADR-NNNN 取代」。
