# ADR-0009：MCP 连接点归引擎，runner 只收已连好的工具箱

- **日期**：2026-08-14
- **状态**：✅ 已接受
- **相关**：[ADR-0007](0007-引擎入口归属与装配点.md)（引擎入口与装配点）

---

## 背景：两个缺陷，第二个才是要害

**一、`mcp_config_dir` 全仓库无人传。**

`AgentRunnerConfig.mcp_config_dir` 定义了，README 写了，真机演示过
（模型自主调用 `github__list_commits` 拿到真实 SHA）——
但整个仓库里**没有任何一处传过它**，不在 service，不在测试，不在脚本。
也就是说在生产路径上，MCP 根本没有办法被打开。

这与「langgraph 装在依赖里零 import」是同一个形状，而且同样
**没有任何测试会红**：`test_mcp_client.py` 那 15 条全绿，
它们测的是模块本身 —— 模块本身当然是对的，它只是没接上。

**二、连接点在错误的层。**

`build_mcp_toolbox()` 是在 `_AgentRun.__init__` 里调的，
而 `_AgentRun` 是**每个 packet 新建一次**的。也就是说，
如果当初真把目录传进去了，后果是：

- 每个 packet 把所有 MCP server 重连一遍
- 8 路并行 = 48 个 npx 进程
- 与设计里那句「**主 Agent 接一次，所有已连服务的工具自动进入工具面**」直接冲突

★ 第二个缺陷比第一个隐蔽得多：第一个是「没接」，一眼能看出来；
  第二个是「接了，但接在错的地方」—— 它能跑通，只是代价荒谬。
  而且因为第一个缺陷的存在，**第二个从来没有机会暴露**。

---

## 决策一：连接点上移到 `EngineService`，连一次并共享

`EngineService._ensure_mcp()` 懒连接一次，之后所有 packet 共享同一个工具箱。

**懒连接而非启动即连**：没有 packet 要跑时不该有 npx 进程在后台待着，
handshake 也不该被几秒的 server 启动拖住。

**共享是安全的**：`McpClient._request` 用 `threading.Lock` 把
「写请求 + 读到匹配 id 的响应」整段护住了，并行 packet 不会串包。
—— 这一条是先去核对过才敢共享的，不是假设。

---

## 决策二：runner 收「工具箱」而不是「配置目录」

这是本 ADR 真正想固定下来的东西。

|  | 结果 |
|---|---|
| 收配置目录 | runner **有能力**自己连 → 迟早有人在 `__init__` 里连 → 回到原缺陷 |
| 收已连好的工具箱 | runner **根本没有连接的手段** |

★ 这是本项目那条约束实现优先级的直接应用：
  **不可见 > 无权限 > 被拦截 > 提示词劝阻**。
  一条「请只在引擎层连一次」的注释属于最后一档，
  而最后一档在半年后的重构里是不设防的。

`test_runner_config_cannot_connect_mcp_by_itself` 把这条性质钉住：
`AgentRunnerConfig` 里必须有 `mcp_toolbox`、且**不得**有 `mcp_config_dir`。

---

## 决策三：默认关，但「关」必须看得见

`EngineConfig.mcp_config_dir` 默认 `None`。

**默认关是有意的**：可启动的 server 靠 npx 拉起来，启动要几秒、要网络、
缺凭据的还会失败。默认开等于给每次引擎启动加一段不可控的等待与失败面。

**但「默认关」不等于「没接」** —— 区别在于现在它是**一个开关**，
在此之前它是死代码。

连接结果落盘到 `.codentum/mcp/connections.json`：配置目录、连接时刻、
工具总数、每个 server 的 connected / toolCount / **error 原文**。

★ 没有这份报告的话，下面三种情况从外面看是同一个样子：

    1. 没配置
    2. 配了，但一个都没连上
    3. 连上了，但模型没调用

  都表现为「MCP 好像没起作用」，而它们的处理办法完全不同。
  失败原因必须**说出缺哪个环境变量的名字** —— 否则使用者只看到
  「没连上」，不知道该去配什么。

### 真机一跑，第 2 种当场发生了

接完之后指向真实的 `packages/roles/mcp/` 跑了一次：
**工具总数 0，而且连一条连接报告都没有。**

原因是 `load_mcp_configs` 静默跳过了全部 10 个配置：

| 情况 | 数量 | 说明 |
|---|---|---|
| `enabled: false` | 6 | 出厂即关闭，靠 `credentialHowTo` 指导逐个打开 —— **这是有意的设计** |
| 声明式清单（`transport: http`） | 1 | 只作能力投影，不启动 |
| stdio 但**没有 command** | 3 | `browser` / `filesystem` / `git`，配置本身不完整 |

出厂即关闭是对的。但「静默跳过」不对 —— 一个刚接手的人把目录配对了、
什么也没发生，**会先去怀疑代码**，而答案其实写在配置文件的
`credentialHowTo` 字段里。

于是补了 `describe_skipped()`：列出每个没被加载的条目**及原因**，
并把配置自己写的开启指引原样带出来。现在报告长这样：

```
playwright.json   enabled=false（未启用）。无需凭据；首次运行会下载浏览器内核
github.json       enabled=false（未启用）。GitHub → Settings → Developer settings → …
browser.json      stdio 但没有 command，无法启动
agentteams.json   声明式清单（transport='http'），只作能力投影不启动
```

★ 这条是自己给自己做观测的直接回报：ADR 里写下「三种情况看起来一样」
  之后第一次真跑，撞上的正是第 2 种。**先写清楚要防什么，
  比事后解释发生了什么便宜得多。**

## 判据

四条守接线，一条守链路末端：

| 测试 | 守什么 |
|---|---|
| `test_mcp_is_off_when_not_configured` | 不配 = 不连，且不留痕迹让人误以为连过 |
| `test_mcp_connects_once_and_is_shared` | 反复取工具箱拿到**同一个实例** |
| `test_mcp_connection_report_lands_on_disk` | 报告落盘且含每个 server 的状态 |
| `test_runner_config_cannot_connect_mcp_by_itself` | 「自己连」这条路在结构上被堵死 |
| `test_mcp_tools_reach_the_model_tool_surface` | **MCP 工具真的出现在模型请求里**，与内置工具并排 |

最后一条是链路的最后一段。前四条全绿而模型看不到工具的话，
从结果上和没接是一样的。

★ 全部用**真子进程 MCP server**（复用 `test_mcp_client` 的最小实现），不打桩。
  打桩能证明代码路径通，证明不了协议握手真的成立。
