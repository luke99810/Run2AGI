# ADR-0006：预算与成本口径由 USD 改为 CNY

- **日期**：2026-08-10（**追记**；变更本身发生在 2026-08-06，见 §五）
- **状态**：✅ 已接受
- **决策人**：A（队长）
- **相关**：[ADR-0005](0005-模型-Provider-选阿里云百炼.md)（百炼为默认 Provider）
- **落地提交**：`50bca30 refactor: USD → CNY 改用人民币，国产模型为主`

---

## 一、背景

ADR-0005 把默认 Provider 定为阿里云百炼，但当时**没有连带处理计价口径**。
契约在第 0 周冻结时写的是美元：

```
BudgetGrantRuntime.limit_usd · WorkerCompleted/Failed/Aborted.spent_usd
Usage.cost_usd · ModelGateway.open(grant_usd=...)
```

百炼按**人民币**计价。于是只剩两条路，两条都不能走：

1. **把人民币数值塞进 `*_usd` 字段** —— 字段名与实际单位不符。
   这类不一致不会报错，只会让账本在某一天被人按美元读一次，
   而没有任何测试会因此变红。正是本项目一直在防的那类静默缺陷。
2. **在网关里按固定汇率折算** —— 汇率是会动的，折算误差被埋进账本，
   事后无法区分「模型贵了」还是「汇率变了」。**把不可归因的误差写进
   记账系统，比不记账更糟。**

所以口径必须改，而且必须改在契约层。

---

## 二、决策

**预算、授权与成本一律以人民币（CNY）为单一口径，字段后缀统一为 `_cny`。**

```
BudgetGrantRuntime.limit_cny
WorkerCompleted / WorkerFailed / WorkerAborted.spent_cny
Usage.cost_cny
ModelGateway.open(role, routing, grant_cny)
```

三点约束：

1. **系统内不存在汇率。** 不做任何货币折算——网关拿到什么币种的价格，
   就要求该 Provider 的价格表以 CNY 表达。多币种是 Provider 适配层的问题，
   不是账本的问题。
2. **口径唯一。** 不并存 `*_usd` 与 `*_cny`，不留兼容字段。
   两套口径共存 = 迟早有一处读错，而且读错时不报错。
3. **仍然不按 token 记预算。** 这一条来自已冻结接口的原有约束，本次不变：
   不同模型家族分词器差异可达 ~30%，异构路由下按 token 记预算会静默失真，
   且失真方向随路由变化。**换币种不改变「按货币记账」这个决定。**

---

## 三、否决的方案

| 方案 | 否决理由 |
|---|---|
| 保留 `*_usd`，网关内按固定汇率折算 | 误差不可归因（见 §一.2）；且汇率写死在代码里迟早过期 |
| 保留 `*_usd`，把人民币数值直接写进去 | 字段名撒谎，零测试会变红 |
| 引入 `Money{amount, currency}` 值对象 | 表达力够，但要改 8 份 schema + 两端序列化，且当前只有一个币种。**为一个不存在的需求付冻结期的改契约成本，不划算。** 若将来真需要多币种，走新 ADR |
| 不改契约，只在 UI 层显示人民币 | 展示层折算 = 账本与展示不一致，排查成本转嫁给最没有上下文的人 |

---

## 四、后果

**正面**
- 账本与百炼官方计价同币种，成本数字可逐笔对回账单
- 系统内无汇率，去掉了一整类不可归因误差

**代价**
- 一次性触及 39 个文件（其中 5 个是契约真源：`interfaces.py` /
  `state.py` / `budget.schema.json` / `identifiers.schema.json` / `state.ts`），
  外加 fixtures 全量重写
- Anthropic 作为第二实现时，其价格表需在 Provider 适配层折算成 CNY 后再进账本，
  折算参数必须显式配置、可审计——不许在代码里写死

**风险（🔴 尚未关闭）**
- **价格表证据缺失。** 当前 `TokenPricingConfig` 仍按 unknown pricing 运行，
  真实 smoke 只能证明模型连通性，**不能证明成本数字准确**。
  在补上百炼官方价格表并写成可审计配置之前，任何成本展示都不应被当作依据。
  这一条不属于本 ADR 的决策，但属于本 ADR 的未完成后果，故记在此处。

## 五、★ 这份 ADR 是追记的 —— 变更先于 ADR 发生

必须如实写明，因为它本身就是一次流程违规的证据：

- `boundaries.yaml` 的 `frozen_at = 2026-08-02`
- 契约冻结后改 `packages/contracts/**` 的规则是：**三人同意 + 新 ADR + 走变更窗口**
- 而 `50bca30`（2026-08-06）改了 5 个契约文件，**提交信息只有一行，没有 ADR**
- 本文写于 2026-08-10，是**事后补记**，不是事前决策

**为什么补而不是假装没发生**：这个项目的中心主张是「可靠性来自不变量，不是靠约定」。
一次绕过冻结的契约变更被无声地放行，说明当时那条规则**只是约定**——
`check_boundaries` 的 I3 检查能对回作者，却拦不住「作者对但没写 ADR」。
把它记下来，比让它消失更有用。

**两条应当落进流程的推论**：

1. **I3 应当增加一条：`type: contract` 的提交若未引用 ADR 编号，直接拒绝。**
   目前 I3 只校验「改 contracts 的人是不是 A」，不校验「有没有 ADR」——
   于是这次变更在门禁眼里是完全合规的。**一个只检查一半的门禁，
   它的绿灯与「全部合规」长得一模一样。**
2. **口径类变更要连带扫描注释。** 本次字段全改完了，
   但 `interfaces.py` 里「只有 usd」那行注释留到了 08-10 才被发现——
   四天里它一直在向读代码的人陈述一件与实现相反的事。
