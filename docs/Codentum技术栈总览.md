## 一句话

**Python 核心引擎 + TypeScript 桌面端，JSON Schema 作为跨语言契约的唯一真源。**

选型总原则不是"哪个技术更强"，而是：

> **不可恢复的错误交给确定性代码，可恢复的错误才交给模型。**
> 落到技术栈上 = **能在编译/校验期挡住的，不要留到运行期；能在运行期挡住的，不要留给提示词。**

## 二、为什么从 TypeScript 改成 Python

08-02 的 ADR-0002 用四条理由选了全 TypeScript。其中三条现在依然成立，**但它漏掉了一个变量：团队的实际熟练度。**

事实：三人都是 Python 熟、TS 生疏，距初赛截止 15 天。

> **「团队写不动」是比「契约可能漂移」更硬的约束。**
> 一个理论上更优、但团队要边学边写的技术栈，在 15 天窗口里是净负债。

ADR-0002 的技术论证本身没错，错在**把一个从没验证过的假设当成了已知**——它默认团队对两种语言成本相同。

### 采纳的其他理由

1. RAG / 嵌入生态 Python 更厚
2. 动态性让「Agent 写 Skill」更顺
3. Aider、OpenHands 是 Python（Devin 闭源、OpenClaw 实现不详，这两个不作证据）

### 没采纳的一条（记下来免得重复讨论）

**「Node 动态性不如 Python」不成立。** `new Function()` / `vm.runInNewContext()` 一样便宜。差别在**要不要让生成代码先过类型检查**，而那是选择不是限制。

## 三、失去 `tsc` 之后，门禁怎么补

这是这次改动**最实在的损失**，必须正视。

`tsc --noEmit` 是零成本、确定性、一秒出结果的验收谓词，天然属于 Harness「收敛阶段【无模型】」的那一段。Python 没有等价物。

### 替代方案（三层）

```
mypy --strict        静态类型
ruff                 lint（含 bandit 安全规则、禁 print）
pydantic v2          ★ 运行时校验 —— TS 没有的东西
```

### ⚠️ 但 mypy 可以被绕过，tsc 不能

所以 `pyproject.toml` 里定死了一条：

```toml
enable_error_code = ["ignore-without-code", ...]
warn_unused_ignores = true
```

**裸的 `# type: ignore` 直接报错**，必须写成 `# type: ignore[具体错误码]` 并附一行理由。

配套规则：**ignore 数量进 CI 计数，只许降不许升。**

> 不这样做，「能绕过的约束等于没有约束」就会应验在我们自己身上。

### Pydantic 补回来的东西

生成的模型全部 `frozen=True` + `extra="forbid"`，且**品牌类型带 pattern 校验**：

```python
PacketId = NewType("PacketId", Annotated[str, StringConstraints(pattern=r"^wp-[0-9a-z]{6,}$")])
```

- `NewType` → mypy 下 `PacketId` 与 `EvidenceRef` 不可互换（等价 TS 品牌类型）
- `Annotated` → 运行时校验格式

**已验证**：畸形 id、错误 digest 格式、写成人话的 reasonCode，全部被运行时拒绝。这是 TS 侧做不到的。

## 四、跨语言契约怎么防漂移

跨语言边界是契约漂移的高发区。**唯一有效的缓解是：两侧都是生成物，谁都不手写。**

```
packages/contracts/schemas/*.json          ← 唯一真源，8 份
            │
   python scripts/gen_types.py
            ├──→ python/codentum_contracts/state.py    (Pydantic)
            └──→ typescript/state.ts                   (供桌面端)
```

`make gen-check` 同时校验两套输出。手改任一侧 → CI 红。

> 这是当初把真源放进 JSON Schema 而不是 TS 类型的意外回报：
> **换语言的代价从"重写契约"降成了"加一个发射器"。**

### ★ 一个减小风险的发现

**四个核心接口只有 Python 一侧**——它们全在引擎内部。桌面端是纯读端，只读 `.codentum/` 状态文件，不实现也不调用它们。

**所以跨语言边界只覆盖 state 数据，不覆盖行为契约，比预想的小得多。**

### 跨语言踩到的两个真坑（已堵）

| 坑 | 现象 | 修法 |
|---|---|---|
| `from` 是 Python 关键字 | schema 里 `from`/`to` 字段导致生成的 Python 语法错误 | `Field(alias="from")`，属性叫 `from_`，线上格式不变 |
| Windows 控制台 GBK | 脚本打一个 ✓ 就抛 UnicodeEncodeError，**且抛在最后一行**（工作已全做完） | `lib/console.py` 统一切 UTF-8 |

第二个坑值得说：**"崩在最后一步"的报错最容易误导人去查前面的逻辑**。三个人都在 Windows 上，不堵一定会踩。

## 五、LangGraph 用在哪层

「Graph 工程」和 LangGraph 的 Graph **不是同一个东西**，混在一起会导致架构层次错位。

| | 是什么 | 例子 |
|---|---|---|
| **本设计的「四张图」** | **数据结构** —— 系统状态的拓扑 | 依赖图、所有权图、溯源图、知识图 |
| **LangGraph 的 Graph** | **控制流图** —— 一次执行的步骤走向 | 节点是函数，边是转移，state + checkpointer |

**依赖图不是可执行的图，它是一张"谁要等谁"的表。** 拿 LangGraph 表达它是范畴错误。

但**一次 Coder 执行内部的 plan → edit → test → fix，正是 LangGraph 擅长的**——这就是「Loop 工程」和「子 Agent 内部规划」。

### 分层结论

```
控制平面  ❌ 不用 LangGraph
  调和循环（对标 K8s controller）· 路径锁 · 准入 · 门禁 · Guardian
  状态 = .codentum/ 的 Git 文件。★ 零 LLM。
              ↓ WorkerRuntime.spawn()
执行平面  ✅ 用 LangGraph
  准备【无模型】 → ★ LangGraph 图【有模型】 → 收敛【无模型】
  每角色一张图：RARE-V 循环 · 分级求助 · 子 Agent 内部规划
```

### ★ 必须守住的边界

> **LangGraph 的 state 是【一次执行的临时状态】，永远不会成为系统状态。**

| 规则 | 违反的后果 |
|---|---|
| checkpointer 只存本次执行的中间态，**不存四张图** | 系统状态出现第二个真源，Git 不再权威 |
| 图的节点**不得直接写 `.codentum/`** | 绕过准入校验与审计链，六条不变量全部失效 |
| 出口只有一个：产出 `WorkerOutcome`（含 evidence） | 状态推进失去证据（破坏 I6） |

**判据：把 LangGraph 整个换掉，控制平面应当一行都不用改。**

### 为什么不用 AutoGen / CrewAI

它们的抽象层次是"多个 Agent 对话协作"，而**本设计里 Agent 之间不直接对话**——协同发生在控制平面，通过 WorkPacket 的依赖、路径锁的独占、门禁的判定。

这是它与"多 Agent 对话框架"的根本分野，也是并行安全能被证明的原因。所以需要的是**单 Agent 内部**的编排，不是 Agent 间的对话编排。

## 六、数据层

### ★ 状态存在 Git 仓库里，不是数据库

```
.codentum/
├── graph.json          依赖图（静态 DAG）+ 所有权图（运行时）
├── packets/<id>.json   WorkPacket
├── evidence/<id>.json  证据（带审计哈希链）
├── decisions.jsonl     决策追加日志 —— 溯源图的边由此派生
├── budget.json         预算
└── knowledge/          知识图（有环）
```

| 想要的性质 | Git 白送 | 数据库要另建 |
|---|---|---|
| 完整历史、可回滚 | ✅ | 审计表 + 触发器 |
| 每次变更有作者/时间/原因 | ✅ commit | 自己设计 |
| 分支 = 并行探索 | ✅ | 极难 |
| **Solo / Team 双模式共用一套控制平面** | ✅ | 几乎不可能 |

### SQLite 的定位

**只做可重建的派生索引**，不是真源。推荐 `sqlite3`（stdlib）或 `aiosqlite`。

> ⚠️ **判据：删掉整个 SQLite 文件，系统重建后应完全等价。**
> 做不到，就说明它已经悄悄变成真源了。

### 向量检索：MVP 先不做

检索有**确定性梯度**，越靠上越确定：

```
exact → structural → lexical → semantic
                                  ↑ 最不确定，兜底用
```

**检索必须确定性可复现**（同 query + 同索引版本 → 逐条相同结果），否则 replay 失效，出了问题永远查不出是模型的锅还是检索的锅。

真需要时用 `sqlite-vec`，不引独立向量数据库。

## 七、⚠️ 本次改动引入的最大风险

**Electron 拉起 Python 引擎 + PyInstaller 打包。**

```
Electron 主进程  ──spawn──→  Python 引擎（stdio 或 localhost HTTP）
发布时：PyInstaller 打成单可执行文件随包分发
```

这比纯 Node 打包明显难，**而且落在经验最薄的成员（C）身上**。

**必须做的事：P1 阶段就打通一次最小链路**（Electron 拉起 Python、通一次消息、打包跑通），不要等到最后一周。冷启动复现测试必须覆盖它。

> 这是 ADR-0003 里明确记下的代价。记下来是为了**它真出问题时我们知道这是预料之中的，而不是意外**。

## 八、图表库 —— 前端唯一真正待定的选型 ⬜

甘特图 + 依赖图（DAG）是控制台两块主屏，也是 Demo 现场评委盯着看的东西。

**建议**：**依赖图用 `dagre`（只做布局）+ 自绘 SVG；甘特图自己画。**

理由：甘特图本质是"横条 + 时间轴"，自己画不难且完全可控；DAG 的**布局算法**才是真难点，那部分借现成的。既不引重库，又不啃最难的那块。

**判据（选之前问自己）**：

```
□ 100+ 节点时还流畅吗？
□ 空数据（empty 快照）不崩吗？   ★ 最常被跳过的边界
□ 能否在 Electron 里离线跑（不拉 CDN）？
□ C 能在两天内做出可用版本吗？
```

### 模型路由的三条已知事实（别踩）

1. **预算一律用货币，不用 token** —— 分词器差异可达 ~30%，异构路由下 token 预算会静默失真，**且失真方向随路由变化，事后查不出来**
2. **同一次尝试内不换模型** —— 缓存按模型分桶，中途换 = 整个前缀冷重写。**要加强就提高 `effort`**
3. **Evolver 走 Batch API** —— 延迟不敏感，约五折，纯赚无取舍

### 11.1 唯一的硬要求：AgentTeams

手册原文：**「多 Agent 协同设计必须以 AgentTeams 为设计基点」**。

这是清单里唯一用「必须」措辞的一条，也是**此前技术栈总览完全没提到的一条**。
补上，并说明它在架构里的确切位置：

```
Solo 模式   本地单进程 + 本地 Worker + 本地 Git + SQLite     零外部依赖，装完就跑
Team 模式   ★ 跑在 AgentTeams 上（Manager-Workers）           赛题基点
            └ 四个接口的另一套实现，控制平面一行不改
```

**对齐点是 `WorkerRuntime`**：Solo 模式下它 spawn 本地进程，Team 模式下它把
WorkPacket 投给 AgentTeams 的 Manager-Worker。这不是为赛题临时加的适配层 ——
双运行模式在 08-01 的设计里就定死了，四个接口「P1 就定死，之后只加实现不改签名」。

> ★ 这一条要在参赛材料里讲清楚：**我们不是在 AgentTeams 之上再套一层框架，
> 而是把它作为执行平面的运行时之一。** 控制平面（不变量、锁、门禁）是我们的
> 增量，AgentTeams 是它调度的对象。两者是编排与被编排的关系，不是竞争关系。

| 项 | 内容 |
|---|---|
| 安装 | 一键脚本（Windows PowerShell / macOS / Linux 各一条，见清单 §1.2） |
| 强依赖 | **Docker Desktop / Engine**（4 核 8G 起） |
| 验证 | `docker ps \| grep hiclaw-manager` · Element Web `:18088` · Higress 控制台 `:18001` |
| 现状 | ⬜ **尚未安装验证** —— 清单里这是「成员 B」的事项 |

| **LoongSuite + AgentScope Studio** | 无侵入采集推理轨迹 | 🟡 **待评估** | 同上。LoongSuite 需 Node.js 22，与桌面端技术栈不冲突 |
| **Nacos** | Agent/Skill/Prompt/配置的管理与服务发现 | ⚠️ **Solo 不用，Team 可选** | ★ **本地优先产品的配置真源必须是本地文件**。Skill Manifest、RoleSpec、boundaries 都在 Git 里 —— 那是刻意的：配置进了外部注册中心，「删掉它系统仍能重建」就不成立了。Team 模式下作为**派生的**服务发现可以接 |
| **PolarDB for PostgreSQL（pgvector）** | 向量、长记忆、RAG、审计日志存储 | ❌ **MVP 明确不用** | 见 §六：检索有确定性梯度，`exact → structural → lexical → semantic`，**语义检索是兜底不是首选**。MVP 阶段引向量库会让「检索确定性可复现」这条先失守。真需要时用 `sqlite-vec`，不引独立向量数据库 |
| **RocketMQ** | 事件驱动、异步调度、**Agent 间消息协同**、状态流转 | ❌ **明确不用** | ★ **它的核心用途与本设计的中心分野直接冲突：Codentum 里 Agent 之间不直接通信。** 协同发生在控制平面 —— 通过 WorkPacket 的依赖、路径锁的独占、门禁的判定。引入消息总线等于开一条绕过控制平面的旁路，六条不变量会从那里漏掉 |

> ⚠️ **两条 ❌ 要在参赛材料里主动讲，不要等评审问。**
> 「用了多少阿里云组件」和「架构是否自洽」在评审那里未必同权，但
> **一个说不出为什么不用的选择，一定是减分的**。
> 尤其 RocketMQ 那条 —— 拒绝它恰恰是在演示本设计的核心主张，
> 讲好了是加分项而不是缺失项。
