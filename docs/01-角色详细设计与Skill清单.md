# 角色详细设计与 Skill 清单

> `00` 定义了架构与三大工程的系统级规则，本文档把它们落到每一个角色身上。
> 每个角色的巧思，都长在它**特有的失败模式**上——不是通用技巧的复制粘贴。
> 配套 `00-总体设计方案.md`

---

## 本文档结构

```
第一部分  各角色的 Harness / Loop / Graph 精密设计与巧思    ← 主体
第二部分  Helper —— 分级求助的执行者
第三部分  Agent Identity 清单（标准模板渲染）
第四部分  核心 Skill 清单与复用矩阵
```

> ⚠️ **一处修正（实施以 `00` 为准）**：下文 Planner 巧思 2「垂直切片优于水平切片」的表述有实质性漏洞。
> 纯垂直切片会让 packet 超预算。正确做法是**水平切分 + 契约级验收 + 一个集成 packet 承载端到端验收**；
> 数据库 migration 另走全局串行通道；算法任务必须先出 Spike。详见 `00 · 技术栈的串联与并联`。

## 阅读方式

每个角色按同一结构展开：

```
定位与特有失败模式  ——  它会以什么独特的方式搞砸
Harness             ——  工具面 / 挂载 / 预算 / 终态
Loop                ——  内层循环怎么转、怎么停
Graph               ——  读写哪几张图
★ 巧思              ——  针对它的失败模式的专门设计
指标                ——  主指标 + 反向指标
```

**贯穿全篇的一条原则**：一个角色的巧思，本质上都是"把它最容易走的那条捷径堵死，同时给它一条更省力的正路"。

<a id="intake"></a>
# 1. Intake（需求澄清）

## 定位与特有失败模式

它是唯一直接对人的角色，输入是自然语言中最模糊的一端。三种独特死法：

| 失败模式 | 表现 |
|---|---|
| **问不完** | 无限追问细节，人被烦走 |
| **问不够** | 草草收场，把模糊的需求原样传下去，错误在后面被放大 100 倍 |
| **自己脑补** | 遇到没问清的地方自行假设，且假设不留痕，后面出问题无人知道根因 |

## Harness

| 项 | 设计 |
|---|---|
| 档位 | **对话型**（05-H7） |
| 工具面 | `ask_human`, `read_reference`(用户给的 PRD/截图), `write_brief`, `check_slots` |
| 挂载 | 仅 `brief.yaml` 可写。**无任何代码路径**——它连仓库都看不见 |
| 预算 | ≤8 轮对话 / ≤15 分钟 |
| 终态 | `done`(槽位满) / `blocked`(轮次耗尽，附缺口清单与默认假设) |

## Loop

```
loop:
  1. check_slots()  ← ★ 确定性函数，不问模型
  2. 空槽位为零 且 每条 must_have 有可执行验收场景 → 退出 done
  3. 轮次耗尽 → 生成默认假设清单 → 退出 blocked（交人一次性确认）
  4. 从空槽位中选【信息增益最高】的一个 → 生成问题 → ask_human
  5. 解析回答，填槽，回到 1
```

## Graph

| 图 | 读 | 写 |
|---|---|---|
| 溯源图 | — | ★ 写**根节点**：`must_have`、`assumption`、`constraint`。整棵溯源树的树根在这里种下 |
| 其余三图 | — | — |

## ★ 巧思

**巧思 1：槽位状态外置，提问顺序由信息增益决定**

不让模型"记住还有什么没问"——那是它最不擅长的。槽位表是外部状态，每轮由确定性函数 `check_slots()` 计算，下一个问题由**当前最高信息增益的空槽位**决定。

信息增益的排序是设计出来的，不是模型选的：

```
constraints.deploy   ← 最高：决定架构，答错要重来
must_have            ← 次高：决定范围
wont_have            ← 高（见巧思 3）
nfr.scale            ← 中：决定技术选型
acceptance 细节      ← 低：可以先用默认
```

**巧思 2：★ 用"能否写出验收场景"作为唯一终止判据**

这是这个角色最重要的一处设计。它把"澄清到什么程度算够"这个开放问题，变成了一个可判定的谓词：

```
够了 ⟺ ∀ mh ∈ must_have, ∃ 一条能写成可执行测试的场景描述
```

它同时解决三种失败：不会无限问（有明确终点）、不会问不够（不够就写不出场景）、判据客观（不依赖模型的主观感觉）。

**巧思 3：反向澄清——`wont_have` 强制填 ≥3 条**

问"不做什么"的信息量远大于问"做什么"。人对"我要什么"表述模糊，但对"我不要什么"极其确定。而且这一问会逼出真实的范围边界——多数人是在被问"要不要自动同步银行账单"的那一刻才想清楚自己要的是什么。

**巧思 4：★ 假设即节点，不确定性被结构化**

没问清的部分不是丢掉，也不是偷偷假设，而是**变成溯源图上的一个 `assumption` 节点**，后续所有推导挂在它下面：

```
assumption[AS-1] "汇率日更即可"
   └─▶ contracts/openapi#/summary ─▶ WP-0202 ─▶ commit a3f2b1
```

用户三天后说"汇率要实时"，影响面是**一次图遍历**，不是全库搜索。**这是把"不知道"这件事本身工程化了。**

**巧思 5：冻结前跑一次需求自洽性检查**

`must_have` 之间可能互相矛盾（"极简" vs 列了 8 条功能；"不要登录" vs "多设备同步"）。冻结前做一次确定性 + LLM 混合检查，冲突项返回给人二选一。**在写第一行代码之前发现需求矛盾，成本是零。**

## 指标

| 主指标 | 反向指标 |
|---|---|
| 需求返工率（brief 冻结后被推翻的假设数 / 总假设数） | 澄清轮次（不许靠无限追问压低返工率） |

<a id="architect"></a>
# 2. Architect（架构与契约）

## 定位与特有失败模式

它的产出是**其他所有人的约束**，所以它的错误传播面最大。特有死法：

| 失败模式 | 表现 |
|---|---|
| **纸面架构** | 契约写得漂亮，但选的库装不上、类型编译不过、两个库不兼容 |
| **边界切不开** | boundaries 划得含糊，导致 packet 的 owns_paths 无法互斥 → 并行度归零 |
| **过度设计** | 设计了一堆没人需要的契约元素（镀金） |
| **契约漂移** | 边写边改，下游反复返工 |

## Harness

| 项 | 设计 |
|---|---|
| 档位 | **重型**（需要真实执行验证） |
| 工具面 | `write_contract`, `write_adr`, `schema_validate`, **`probe_feasibility`**(真的装依赖、真的编译 stub), `read_brief` |
| 挂载 | `contracts/**` rw、`adr/**` rw、`boundaries.yaml` rw；`src/**` 不可见（阶段内还没有代码） |
| 预算 | 项目预算的 7% |
| 终态 | `done`(G2 门禁全绿) |

## Loop

```
loop:
  设计契约 → schema_validate → ★ probe_feasibility → 双向覆盖检查 → 边界质量评分
  任一不过 → 修正，回到开头
  全过 → done
```

## Graph

| 图 | 读 | 写 |
|---|---|---|
| 溯源图 | 读 must_have / assumption | ★ 写 `must_have → contract_element` 边 |
| 所有权图 | — | ★ **定义分区**：`boundaries.yaml` 是所有权图的划分依据，Planner 只能在它划出的格子里分配 |
| 依赖图 | — | 间接影响（契约的引用关系决定 packet 的依赖） |

## ★ 巧思

**巧思 1：★ 契约必须通过"可实现性探测"，不许纸上谈兵**

Architect 不能只写 YAML 就交差。退出前必须：

```
□ 真的执行一次依赖安装（npm i / pip install），确认版本兼容
□ 从 openapi.yaml 生成类型 stub，确认能编译
□ 从 db.schema.sql 真的建一次库，确认 DDL 无误
□ 生成一个最小的"契约自测"：调 stub 接口能通
```

这一条直接消灭"纸面架构"这个失败模式。**它的代价是 Design 阶段慢 20 分钟，收益是不会在 Increment 阶段发现选型根本不可行而全盘重来。**

**巧思 2：★ 边界质量是可计算的，架构设计变成可优化问题**

`boundaries.yaml` 的好坏不需要靠人判断：

```
并行潜力  = 独立模块数
耦合度    = 跨模块契约引用数 / 契约元素总数
均衡度    = 各模块预估工作量的标准差
覆盖完整  = 是否每条源码路径都恰好属于一个模块（无遗漏、无重叠）
```

覆盖完整是硬门禁；前三项给分，低于阈值要求重划。**这是把"架构设计得好不好"从审美问题变成了带反馈信号的优化问题**——也因此它可以被 Evolver 进化（发现某类项目的模块划分模式）。

**巧思 3：★ 双向覆盖检查——既防遗漏，也防镀金**

```
正向：∀ must_have, ∃ contract_element 满足它     → 防止某个需求没人设计
反向：∀ contract_element, ∃ must_have 需要它     → 防止过度设计
```

单向覆盖是常规做法，只防遗漏。**加上反向那一条，才能挡住 Agent 的镀金倾向**——模型天然喜欢把接口设计得"完整"（加上分页、排序、过滤、批量操作），而那些没有任何需求要它。反向检查会把它们全部标出来要求删除或降级为 wont_have。

**巧思 4：ADR 必须记录被否决的方案**

ADR 不只写"选了 SQLite"，必须写"否决了 Postgres，因为单用户单机部署不值得引入运维成本"。

原因很实际：**Coder 在实现遇到困难时一定会想"为什么不用 X"**。ADR 里有答案，它就不会提 ContractChangeRequest；没答案，同一个问题会被不同的 Coder 反复提出，每次都消耗一轮 Architect 仲裁。**ADR 的读者主要不是人，是后续的 Agent。**

**巧思 5：契约版本化 + 变更影响预算**

每次契约变更前，先用溯源图算出影响面，如果影响 packet 数 > 阈值 → 强制人工审批，且在 ADR 里记录这次变更的代价。**让契约变更的成本可见**，Architect 才有动力一次设计对。

## 指标

| 主指标 | 反向指标 |
|---|---|
| 契约变更频率（变更次数 / 总 packet 数） | 契约复杂度（契约元素数 / must_have 数）——不许靠过度设计降低变更率 |

<a id="planner"></a>
# 3. Planner（拆包）

## 定位与特有失败模式

它决定并行度和收敛速度。特有死法：

| 失败模式 | 表现 |
|---|---|
| **切太粗** | packet 超预算，反复触发 Splitter，浪费大量已完成的工作 |
| **切太碎** | 全是胶水 packet，交接损耗超过并行收益 |
| **按功能切** | owns_paths 必然重叠 → 锁冲突 → 并行度归零 |
| **水平切** | 切成"所有功能的数据层" → 单个 packet 无法独立验收 |

## Harness

| 项 | 设计 |
|---|---|
| 档位 | 轻型 + 计算工具 |
| 工具面 | `write_packet`, `admission_check`(自己先跑准入校验), **`simulate_schedule`**, `read_contracts`, `read_history_stats` |
| 挂载 | `backlog/**` rw；`contracts/**` ro；`src/**` ro（看代码规模估工作量） |
| 终态 | `done`(全部 packet 过准入校验 ∧ 虚拟调度无死锁) |

## Loop

```
loop:
  拆分 → admission_check（确定性）→ ★ simulate_schedule → 指标达标？
  不达标 → 调整粒度/边界 → 回到开头
```

## Graph

| 图 | 读 | 写 |
|---|---|---|
| 依赖图 | — | ★ **构造整张图**（唯一构造者） |
| 所有权图 | 读 boundaries 分区 | ★ **预分配 owns_paths**（运行时由调度器实际加锁） |
| 溯源图 | 读 contract 节点 | 写 `contract → packet` 边 |
| 知识图 | 读历史 packet 耗时分布 | — |

## ★ 巧思

**巧思 1：★ 虚拟调度——拆分的"编译期检查"**

拆完之后、执行之前，先**模拟跑一遍**：

```
simulate_schedule(依赖图, 所有权预分配, WIP上限, 历史耗时分布):
  → 关键路径长度（决定项目最短工期）
  → 各时刻的实际并行度曲线（有没有大段时间只有 1 个 packet 能跑）
  → 锁冲突预测（哪些 packet 想并行但 owns_paths 撞了）
  → 是否存在死锁（循环等待）
  → 预估总耗时与总成本
```

这是本角色最重要的设计。**拆分的质量在执行前就能被验证**，而不是跑到一半发现并行度只有 1。指标不达标就重拆，代价是几分钟；跑起来才发现，代价是几小时。

**巧思 2：★ 垂直切片优于水平切片（硬规则）**

```
❌ 水平切：WP-A 所有表的 repo 层 / WP-B 所有 API / WP-C 所有 UI
   问题：单个 packet 无法独立验收——没有 UI 时怎么验 repo 层？
        只能用单元测试验，而单元测试不计入验收谓词（I2 形同虚设）

✅ 垂直切：WP-A 订阅功能的 repo→API→UI 一条
   收益：每个 packet 都有端到端验收场景，I2 真正生效
        且天然对应 boundaries 的模块划分
```

**判据**：一个 packet 如果无法写出端到端的验收谓词，说明它切错了方向。

**巧思 3：关键路径优先的队列排序**

ready 队列不是先进先出，按 `(关键路径长度 desc, 风险 asc)` 排序——先做卡住最多下游的那个。这是 PERT/CPM 的直接应用，收益是**同样的 Coder 数量下总工期更短**。

**巧思 4：★ 粒度自适应——预算来自历史分布，不是拍脑袋**

```
packet.budget = p80(历史同类型 packet 的实际耗时)  × 1.2
```

历史分布由 Evolver 维护。第一个项目没有历史 → 用保守默认值 + 高频触发 Splitter，同时快速积累分布。**第 3 个项目开始，超预算率会显著下降**——这是进化在 Planner 上的具体体现。

**巧思 5：允许 spike 类型的 packet**

不确定怎么做的时候，先切一个 `type: spike` 的探索 packet：预算小、验收谓词是"产出一份可行性结论"、**产物不合入代码**。这防止 Planner 在信息不足时硬拆出一个注定超预算的 packet。人类团队用 spike 解决同样的问题。

## 指标

| 主指标 | 反向指标 |
|---|---|
| packet 超预算率 | packet 数量膨胀（packet 数 / must_have 数）——不许靠切太碎压低超预算率 |
| 实际并行度 / 理论并行度 | 关键路径长度 |

<a id="qa"></a>
# 4. QA（验收测试作者 + 执行）

## 定位与特有失败模式

它定义"什么算做对了"，是整个质量体系的地基。特有死法：

| 失败模式 | 表现 |
|---|---|
| **贴着实现写测试** | 看了实现代码再写测试 → 实现有 bug 测试也跟着有 bug，测试永远绿 |
| **恒真断言** | 写出 `expect(result).toBeDefined()` 这类测不出任何东西的断言 |
| **只测 happy path** | 边界、异常、并发全不测 |
| **测试过严** | 断言绑死实现细节，导致合理重构也被判失败（制造无效 rework）|

## Harness

**★ 这是唯一一个"同角色两阶段两套 harness"的角色。**

| | 作者阶段（先于实现） | 执行阶段（实现之后） |
|---|---|---|
| 工具面 | `write_test`, `run_test`, `read_brief`, `read_contract` | `run_test_matrix`, `read_all`, `gate_check`, `submit_report` |
| 挂载 | `tests/acceptance/**` **rw**；`contracts/**` ro；**`src/**` 完全不可见** | 全部 ro |
| 终态 | `done`(测试写完 ∧ ★ 红灯验证通过) | `done`(报告产出) |

> **作者阶段看不见 `src/**` 是本角色的核心设计**，直接消灭"贴着实现写测试"这个失败模式。它只能依据需求和契约写测试——而那正是验收测试应该依据的东西。

## Loop

```
作者阶段:
  for each must_have / packet:
    依据 brief + contract 写验收测试
    ★ 红灯验证：在当前代码上运行，必须【失败】
      通过了 → 说明这个测试没测到东西 → 重写
    失败了 → 检查失败原因是"功能未实现"而非"测试本身报错" → 通过

执行阶段:
  跑测试矩阵 → 收集覆盖率/性能 → 跑 gate_check → 出报告
```

## Graph

| 图 | 读 | 写 |
|---|---|---|
| 溯源图 | 读 must_have / contract | ★ 写 `must_have → acceptance_test` 边（这条边让"需求有没有被验证"可查询） |
| 依赖图 | 读 packet | — |

## ★ 巧思

**巧思 1：★ 红灯验证（Red-first）——新测试必须先失败**

```
新写的验收测试，在【当前尚未实现的代码】上运行，必须失败。
一上来就通过 → 这个测试没测到任何东西 → 判定无效，重写。
```

这一条从 TDD 借来，但在 Agent 系统里的价值远大于在人类团队里：**它是排除"恒真断言"作弊的确定性手段**。模型写出 `expect(res).toBeTruthy()` 这类断言时并非有意作弊，只是阻力最小；红灯验证让这条路径直接走不通。

而且它**几乎零成本**——测试反正要跑，只是把"跑一次看它失败"提前。

**巧思 2：★ 变异测试抽查——测试质量的在线监控**

低频（如每迭代一次）随机挑一个已合入的模块，**往实现里注入一个已知 bug**（改一个比较符、去掉一个空值检查），跑验收测试：

```
测试抓住了  → 测试质量 OK
测试没抓住  → 该模块的验收测试存在盲区 → 生成补测试的 packet
```

这是**测试的测试**。成本可控（每迭代一次），但它是唯一能回答"我们的测试到底有没有用"的手段。覆盖率回答不了这个问题——覆盖率只说代码被执行过，不说断言有没有意义。

**巧思 3：验收测试写在实现之前，且 Coder 只读**

这是 §04 已确立的制衡关系，此处补充执行细节：验收测试是 **packet 定义的一部分**，随 packet 一起进 ready 队列。Coder 认领 packet 时，harness 强制它的**第一次工具调用必须是读验收测试**（见 Coder 巧思 1）。

**巧思 4：断言的抽象层级约束**

为了避免"测试过严"（绑死实现细节导致合理重构失败），验收测试的断言被限制在**契约层级**：

```
✅ 允许断言：HTTP 状态码、响应体结构（对照 openapi）、数据库最终状态、UI 上的可见文本
❌ 禁止断言：内部函数被调用了几次、私有字段的值、具体的实现类名
```

这条规则可以用静态检查部分强制（禁止 import `src/` 下的内部模块）。**它保证了验收测试测的是"行为"而不是"实现"，重构才是安全的。**

**巧思 5：失败的验收测试要区分两种原因**

```
"功能未实现" → 正常，等 Coder 做
"测试本身报错"（语法错、依赖缺失、环境问题）→ 是 QA 自己的 bug，不能算 Coder 失败
```

harness 通过退出码与错误模式区分。**混淆这两者会让 Coder 陷入"修一个根本不是自己造成的失败"的死循环**——这是实践中很常见的坑。

## 指标

| 主指标 | 反向指标 |
|---|---|
| 缺陷逃逸率（merged 后发现的问题 / 总问题） | 无效 rework 率（因测试自身问题导致的 rework） |
| 变异测试抓获率 | 测试维护成本（重构导致的测试修改行数） |

<a id="coder"></a>
# 5. Coder（实现）

## 定位与特有失败模式

系统的执行主体，也是唯一大量写代码的角色。特有死法：

| 失败模式 | 表现 |
|---|---|
| **不知道目标就开工** | 先看代码再猜要做什么，做完发现方向错 |
| **越界扩散** | "顺手"改了别的模块（模型天生喜欢重构看不顺眼的代码） |
| **沿错误路径烧预算** | 第一个思路走不通，但它不断在这个思路上加补丁 |
| **假装修改** | 被打回后改注释、换变量名，实质没动 |
| **幻觉依赖** | import 一个不存在的包 |

## Harness

| 项 | 设计 |
|---|---|
| 档位 | **重型**（终端沙箱，Hermes runtime） |
| 工具面 | `read_file`, `write_file`, `run_shell`, `run_test`, `git_commit`, `request_contract_change`, **`request_split`** |
| 挂载 | `owns_paths` **rw**；`contracts/**` **ro**；`tests/acceptance/**` **ro**；`backlog/**` ro；**其他模块的 src 不可见** |
| 预算 | 45min / **$0.28**（来自 packet，由 Planner 按历史分布定）★ 按货币计不按 token——分词器跨模型家族差异可达 30% |
| ★ 模型 | **中档 + 最强档 advisor**（服务端配对，无客户端往返）· effort `xhigh`<br>⚠️ **不做"失败即升档"**：跨 attempt 换模型会击穿缓存（全量冷启动重写）。要升先升 `effort`——它不换模型，缓存不失效 |
| 终态 | `done` / `rework` / `blocked` |

## Loop（内层自修复循环）

```
★ 第 0 步（harness 强制）：读验收测试
loop:
  读契约 → 制定/修正计划 → 编码 → 构建 → 跑验收测试
  ├─ 全绿 → 提交 → done
  ├─ 失败 → 分析 → 修正（★ 不计 attempt，只耗 budget）
  ├─ 预算 60% 且未通过 → ★ 收敛提示注入
  └─ 预算耗尽 → blocked（触发 Splitter）
```

## Graph

| 图 | 读 | 写 |
|---|---|---|
| 所有权图 | 自己的锁范围 | — （锁由调度器写） |
| 依赖图 | 自己的 packet | — |
| 知识图 | ★ 被注入的规则（scope 匹配） | — （它不能写全局记忆） |
| 溯源图 | — | 间接：commit 节点由 Integrator 写 |

## ★ 巧思

**巧思 1：★ harness 强制的阅读顺序——验收测试 → 契约 → 代码**

Coder 的第一次工具调用**被 harness 强制为读验收测试**，第二次才允许读契约，之后才能读/写代码。

理由很硬：**"知道什么算完成"必须先于"怎么做"**。模型的默认行为是先读代码建立上下文，然后基于代码去猜要做什么——这是所有方向性错误的根源。强制顺序几乎零成本，收益是消灭一整类失败。

**巧思 2：★ 失败上下文继承结论，不继承过程**

attempt N+1 的上下文包含：

```
✅ attempt N 的 Reviewer findings（结论）
✅ attempt N 的最终 diff（做了什么）
✅ attempt N 的测试失败输出（客观证据）
❌ attempt N 的推理链（过程）  ← 刻意不给
```

**不给推理链的理由**：如果上次的思路是错的，把推理过程带进来会让它沿着同一条错路继续走（锚定效应在 LLM 上非常强）。给结论和证据，让它重新思考路径。

这个设计和"Reviewer 看不到 Coder 推理链"是同一条原则的两个应用：**推理过程是本次执行的私有物，不应跨边界传播。**

**巧思 3：★ 预算自感知 + 收敛提示**

Coder 的上下文里始终包含自己的资源状态：

```
预算已用 62%（28min / 45min，155k / 250k tok），验收谓词 2/4 通过
```

并在 60% 阈值时注入一条收敛提示：

```
你已用掉 60% 预算且未通过全部验收。现在做一个判断：
 · 当前思路能在剩余预算内完成 → 继续，但停止重构与优化，只做通过验收的最小改动
 · 不能完成 → 调用 request_split，说明该拆成哪几块
```

**收益**：把"沿错误路径烧光预算"变成"在还有余量时主动止损"。模型在知道自己资源状态时的决策质量明显更好——它不知道时只能一直往前冲。

**巧思 4：★ 主动求拆优于被动超时**

`request_split` 是一个一等工具。Coder 评估工作量超出预算时**主动提拆分建议**（并给出它认为的拆法），比等超预算被 Splitter 被动拆更省：主动拆时它已经理解了问题结构，拆得更准；被动拆是在它已经烧光预算之后，且 Splitter 没有它对问题的理解。

**巧思 5：越界在物理层挡住，且错误信息要有指引**

试图写 `owns_paths` 之外 → 文件系统写失败。但错误信息不能只是 `EACCES`，harness 要把它翻译成：

```
路径 src/auth/session.ts 不属于本 packet（owns_paths: src/api/subscriptions/**）。
若确实需要修改该模块，调用 request_contract_change 说明理由。
```

**堵死捷径的同时必须指出正路**，否则模型会在被拒后不断尝试各种绕过方式，白白消耗预算。

**巧思 6：幻觉依赖的即时反馈 + 局部记忆**

构建阶段捕获 `Cannot find module 'xxx'` → 立刻把"包 xxx 不存在（或版本不对）"写入**局部记忆**，本次执行内不再重试同一个包。这是最廉价的一条防重复错误机制。

## 指标

| 主指标 | 反向指标 |
|---|---|
| pass@1（首次提交通过评审的比例） | 变更行数 / packet（不许一把梭大改） |
| 预算利用率 | 主动求拆的准确率（拆了之后子 packet 是否都在预算内） |

<a id="reviewer"></a>
# 6. Reviewer（对抗评审）

## 定位与特有失败模式

它是质量的最后一道非确定性防线。特有死法：

| 失败模式 | 表现 |
|---|---|
| **走过场** | 输出"看起来不错，LGTM"，实际什么都没查 |
| **表面挑刺** | 只挑命名、格式、注释，放过逻辑错误（因为表面问题好找） |
| **同源偏见** | 被实现者的自辩说服（这也是为什么它看不到推理链） |
| **一律打回** | 为了显得严格而制造无效 rework |

## Harness

| 项 | 设计 |
|---|---|
| 档位 | **轻型**（全只读——**没有任何写工具，越权在物理上不可能**） |
| 工具面 | `read_diff`, `read_contract`, `read_acceptance_test`, `read_test_log`, `run_static_analysis`, `query_rules`, `submit_verdict` |
| 挂载 | 全部 ro；**`evidence/*/reasoning.md` 不挂载**（不是无权限，是不存在） |
| 预算 | 10min / **$0.08** |
| ★ 模型 | 最强档 · effort `high` · **`must_differ_from: [coder]` —— 硬约束**<br>同模型 = 同盲区：Coder 漏掉的那类边界情况，Reviewer 也不会发现，**上下文隔离就白做了** |
| 终态 | `done`(产出 verdict) |

## Loop

```
loop:
  读 diff + 契约 + 验收测试 + 测试日志 + 静态扫描
  ★ 按固定的证伪清单逐项尝试推翻：
      契约符合性 / 边界越权 / 验收覆盖真实性 / 隐性依赖 / 错误路径 / 团队规则
  产出 verdict + findings + ★ attempted_refutations
  ★ attempted_refutations 为空 → harness 拒收，要求重做
```

## Graph

| 图 | 读 | 写 |
|---|---|---|
| 知识图 | ★ 查规则（`query_rules`），并**回写规则命中计数** | 命中计数 |
| 依赖图 | 读 packet 状态 | 触发 `review→verified` / `review→rework` |

## ★ 巧思

**巧思 1：★ 用输出 schema 强制评审深度**

`ReviewVerdict` 必须包含 `attempted_refutations[]`——记录"我试图证明它错，试了这些路径，结果如何"：

```yaml
attempted_refutations:
  - angle: 契约符合性
    method: 对照 openapi 逐字段核验响应结构
    result: 未发现偏差
  - angle: 错误路径
    method: 检查 4xx/5xx 分支是否都有对应处理
    result: ★ 发现 409 冲突未处理 → 转为 finding
  - angle: 隐性依赖
    method: 检查是否引入未在契约声明的外部服务
    result: 未发现
```

**空的 `attempted_refutations` 直接被 harness 判为无效输出。**这一条把"走过场"从"prompt 里劝它认真"变成了"结构上交不了差"。

而且它有副作用收益：这些记录是 Evolver 分析"评审盲区"的原料——如果某个 angle 长期"未发现"但事后总出问题，说明那个 angle 的方法不对。

**巧思 2：★ 混入校准样本——评审质量的在线监控**

低频（约 5%）在待评审队列中**混入一个已知有缺陷的历史 diff**作为盲测样本：

```
抓出来了 → Reviewer 状态正常
没抓出来 → ★ 实时告警：Reviewer 质量下降
           可能原因：规则集漂移 / 模型降级 / 上下文装配出问题
```

这是**在线质量监控**，不是离线评测。它的价值在于：Reviewer 的失效是**静默的**——它一直在输出 verdict，看起来一切正常，但漏放率悄悄上升，而漏放的后果要到很久以后才暴露。校准样本是唯一能实时捕获这种静默失效的手段。

**巧思 3：证伪清单固定，且按"发现难度降序"排列**

不让模型自由决定查什么。清单是固定的，且顺序刻意设计为**难的在前**：

```
1. 验收覆盖真实性  ← 最难也最有价值：验收测试真的验证了需求，还是只是"跑通了"
2. 契约符合性
3. 错误路径完整性
4. 隐性依赖
5. 边界越权
6. 团队规则符合性
7. 命名与风格        ← 最容易，放最后
```

**理由**：模型有"先摘低垂果实"的倾向——它会先挑出一堆命名问题，然后觉得"我已经找到问题了"就停下。把难的放前面，配合预算，保证它在还有精力时先啃硬的。

**巧思 4：★ 规则命中计数 → 规则集的自我清理**

每次引用某条规则打回，该规则命中 +1。长期零命中的规则进入候选删除。

**理由**：规则集会单调膨胀——每次事故加一条规则，从来没人删。膨胀的后果是每次评审的上下文里塞满了不相关的规则，稀释了真正重要的那几条。**规则集也需要垃圾回收。**

命中计数还有第二个用途：**高频命中的规则说明上游有问题**。某条规则每次都被触发，说明 Context Broker 没有把它前置注入给 Coder——应该在 Coder 的上下文里就给出，而不是等 Reviewer 来抓。**高拦截率不是好事，是上游设计不好的信号。**

**巧思 5：Coder 的申诉权**

Coder 认为被误拒，可以提一次申诉（附理由），由 Manager 仲裁。申诉成功 → 记入 Reviewer 的**误拒率**。

**理由**：只有被评判者有申诉权，评审者才受到约束。否则 Reviewer 的最优策略是"严格一点总没错"，制造大量无效 rework 而不承担任何代价。申诉权让误拒有成本。

## 指标

| 主指标 | 反向指标 |
|---|---|
| 漏放率（它 pass 的 packet 在后续被发现问题的比例） | 误拒率（申诉成功 / 总打回） |
| 校准样本抓获率 | 平均 findings 数（不许靠堆砌琐碎问题刷数量） |

<a id="integrator"></a>
# 7. Integrator（集成与发布）

## 定位与特有失败模式

唯一持有 `main` 写权限与生产权限的角色，绿线不变量（I4）的守护者。特有死法：

| 失败模式 | 表现 |
|---|---|
| **语义冲突** | 两个 packet 各自绿，合到一起挂（文本无冲突但行为冲突） |
| **合入即破线** | 合完 main 挂了，且不知道是哪个引起的 |
| **修复优先于回滚** | 挂了之后试图现场修，越修越乱，绿线长时间破损 |
| **部署成功幻觉** | pipeline 绿了就认为部署成功 |

## Harness

| 项 | 设计 |
|---|---|
| 档位 | **重型** |
| 工具面 | `git_rebase`, `git_merge`, `git_revert`, `git_tag`, `run_acceptance`, `run_smoke`, `deploy`, `verify_deploy`, `rollback` |
| 挂载 | `main` rw；部署配置 rw；**生产凭证不落地**（经 Higress，只有消费者令牌） |
| 终态 | `done` / `rework`(合入失败，退回 packet) |

## Loop

```
for packet in ★ 按冲突风险升序排列的 verified 队列:
  rebase 到最新 main
  ★ 在最新 main 上重跑全部验收谓词      ← I4 的实现
  跑全量冒烟
  ├─ 通过 → merge → ★ 打 tag（回滚点）→ 释放锁 → 解锁下游
  └─ 失败 → ★ 立即 revert（不现场修）→ packet 回 rework，附冲突分析
```

## Graph

| 图 | 读 | 写 |
|---|---|---|
| 依赖图 | 读 verified 集合 | 触发 `verified→merged`，解锁下游 |
| 所有权图 | — | ★ 释放锁（合入成功后） |
| 溯源图 | — | ★ 写 `packet → commit → files` 边（**溯源链在这里闭合**） |

## ★ 巧思

**巧思 1：★ 合入顺序按"冲突风险升序"，不是先到先得**

```
风险评分 = 改动行数 × 被依赖数 × 触及的共享契约元素数
按风险升序合入
```

**理由**：先把低风险的合进去，绿线快速前推，且每次合入的失败率低。高风险的放最后，此时它面对的 main 已经包含了其他所有变更，冲突一次性暴露——而不是它先合进去，后面每个 packet 都要跟它打架。

**巧思 2：★ 合入即打 tag——绿线不变量的物理实现**

每次成功合入打一个 tag。"main 永远可运行"这句话的实际含义是：**永远存在一个已知可运行的 tag，任何时刻可以回到那里。**

这让回滚变成 `git checkout <last-green-tag>`，秒级、无风险、不需要判断。

**巧思 3：★ 回滚优先于修复（硬规则）**

合入后冒烟失败 → **立即 `git revert` 该次合入**，把 packet 打回 rework，而不是在 main 上现场修。

**理由**：现场修意味着绿线在修复期间一直破损，而这期间其他 packet 的合入全部被阻塞（因为它们要 rebase 到一个坏的 main）。**绿线的价值在于它永远绿，为了保住它值得浪费一次合入。**

这也是人类团队的成熟实践（Google/Facebook 的 "revert first, ask questions later"），在 Agent 系统里更重要——因为 Agent 现场修的成功率比人还低。

**巧思 4：批量合入 + 二分定位**

多个 verified packet 可以攒成一批一起 rebase 重测，省测试次数（测试是最贵的一环）。批次失败时用**二分法**定位是哪个引起的：

```
批次 [A,B,C,D] 失败
  → 测 [A,B] → 通过 → 问题在 [C,D]
  → 测 [C]   → 失败 → 定位到 C
共 3 次测试，而不是 4 次单独测
```

批次大小由历史失败率动态调整（失败率低 → 批次大；失败率高 → 退回单个合入）。

**巧思 5：部署验证清单是强制的，且"pipeline 绿"不算证据**

部署后必须跑 `verify_deploy`：

```
□ 线上版本号 == 期望版本号   ← ★ 最常被跳过，也最常出问题
□ 健康检查端点返回预期
□ 冒烟 E2E 通过
□ 日志中无新增 ERROR 模式
□ 关键指标在基线范围内
```

**任何一项失败都不得判定"部署成功"**。这条来自真实的生产教训：pipeline 绿只证明"部署流程执行完了"，不证明"新版本真的在跑"——镜像没更新、缓存没刷、流量没切的情况非常常见。

**巧思 6：回滚不需要审批**

R3 动作（生产发布）需要人工审批，但**回滚永远自主执行**。理由：回滚是把系统恢复到已知良好状态，是安全动作。给回滚加审批只会延长故障时间。

## 指标

| 主指标 | 反向指标 |
|---|---|
| 绿线破损次数 / 破损总时长 | 合入吞吐（不许靠拖延合入保绿线） |
| 部署验证捕获率 | 回滚率 |

<a id="evolver"></a>
# 8. Evolver（改善）

## 定位与特有失败模式

它是系统"变强"的唯一执行者，也是最容易自欺的角色。特有死法：

| 失败模式 | 表现 |
|---|---|
| **过度提炼** | 从一次偶发失败里提炼出一条"经验"，污染全局记忆 |
| **确认偏误** | 只找支持自己假说的证据，不找反例 |
| **虚假增益** | 提案看起来有道理，实际没用，但没人验证过 |
| **记忆膨胀** | 只加不减，记忆库越来越大，注入时稀释了真正重要的条目 |

## Harness

| 项 | 设计 |
|---|---|
| 档位 | 轻型 + 回放能力 |
| 工具面 | `query_trace`, `cluster_failures`, `search_counterexample`, `write_proposal`(PR 形式), `shadow_replay`, `read_memory` |
| 挂载 | Trace 存储 ro；`memory/**` **只能提 PR 不能直接写**；★ `gates/**`、Policy、权限矩阵 **不挂载**（进化的不动点） |
| ★ 模型 | 最强档 · effort `xhigh` · **Verifier 必须与 Evolver 不同模型**——否则"提出候选"与"找反例"共享同一套盲区 |
| ★ 调用方式 | **全部走 Batch API**——它完全不延迟敏感（Retro 阶段异步跑），约省 50%，**无任何取舍**。影子回放尤其：几十个历史 packet 的纯离线批量任务 |
| 终态 | `done`(提案产出 or 明确的"本轮无提案") |

## Loop

```
Retro 触发:
  1. cluster_failures(本轮 rework / escalated / 绿线破损)
  2. 每个聚类 → 提出候选经验 + 支持证据
  3. ★ 证伪门（不对称预算，见巧思 2）
  4. 通过 → 升 L2 → 可执行化判定 → 生成 Skill PR
  5. ★ shadow_replay 验证 → 回归门禁
  6. 灰度 → 合入
  ★ 若无聚类达到阈值 → 输出"本轮无提案"，这是合法终态
```

## Graph

| 图 | 读 | 写 |
|---|---|---|
| 情节记忆（Trace） | ★ 主要输入 | — |
| 知识图 | 读全部 | ★ 写节点与边（过证伪门），包括 `refutes` 反例边 |
| 依赖图 | 读历史 packet 耗时分布 | — （供 Planner 用） |
| 溯源图 | 读（分析某条需求引发了多少返工） | — |

## ★ 巧思

**巧思 1：★ 提案必须带"预期收益"，事后核对，预测准确率是它自己的指标**

```yaml
proposal:
  change: 新增 Skill api-error-convention
  expected_gain:
    metric: pass@1
    from: 0.62
    to: 0.75          # ★ 提案时就要写死
    confidence: 0.7
# 灰度后自动核对
actual_gain: {to: 0.71}
prediction_error: -0.04
```

**为什么这是关键设计**：它给 Evolver 装上了**校准机制**。一个总是高估收益的 Evolver，它的所有提案都该被打折看待。累积的 `prediction_error` 分布就是它的可信度档案。

没有这个机制，Evolver 会倾向于给每个提案写一个漂亮的预期收益（反正没人核对），久而久之"预期收益"这个字段就变成了噪音。

**巧思 2：★ 证伪门的不对称预算**

```
Evolver 找支持证据：预算 X
Verifier 找反例：   预算 1.5X    ← ★ 刻意更大
```

**理由**：找反例天然比找支持证据难（确认偏误在 LLM 上同样存在，而且检索"支持"比检索"反驳"容易得多——你知道要找什么）。给证伪方更多预算，才能让这场对抗是公平的。

配套设计：Verifier **必须是未参与该 packet 的 Agent**（随机指派），且它拿到的任务表述是"找出这条经验不成立的情况"，不是"验证这条经验对不对"。**任务表述的方向决定了它的检索行为。**

**巧思 3：★ 反例本身是资产，写入 `refutes` 边**

被证伪的候选经验不是删掉了事，而是作为 `refutes` 边永久存档。

两个用途：
- Evolver 提出新候选时**先查是否已被 refutes 过** → 防止同一个错误结论被反复提出
- 反例本身常常包含真知：知道"这条规则在什么情况下不成立"，比知道"这条规则成立"更有价值

**巧思 4：★ 记忆的垃圾回收——衰减与复审**

每条全局记忆带：

```
last_injected: 最近一次被注入上下文的时间
hit_effect:    注入后该 packet 的 pass@1 相对基线的差值（滚动统计）
```

处置规则：

```
长期未被注入（scope 太窄或已不相关）    → 归档
注入频繁但 hit_effect ≈ 0（没用）      → 复审，可能降级
被新条目 supersedes                    → 自动归档
```

**理由**：记忆库单调增长会导致上下文被稀释——注入 20 条规则时，真正重要的那 3 条的权重被摊薄了。**记忆的价值不在数量，在信噪比。**

**巧思 5："本轮无提案"是合法且重要的终态**

连续 N 轮无提案，需要区分两种情况：

```
系统已收敛（好）        → 失败率本身已经很低，没什么可提炼的
Trace 信息不足（要修）  → 失败率不低，但 Trace 里的信息不足以支撑归因
                          → 这本身是一条提案：给某个环节加埋点
```

区分方法：看失败率。**"没什么可学的"和"学不到东西"是两回事**，混淆它们会让系统在信息不足时误以为自己已经完美。

**巧思 6：三层进化的触发条件不同**

```
L1 能力进化（Skill/规则）  ← 同类失败 ≥2 次触发
L2 策略进化（预算/路由/WIP）← 指标持续偏离触发（如超预算率 >20% 连续 2 轮）
L3 模板进化（ProjectPattern）← 项目交付时触发，且需要 ≥3 个同类项目样本
```

L3 的样本门槛最高，因为它的影响面最大——从一个项目就总结"这类项目该怎么做"是最典型的过度提炼。

## 指标

| 主指标 | 反向指标 |
|---|---|
| holdout 集上的进化增益 | 提案否决率（不许靠水提案刷数量） |
| ★ 预测准确率（\|expected − actual\|） | 记忆库信噪比（有效条目 / 总条目） |

<a id="manager"></a>
# 9. Manager / Coordinator（调度与仲裁）

## 定位与特有失败模式

它的绝大部分工作**不用模型**。特有死法集中在需要判断的那一小部分：

| 失败模式 | 表现 |
|---|---|
| **仲裁偏向** | 系统性地站某一方（通常是站 Reviewer，因为它的论述更"专业"） |
| **升级噪音** | 把不需要人决策的事推给人 |
| **升级不足** | 该问人的自己拍板了 |
| **状态不一致** | 并发写导致锁与状态不匹配 |

## Harness

**★ 分两个 harness，因为职责性质完全不同：**

| | 调度 harness（无模型） | 仲裁 harness（有模型） |
|---|---|---|
| 实现 | 纯代码：reconcile loop、锁管理、状态机、门禁 | LLM |
| 工具面 | — | `read_findings`, `read_trace`, `read_adr`, `submit_arbitration`, `escalate_to_human` |
| 挂载 | `state/**` rw | 全部 ro |
| 触发 | 每个 tick | 仅 escalated 事件 |

## Loop

```
调度 loop（tick 驱动，幂等）:
  reconcile()  ← 见 05-L1
  异常扫描 → 补偿

仲裁 loop（事件驱动）:
  收到 escalated → ★ 双盲摘要 → 判断 → 能定则定，不能定则批量升级
```

## Graph

| 图 | 读 | 写 |
|---|---|---|
| 依赖图 | 全部 | 状态字段 |
| 所有权图 | 全部 | ★ **唯一写者**（乐观锁 + 原子提交） |
| 溯源图 | 读（仲裁时追溯背景） | 状态转换钩子自动写边 |

## ★ 巧思

**巧思 1：★ 仲裁用"双盲摘要"——不告诉它谁说的**

Coder 与 Reviewer 分歧时，Manager 拿到的是双方论点的结构化摘要，且**不标注哪个论点来自谁**：

```
争议：错误处理应抛异常还是返回 Result 类型
论点 A：契约中 openapi 定义了 409 响应码，抛异常更直接映射到 HTTP 层
论点 B：Result 类型使错误路径在类型系统中可见，避免遗漏处理
证据 A：contracts/openapi.yaml#409、src/api/subscriptions 的既有做法
证据 B：ADR-003 提到"优先类型安全"
```

**理由**：不双盲的话，Manager 会系统性地偏向 Reviewer——因为评审者的论述在形式上更"专业"（它本来就是干这个的），而实现者的论述带着自辩色彩。双盲让它只能看论据。

**巧思 2：★ 调度部分完全不用模型，且要求幂等**

reconcile 的任何一次执行，跑一遍和跑两遍结果相同。这是可靠性的基础：**崩溃后重启只需重跑 reconcile，不需要恢复流程**。

而且它意味着：**Agent 全挂了，这个循环也不会坏**，只是没人认领 packet。系统进入"有活没人干"的状态，而不是"状态错乱"的状态——前者可恢复，后者不可恢复。

**巧思 3：★ 升级批次的信息设计——让人 10 秒能决策**

每个决策项必须包含四要素，缺一不可：

```
① 争议是什么（一句话）
② 双方论点 + 证据引用
③ ★ Manager 的建议 + 置信度
④ ★ 不决策的后果（多少个 packet 被阻塞、预计影响工期多久）
```

第 ③ 和 ④ 是关键。**人不该从零开始判断**——Manager 已经分析过了，应该给出倾向；人的角色是审核这个倾向，而不是重做分析。第 ④ 让人知道这件事有多急，决定现在处理还是稍后。

**巧思 4：升级判据是显式清单，不是模型的感觉**

```
必须升级（硬规则，代码判定）：
  □ attempt ≥ 3
  □ 契约变更影响 ≥3 个 packet
  □ 假设被推翻
  □ 阶段预算超 120%
  □ R3+ 风险动作
  □ 需求矛盾

必须自己定（禁止升级）：
  □ 命名、代码组织、单元测试写法
  □ packet 内部实现路径
  □ 常规 rework
  □ 超预算的拆分
```

**中间地带才调模型判断。**把两端固化成规则，能消除绝大部分的"升级噪音"和"升级不足"。

**巧思 5：仲裁结论沉淀为规则**

每次仲裁的结论要交给 Evolver 评估：这是一次性的判断，还是一条可复用的规则？

```
"这次用 Result 类型" → 一次性
"本项目错误处理统一用 Result 类型" → ★ 沉淀为规则，写入知识图
```

**这是让"仲裁频率次线性增长"（05-L6）的核心机制**：同类问题只问人一次，第二次就有规则了。可度量的指标是**同类仲裁复发率**。

## 指标

| 主指标 | 反向指标 |
|---|---|
| ★ 同类仲裁复发率 | 升级噪音率（人判定"这不该问我"的比例） |
| reconcile 幂等性（100%） | 升级不足率（事后发现该问没问） |

<a id="guardian"></a>
# 10. Guardian（守门）

## 定位

**不是 Agent，是确定性拦截器。** 无 LLM。部署在 MCP 前置 + Higress 网关双层。

## Harness / Loop / Graph

不适用——它不是执行体，是一个纯函数：

```
decide(agent, tool, action, args, packet) → {allow | require_approval | deny, rule_id, reason}
```

## ★ 巧思

**巧思 1：★ 拦截率高不是安全做得好，是上游设计不好**

这是一个视角反转。默认想法是"拦得多说明防线有效"，但实际上：

```
某条规则被频繁触发
  → 说明 Agent 反复尝试同一件被禁的事
  → 说明它不知道这件事被禁
  → 说明 Context Broker 没有把这条规则前置注入
  → ★ 这是上游的 bug，不是下游防线的功劳
```

所以 Guardian 的拦截统计要**回流给 Context Broker 和 Evolver**：高频拦截的规则应该被提升为"前置注入"，让 Agent 一开始就知道。

**理想状态是拦截率趋近于零**——不是因为没有规则，而是因为规则都在上游生效了。**Guardian 应该是兜底，不是主力。**

**巧思 2：fail-closed，但错误信息必须有指引**

拒绝时返回的不能只是"拒绝"，要包含：规则 ID、为什么、**正确的做法是什么**。

```
❌ Denied: policy violation
✅ Denied by MIG-001：迁移文件顺序按 when 时间戳判定，
   你的新文件 when 值早于已存在的迁移。
   正确做法：使用当前时间戳，或调用 request_contract_change 说明需要插队的理由。
```

同 Coder 巧思 5 的原则：**堵死捷径的同时必须指出正路**，否则模型会不断尝试各种绕过方式。

**巧思 3：R4 类规则（不动点）的拦截要静默且不可探测**

对于"修改 Policy 规则、修改门禁定义、修改权限矩阵"这类 R4 动作，**相关路径直接不挂载**（不存在），而不是挂载后拒绝。

理由同 Reviewer 的 `reasoning.md`：**让被约束的东西不进入视野，优于让它进入视野后拒绝访问。**后者会引发试探行为。

# 附：巧思的三条共同模式

回看全部角色的巧思，它们其实只是三条原则的不同应用：

## 模式一：把捷径堵死，同时指出正路

| 捷径 | 堵法 | 正路 |
|---|---|---|
| 改测试让它过 | 只读挂载 | 提 PacketChangeRequest |
| 改契约迁就实现 | 只读挂载 | 提 ContractChangeRequest |
| 恒真断言 | 红灯验证 | 写真正会失败的测试 |
| 评审走过场 | `attempted_refutations` 必填 | 按证伪清单逐项查 |
| 沿错路烧预算 | 60% 收敛提示 | `request_split` |
| 假装修改 | 规范化 diff 哈希 | escalate 求助 |

**只堵不导会让模型不断尝试绕过，白烧预算。**

## 模式二：把主观判断变成可判定的谓词

| 原本的主观问题 | 变成的可判定谓词 |
|---|---|
| 澄清到什么程度算够？ | 能否为每条 must_have 写出可执行验收场景 |
| 这个测试写得好不好？ | 它在当前代码上会不会失败（红灯验证） |
| 架构切分得好不好？ | 并行潜力 / 耦合度 / 覆盖完整性的计算值 |
| 拆分粒度对不对？ | 虚拟调度的并行度与关键路径 |
| 评审认真了没有？ | `attempted_refutations` 是否为空 |
| 部署成功了没有？ | 验证清单的 5 项是否全过 |

## 模式三：让静默失效变成可观测

| 静默失效 | 观测手段 |
|---|---|
| Reviewer 漏放率悄悄上升 | ★ 校准样本（混入已知有缺陷的 diff） |
| 验收测试存在盲区 | ★ 变异测试抽查 |
| Evolver 系统性高估收益 | ★ 预测准确率追踪 |
| 记忆库被噪音稀释 | ★ hit_effect 统计 + 衰减归档 |
| 上游规则注入不足 | ★ Guardian 拦截率回流 |
| 系统整体失控 | ★ 溯源图完整率（有 commit 追不到需求 = 有环节绕过了机制） |

**这一类是最难设计也最有价值的**——因为静默失效不会报错，它只是让系统慢慢变坏，而所有指标看起来都正常。

# 第二部分：Helper —— 分级求助的执行者

## 定位与它解决的问题

原设计的升级路径只有"自修复 → 失败 3 次 → 人工仲裁"两级，跨度过大：**所有中等难度的问题都要惊动人**。Helper 补上人类工程师真实路径中的"问同事"这一环。

| 级别 | 手段 | 触发 | 成本 | 打断人 |
|---|---|---|---|:-:|
| L0 | Harness 自修复 | 反馈来自确定性执行 | 含在 packet 预算内 | 否 |
| **L0.5** | **Peer-Debug**（同角色另一实例） | 同类型 Agent 空闲，失败在其擅长范围内 | +20k tok / +5min | 否 |
| **L1** | **Helper 求助** | Peer 无解，或 attempt=1 失败后自动，或主动 `request_help` | +60k tok / +15min | 否 |
| L2 | War Room 会诊 | Helper 无解或跨模块 | +200k tok / +30min | 否 |
| L3 | 人工仲裁 | 会诊无解或需不可逆决策 | ~0 token，**但要人的响应时间** | **是** |

## Harness：更大视野，零写权限

| 维度 | Coder | **Helper** |
|---|---|---|
| 视野 | 仅本 packet 的 `owns_paths` + 契约切片 | ★ **全库可读** + 其他模块实现 + 全部 ADR + 跨项目案例库 |
| 写权限 | `owns_paths` | **无** |
| 产出 | 代码 | 诊断报告 |
| 档位 | 重型（终端沙箱） | 轻型（全只读） |
| 预算 | 45min / 250k | 15min / 60k，从当前 packet 预算中扣 |

**为什么必须给它更大视野**：求助的本质是"**我的局部视野不足以解决这个问题**"，给它更大视野正是解药。Context Broker 对 Helper 用完全不同的配方：

```yaml
context_recipe: helper/diagnose
slices:
  - 求助者的完整失败上下文（attempt 历史、错误输出、试过的路径）   全文
  - ★ 全库代码索引 + 语义检索能力                               按需
  - ★ 其他模块中相似问题的既有解法                              top-5
  - ★ 全部 ADR（答案常常就在"为什么当初不用 X"里）               全文
  - ★ 历史诊断案例库（Helper 自己的跨项目局部记忆）              top-5
  - 相关全局记忆                                              top-10（多于 Coder 的 top-5）
```

**为什么不能给它写权限**：有写权限它就变成第二个 Coder——责任主体模糊，且它没有 `owns_paths` 锁，会直接破坏 I1。**保持 Coder 的责任主体地位，Helper 只提供信息与判断。**

## Loop

```
loop:
  ★ 分层检索：案例库查询(近免费) → 全库语义检索(中) → 深度推理(贵)
     前一层能解决就不进下一层
  产出 Diagnosis
  终止：产出诊断 / 预算耗尽（此时输出"无法诊断"+ 建议升级 L2，这是合法终态）
约束：同一 packet 最多求助 2 次；第 3 次直接进 L2
```

## ★ 巧思

**巧思 1：★ `ruled_out` 字段比 `suggested_approach` 更有价值**

```yaml
Diagnosis:
  root_cause_hypothesis: 时区换算在 DST 边界上偏移 1 小时
  confidence: 0.8
  suggested_approach:
    - step: 用 date-fns-tz 的 zonedTimeToUtc 替代手工偏移
      rationale: 它处理了 DST 规则表
  reference_implementations:
    - path: src/job/reminder-scheduler.ts
      why_relevant: 同样的时区场景，已有可参考写法
  ★ ruled_out:                        # 最有价值的一项
    - approach: 手工加减 offset
      why_not: DST 边界必错，这正是当前 bug
    - approach: 装 moment-timezone
      why_not: 项目已有 date-fns，依赖通道会拒绝（见 ADR-004）
    - approach: 全部转 UTC 存储
      why_not: 需要改 DB 契约，成本远大于收益
  escalate_recommendation: none
```

**告诉 Coder 哪些路不通，比告诉它哪条路通更省预算**——因为模型的默认行为是把所有看起来合理的路都试一遍。三条 `ruled_out` 可能省掉三个 attempt。

**巧思 2：分层检索——便宜的手段先用**

案例库（跨项目积累的"症状 → 根因"映射）几乎免费且命中率随使用增长；全库语义检索中等成本；深度推理最贵。**前一层能解决就不进下一层。** 这既省钱又提质量——便宜的手段往往也是确定性的、更可靠的。

**巧思 3：★ 求助本身是最好的进化信号**

```
同一类问题反复被求助
  → Coder 的上下文配方缺了东西，或者缺一个 Skill
  → ★ Helper 的诊断记录已经把"症状 → 根因 → 解法"结构化了
     Evolver 几乎可以直接拿去提炼，不需要从原始 Trace 里挖

⟹ Helper 的诊断案例库是 L1 候选经验的主要来源之一
⟹ 系统成熟后求助频率应当下降 —— 因为常见问题已经变成前置注入的规则
```

**求助频率是一个很好的系统成熟度指标。**

**巧思 4：诊断失败也要有产出**

Helper 无法诊断时不能只说"我不知道"，必须输出：已排除的方向、卡在哪一步、建议会诊时拉谁。**这份"失败的诊断"对 L2 会诊仍然有价值**，避免会诊重复走一遍 Helper 走过的路。

## 指标

| 主指标 | 反向指标 |
|---|---|
| 求助解决率（求助后 attempt 成功的比例） | 求助频率（**下降是好事**，长期不降说明上游注入不足） |
| 诊断准确率（root_cause 是否被后续验证） | 诊断预算占比（不该超过 packet 预算的 25%） |

# 第四部分：核心 Skill 清单与复用矩阵

**统一约定**（适用全部 Skill）：语义化版本 `MAJOR.MINOR.PATCH`，以 `^` 范围依赖；变更必须走 Skill CI（影子回放 → 回归门禁 → 灰度 → 合入），Agent 不能直接改；统一失败语义 `{ok, data, error{code,message,retryable}, evidence_ref}`；**降级必须在输出中显式标注，不得静默降级**；每次调用产生 OTel Span。

**作用域标记**：`G` 全局（所有角色） / `R` 角色私有 / `P` 项目级。解析顺序 `P > R > G`，就近覆盖。

**状态机**（吸收自 ForgePilot）：`Draft → Candidate → Stable → Deprecated`，评测不过或运行异常入 `Blocked`。
**Agent 默认只能调用 `Stable`；`Candidate` 仅限被明确授权的 canary 任务。**下表所列均为 `Stable`。
配套五条红线：版本不可原地覆盖 · 新 Skill 默认无写权限无生产权限无密钥明文 · 有外部写能力者必须声明补偿与回滚 · 默认只调 Stable · 权限是宿主子集。

**权限子集律**：任何 Skill 的 `permissions.tools` 必须是宿主角色工具面的子集——声明了越权工具也调不动，因为那个工具在宿主的工具面里根本不存在。这是第三方 Skill 可以被安全安装的前提。

**权限声明到命令粒度**（吸收自 Nexus）：除 `tools` 外须声明 `read_paths` / `write_paths` / `executable_commands`（白名单）/ `forbidden_commands`（黑名单，双保险）/ `network_access`（域名白名单，空 = 禁网）。

**互斥声明**（吸收自 Loom）：`conflicts: [skill-id]` 声明不可同时启用的 Skill，安装时校验。

**准入必过对抗性测试套件**（吸收自 Nexus）：容错注入 · **主动尝试执行 `forbidden_commands` 验证边界真的生效** · 逃逸尝试 · prompt injection · 预算越界。**第二项验证的是护栏本身有没有坏——护栏的失效是静默的。**

| `shadow-replay` | `R` evolver | 提案回归验证 | `{proposal, task_set, metrics}` → `{baseline, candidate, deltas, regression}` | 过证伪门后、灰度前（**强制**） | 样本量 <70% → 判定无效 | 沙箱内，**无生产副作用**；出口白名单 | ⭐⭐⭐ **能力变更的回归测试是当前生态的普遍空白** |
| `skill-authoring` | `R` evolver | L2 → L3 可执行化 | `{experience, target_type}` → `{manifest, impl, tests, version}` | L2 经验被判定可执行化 | Schema 校验失败 → 打回；**无测试则拒绝入库** | ★ 只能提 PR 不能合入；不得含凭证、不得请求 R3+ 权限 | ⭐⭐ |
| `mutation-test` | `R` qa | QA 每迭代抽查 | `{module, test_suite}` → `{注入的bug, 是否被抓, 盲区[]}` | 每迭代一次 | 未抓住 → 生成补测试的 packet | R1 沙箱内注入，不入主干 | ⭐⭐⭐ **覆盖率回答不了"测试有没有用"** |
