## 两条时间线

本项目有两条并行的时间线，**产品路线是主线，参赛节点是主线上的检查点**，不是反过来。

```
产品线   P0 骨架 → P1 编制 → P2 闭环 → P3 界面 → P4 进化 → P5 度量 → P6 强化 → P7 产品
                              ▲                   ▲                        ▲
参赛线                     初赛 8.16          复赛 9.3                 决赛 9.22
```

把参赛当主线的后果是：为了 PPT 好看而做一堆演示用的假东西，赛后一行都用不上。**反过来，产品做扎实了，参赛材料是它的副产品。**

## 产品分期与里程碑判据

每一期都有一条**可判定的交付判据**——不是"大概做完了"，而是能演示的一件具体事实。

| 期 | 目标 | 交付判据（可演示的事实） | 预计 |
|---|---|---|---|
| **P0 骨架期** | 控制平面 + WorkPacket + 单角色 | 一个**手工写的** packet 能被认领、执行、验收、合入，全程状态变更在 Git 里可见 | 1–2 周 |
| **P1 编制期** | 5 角色 + 并行 + 契约先行 + 依赖通道 | 3 个 packet **真并行且零冲突**；Skeleton 阶段跑通；一次依赖请求被自动策略正确拦截并给出替代 | 2–3 周 |
| **P2 闭环期** | 全阶段贯通 + Provisioning + 冷启动 | **一句话 → 可交付应用**：含一次性配置收集、生产级测试、打包，冷启动复现测试通过 | 3–4 周 |
| **P3 界面期** | 桌面壳 + 核心视图 + 人类输入通道 | **全程不碰命令行**：在界面里说需求、确认计划书、看甘特与看板、批决策、填表单、拿交付包 | 2–3 周 |
| **P4 进化期** | 钩子 A/B + 记忆注入 | 一条规则**从失败中长出来**并在后续 packet 中生效（可指出是哪三次失败催生了它） | 2 周 |
| **P5 度量期** | 对照实验 + holdout 集 | 进化增益曲线：Evolver 开 vs 关，holdout 集上 pass@1 拉开差距 | 1–2 周 |
| **P6 强化期** | 证伪门 · 影子回放 · Helper/会诊 · 静默失效观测 | 一个坏 Skill 被回归门禁挡住并一键降级；求助频率随迭代下降 | 3–4 周 |
| **P7 产品期** | 安装包 · 自动更新 · Team 模式 · ProjectPattern | 可分发的安装包；同一套控制平面在 Team 模式下跑通 | 4 周+ |

### 三条排序理由

**P3 界面期排在进化之前** —— 桌面软件的形态决定了"看不见"等于"不可用"。一个只能在终端看日志的版本，内部再完善也不是这个产品。

**P2 必须含 Provisioning 与打包** —— "交付"不是"代码写完了"。省掉这一段，做出来的东西没法给任何人用，也就无法验证它是否真的有价值。

**进化（P4–P6）拆成三期而不是一期** —— 进化的三个主张是递进的：能长出经验（P4）→ 能证明变强（P5）→ 变坏能挡住并回滚（P6）。合成一期会导致三件事都做半截。

## MVP 边界（P0–P2 的严格范围）

### 必须有（否则系统跑不通）

```
✓ 四张图的最小实现（依赖图 + 所有权图必须真做；溯源图先用追加式 jsonl；知识图先用文件）
✓ WorkPacket 定义 + 准入校验器（确定性，不用模型）
✓ 不变量 I1 路径锁 / I2 验收谓词 / I3 契约只读挂载 / I6 证据
✓ ★ Git Worktree 双层隔离（Git 原生能力，几乎零成本，应在 P0 就位）
✓ ★ 执行证据包五类产物（diff / 截图+原始日志 / 报告 / 工具调用清单含哈希 / LLM 摘要）
✓ 受控 Harness：上下文装配 + 工具面裁剪 + 预算 + 三种终态 + 证据产出
✓ 5 角色：Designer(Intake+Architect) / Coordinator(Planner+Manager) / Coder×2 / Reviewer / QA
✓ reconcile loop + 拉动式 ready 队列
✓ 契约测试自动生成（mock + 类型 + 一致性测试）—— 前后端并联的前提
✓ 依赖快速通道（自动策略部分即可，人工兜底）
✓ Walking Skeleton 阶段 + 冷启动测试
✓ Provisioning 表单 + 凭证泄漏扫描
✓ 看板视图（静态 HTML 读 state/*.json 即可，成本极低、诊断价值最高）
✓ 预算树（★ 按货币计不按 token）+ 实时成本显示 + 超支即停
✓ ★ 模型路由表（声明能力需求而非模型 ID）+ Coder↔Reviewer 模型隔离检查
✓ ★ Evolver 走 Batch API（省 50%，无取舍——能做就做）
```

### 可以后加

```
- 审计哈希链（初期普通追加日志即可，但 P4 前必须补上）
- Skill 五态状态机（初期只区分 启用/禁用）· 对抗性测试套件
- 检索确定性梯度（初期直接向量 top-k）· 等价契约切换开关
- Peer-Debug（L0.5）· Helper 与 L1 求助（初期 attempt 用尽直接找人）· L2 会诊
- I4 绿线自动化（初期人工确认合入）· I5 自动 Splitter（初期超预算升级到人）
- 证伪门（初期人工确认经验升格）· 影子回放（初期靠人判断 Skill 有没有用）
- 钩子 C 模板化 · Guardian（初期只读挂载 + hook 已够）
- 甘特图与其余七个视图 · 校准样本 · 变异测试 · 溯源图查询
- 多 runtime · 灰度下发 · 消息总线 · Team 模式
```

### 算法类任务的特别说明

若首个验证项目不含算法模块，Spike 机制可延后；**若含，Spike 与评测集必须在 MVP 内**——否则会陷入"反复 rework 但永远达不到效果"的死循环，这是无法靠工程手段绕过的。

### 最小验证目标

> **一句话输入 → 系统自主产出一个能冷启动跑起来、通过全部验收场景的小应用，
> 过程中至少发生一次"从失败中提炼出一条规则，并在后续 packet 中生效"。**

这两件事同时成立，系统的核心主张就被证明了。其余都是工程量。

## 参赛节点

| 阶段 | 截止 | 提交物 | 对应产品期 |
|---|---|---|---|
| **初赛** | 8.16 | 作品简介(≤500字) + 方案 PPT +（可选）代码包 | P0–P1 |
| 初赛评审 | 8.24 | Top30 进复赛 | — |
| **复赛** | 9.3 | 可执行代码包 + 可运行 Demo/视频 | P2 |
| 复赛评审 | 9.10 | Top15 进决赛 | — |
| **决赛** | 9.22 | 路演 PPT + 现场 Demo + 最终仓库 | P3–P4 |

### 红线：仅 PPT 无 PoC 直接淘汰

赛题明确：**仅 PPT / 概念方案、无可验证 PoC / 日志 / 视频，直接淘汰或大幅扣分**。所以初赛的真实目标不是 PPT：

> **一段 3 分钟真实录屏 + 一张真实的对照数据图。PPT 是它俩的说明书，不是主角。**

### 初赛（到 8.16）的收敛目标

只需证明三件事，其余全砍：

1. **≥3 角色的真实研发闭环**跑得起来——有真实 Git 提交、真实测试结果
2. **契约先行的并行是真的**——3 个 packet 同时跑且零冲突，能展示 `locks.json`
3. **约束是结构性的不是提示词**——录到一次 Coder 试图写 `contracts/` 被文件系统拒绝

进化部分初赛**可以只讲设计**（赛题明确初赛重点评估方向与可行性），但上面三条必须是真跑出来的。

### 与 AgentTeams 的关系（参赛必答）

赛题要求以 AgentTeams 为多 Agent 协同设计基点。本项目的位置很清楚：

```
AgentTeams 提供：执行平面（Manager-Workers）+ 通信（Matrix）+ 凭证隔离（Higress）
                 + 共享文件系统 + 多 runtime + 任务重放
本项目补上：    ★ 控制平面 —— 状态图、锁、准入校验、门禁、预算、进化流水线
```

**Team 模式直接跑在 AgentTeams 上**，Solo 模式是同一套控制平面换本地 Worker。这个双模式设计本身就是"框架能力可替换性"的最好论证——评审关注的正是这一点。

## Demo 剧本（3 分钟，录屏用）

### 设计原则

- **不解说架构，只演事情发生**——架构留给 PPT
- 每个镜头都有**真实产物**（真实 commit hash、真实测试输出、真实 locks.json）
- 进化那段用**预跑好的真实数据**，现场只演小闭环——不要赌 3 分钟内跑出进化曲线

### 分镜

```
[0:00-0:20] 说需求
  画面：桌面应用主界面，输入"做一个管理 SaaS 订阅的记账工具"
  → 系统开始提问：部署在哪？需要自动同步银行账单吗？多币种？
  旁白：它会问到能写出验收标准为止，然后停。

[0:20-0:45] ★ 确认开发计划书（第一个高潮）
  画面：完整计划书——3 条 must_have / 4 条不做 / 2 条假设 /
        5 个模块、并行度 3 / 预计 12h / ★ 预计成本 $8.4 / 后期需 2 个 Key + Logo
  → 点"开始"
  旁白：开工前你就知道它要做什么、不做什么、花多久、烧多少钱。

[0:45-1:20] 并行开发
  画面：甘特图三条并行推进 + 看板各列流动 + Agent 状态板预算条
  → 特写 locks.json：三个 packet 各自锁住不相交的路径
  → ⚠ Coder-01 想装 dayjs → 依赖通道拒绝："项目已有 date-fns，参考 src/utils/time.ts"
  旁白：它们不会撞车，因为边界在写第一行代码之前就定死了。

[1:20-1:50] ★ 约束是结构性的（第二个高潮）
  画面：Coder 试图修改 contracts/openapi.yaml → 文件系统写入失败
  → 它转而提交 ContractChangeRequest → Architect 评估 → 变更窗口 → 受影响 packet 冻结重装
  旁白：这不是提示词里写的"请不要修改契约"，是它根本没有写权限。

[1:50-2:20] ★ 一次性填表（第三个高潮）
  画面：配置收集表单弹出 —— 4 项
        · 汇率 API Key（必填，附申请链接 + 免费额度说明 + 为什么需要它）
        · SMTP（可降级 —— 不填就关闭邮件提醒）
        · Logo（附尺寸要求 + 占位图预览）
        · 域名（可选）
  → 填 3 项，跳过域名 → 即时连通性校验通过
  旁白：整个开发过程只打断你这一次。

[2:20-2:45] 交付
  画面：真实凭证跑全量 E2E ✓ → 凭证泄漏扫描 ✓ → 打包 →
        ★ 全新容器冷启动复现测试 ✓ → 交付报告 + KNOWN_ISSUES
  旁白：它自己在一个干净容器里把交付包跑了一遍，才敢说完成。

[2:45-3:00] 它变强了
  画面：进化曲线（预跑数据）——Evolver 开 vs 关，holdout 集 pass@1 拉开
        事件标注：↑ 这里长出了一条规则
  旁白：所有号称自进化的系统都要回答两个问题：进化了没有？坏了怎么办？
        这条曲线是第一个答案。一键降级到上一个 Skill 版本，是第二个。
```

### 录制注意

- **演示用的配置必须是跑过 ≥50 次的那一套**，不要用刚调通的
- 每段预先录好成功片段，剪辑而非直播
- 所有 API Key 界面打码
- 界面截图前清理调试痕迹

## 度量与验收

### 系统级指标

| 指标 | 定义 | 目标 |
|---|---|---|
| pass@1 | 首次提交通过全部必需门禁的比例 | ≥ 70% |
| 人工介入次数 | R3 审批 + 主动打断 + 死循环仲裁，每项目 | ≤ 6 次 |
| 流动效率 | 增值时间 / 总周期时间 | ≥ 40%（人类团队 5–15%） |
| 绿线破损总时长 | main 不可运行的累计时间 | ≤ 5% 项目时长 |
| 并行度利用率 | 实际并行 / 理论并行 | ≥ 70% |
| 冷启动复现成功率 | 一次通过的比例 | 100%（这是门禁不是指标） |
| **进化增益** | 第 N 轮 vs 第 1 轮 pass@1（**holdout 集**） | +10pp 以上 |

### 对照实验的严谨性

```
✅ 同一批任务、同一模型、同一随机种子
✅ 进化增益在 holdout 集上测（该集不参与提案生成）
✅ ★ 每轮跑 3 次取中位数 —— LLM 有方差，单次结果不可信
✅ 报告失败案例，不只报成功率
✅ 数据与脚本可复现
```

> 第 3 条尤其重要：**只跑一次就画曲线，会被懂行的人一句话问倒。**

## 风险与应对

| 风险 | 严重度 | 应对 |
|---|:-:|---|
| **范围过大** | 🔴 | 严格按 MVP 边界；P0–P2 不碰进化，P0–P3 不碰 Team 模式 |
| **桌面壳与 Agent 生态适配成本** | 🔴 | Solo 模式先复用成熟的本地编码 Agent 作为 Worker，**不自研执行体** |
| **两种模式实现分叉** | 🟠 | 四个接口在 P1 就定死；CI 中两模式跑同一套用例 |
| **成本失控（用户直接买单）** | 🔴 | 预算树 + 实时显示 + 超支即停三选一 + 分层路由，**四者都要在 P2 前就位** |
| ★ **降档反而更贵** | 🟠 | 便宜档位的缓存最小长度可能更长——省了单价却整个失去缓存是净亏。降档前核对该模型的缓存门槛；界面在采纳降档建议时强制提示 |
| ★ **模型隔离被无意破坏** | 🟠 | Coder↔Reviewer、Evolver↔Verifier 同模型 = 同盲区。做成**路由表约束 + 界面显式检查器**，不能只写在文档里 |
| ★ **路由变动污染进化度量** | 🟠 | 路由表版本化；**跑对照实验时必须冻结**；路由实验在 holdout 集上做且一次只改一个角色 |
| **凭证安全事故** | 🔴 | 本地加密 + 最小权限提示 + **凭证泄漏扫描作为不可豁免的交付门禁** |
| **契约先行的前期成本** | 🟠 | Design 慢 20 分钟换 Increment 不返工；用 ProjectPattern 摊薄 |
| **并行度实际很低** | 🟠 | 虚拟调度执行前就能发现；长期 ≤2 说明 boundaries 切分方法要改，**不是加 Coder** |
| **进化在小样本上不显著** | 🟠 | 明确 L1/L2/L3 样本门槛；样本不足时"本轮无提案"是合法终态 |
| **参赛时间挤压产品进度** | 🟠 | 参赛材料只用产品已有的真实产出，**不为演示做一次性代码** |

## 选型结论（已定）

`Method/` 下六套并行方案经十二维度横评后定案，详见 `Method/方案横评与选型决策.md`：

```
Codentum 102 / 120   ← 选定为主干
ForgePilot  91       ← 备选；其 3 项机制已吸收
Nexus       82       ← 5 项机制已吸收
DevPlex     75       ← 2 项已吸收，1 项明确否掉
Loom        69       ← 3 项已吸收
AppDevForge 60       ← 2 项已吸收（参赛材料向）
```

**选 Codentum 的三条理由**：唯一有可证伪中心主张的一份 · 唯一让并行度可计算的一份 · 异常路径写得比正常路径厚。

**另外五套不要删**——决赛若被问"考虑过其他架构吗"，六套并行方案 + 一份十二维度横评是很有力的回答，它证明这个选择是**比较出来的**而不是想到的第一个。

## 已定的三项工程决策

| # | 决策 | 结论 | 理由与后续动作 |
|---|---|---|---|
| 1 | 桌面壳选型 | **Electron** | 生态成熟、上手快、一个人能搞定。Tauri 的体积优势要到 P7 产品期才值得，届时再评估迁移成本 |
| 2 | Solo 模式的 Worker | **复用成熟编码 Agent，不自研执行体** | 我们的价值在控制平面。Coder 位通过 `WorkerRuntime` 接口可插拔，P1 就把接口定死 |
| 3 | 首个验证项目 | **全新小应用（订阅记账工具）** | 能完整走通 Greenfield 全流程；交付物可对外展示；无数据披露成本 |

**由此推出的两条工程纪律**：

```
① 四个接口（WorkerRuntime / ArtifactStore / MemoryIndex / ModelGateway）在 P1 定死，
   之后只允许加实现不允许改签名 —— 否则 Solo/Team 双模式必然分叉
② 任何"为了演示"的代码一律不写。Demo 只用产品已有的真实产出
```
