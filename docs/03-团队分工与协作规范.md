# 团队分工与协作规范

> 三人 + Agent 协同开发的组织方案。
> 配套 `00-总体设计方案.md` / `01-角色详细设计与Skill清单.md` / `02-实施路线与交付计划.md`

---

## 一条原则：用系统自己的设计来组织团队

这套系统解决的问题——多个执行体并行改同一个代码库如何不互相踩——**对人和对 Agent 是同一个问题**。所以团队分工直接复用系统的四条设计：

| 系统里的设计 | 团队里的对应 |
|---|---|
| **契约先行**：边界必须先于代码存在 | 第 0 周只定契约不写实现，三人一起做 |
| **路径独占**：`owns_paths` 互不相交 | 每人独占若干目录，合并时结构上无冲突 |
| **制衡关系**：评判标准的制定者 ≠ 被评判的人 | 谁写验收测试 ≠ 谁写实现；谁定契约 ≠ 谁用契约 |
| **爆炸半径决定风险分配** | 分工不按"难度"切，按**出错后的传播范围**切 |

> **这不是比喻。**如果三人各写各的然后集成，会撞上完全相同的合并地狱——那正是这套设计要消灭的东西。

## 三人定位

**分工的依据不是"谁强谁弱"，是错误的爆炸半径。**

| | 队长（A） | 成员 B | 成员 C |
|---|---|---|---|
| **主责** | 控制平面 + 契约 | Harness + 角色实现 | 桌面端 + 交付链路 |
| **本质** | 定规则的人 | 让规则跑起来的人 | 把系统变成产品的人 |
| **爆炸半径** | **最大**——锁判错即数据损坏 | 中——执行错可被打回重试 | **最小**——见下 |
| **验证方式** | 单元测试（确定性代码，好测） | 集成测试 + 真实 packet 跑通 | 视觉 + fixture 快照对比 |
| **能否独立开工** | 是（不依赖别人） | 依赖 contracts | **是**（有 mock 与 golden fixture） |

### 为什么 C 拿桌面端和交付链路

**不是因为它简单，是因为它对系统状态零写权限。**

```
Console 是纯读端 —— 订阅 Git commit 流做投影，对系统状态零写。
Console 挂掉，系统照常运行。
```

这是**架构属性**，写在设计里的（见 `00 · 可视化控制台`）。它意味着：

| 属性 | 对经验较薄的成员意味着什么 |
|---|---|
| **零写权限** | 犯错不会传播。改坏一个视图，控制平面照常跑 |
| **反馈最密集** | 视觉的东西立刻知道对不对，不需要等别人的模块 |
| **可独立开发** | 有 mock 状态和 golden fixture，第一天就能开工，不等 A/B |
| **验收最明确** | "读 `graph.json`，按 status 分组渲染，在快照上截图对得上"——机器可判定 |

**同一个理由也适用于交付链路**（Provisioning 表单、凭证扫描、打包、冷启动测试）：每一项都是自包含的、判定明确的、失败会立刻显形的。

⚠️ **唯一的例外是凭证泄漏扫描**——实现简单（确定性字符串匹配）但后果严重。所以：**C 实现，A 先写验收测试**（同系统里 QA-first 的制衡）。

### 队长的定位：不是写最多代码的人

> **队长最该做的不是产出最多代码，是守住六条不变量。**

具体是三件事：

1. **契约的唯一写者**（同 I3）——`contracts/` 只有你能改，别人要改提 ChangeRequest
2. **不变量的守护者**——每次集成检查 I1/I2/I3/I4/I6 有没有被绕过
3. **集成与仲裁**——每日集成、跨模块冲突裁决、范围决策

写代码当然要写（控制平面是你的），但**如果你成了"谁都在等你合入"的瓶颈，那是分工错了，不是你不够努力**。

## 第 0 周：契约冻结（3–5 天，三人一起，不分头）

> **这一周产出的是契约，不是代码。**
> 跳过这一周直接分头写，三周后集成时会撞上合并地狱——这套系统存在的理由就是消灭那个地狱。

### 交付物

```
□ 目录骨架建好（所有空目录 + README 占位）
□ .codentum/ 的全部 JSON Schema：
    WorkPacket / RoleSpec / ProductBrief / boundaries / graph.json / locks.json / budget.json
□ 四个接口的签名定死：
    WorkerRuntime / ArtifactStore / MemoryIndex / ModelGateway
□ ★ 前端 ↔ 控制平面的数据契约：
    Console 读哪些文件、什么格式、多久刷新一次
□ ★ golden-state 快照：至少 3 个（空项目 / 开发中 / 交付完成）
□ 路径独占表（上表）写进 docs/ 并全员确认
□ 每个 package 的"完成定义"（machine-checkable，不是"做得好"）
```

### 为什么 golden-state 快照必须在第 0 周就有

**它是 C 的解耦点。** 有了它，C 第一天就能开工，不用等 A 的控制平面能跑。这跟系统里"前端依赖 mock 不依赖实现"是同一招——**前后端并联的原则同样适用于人**。

没有它，C 会空等两周，然后在最后一周被压着赶工——这是三人团队最常见的死法。

### 第 0 周的一条纪律

**四个接口签名在第 0 周定死，之后只允许加实现不允许改签名。** 要改必须三人同意并记 ADR。否则 Solo/Team 双模式必然分叉，而且会反复打断另外两人。

## 分阶段任务分配

### P0 骨架期（约 1–2 周）

| | A（队长） | B | C |
|---|---|---|---|
| **主线** | 状态机 + 路径锁 + 准入校验器 | Harness 最小壳：上下文装配 + 三种终态 + 证据产出 | 看板视图 + Agent 状态板（读 golden-state） |
| **判据** | 手工写的 packet 能被认领→执行→验收→合入，状态变更在 Git 可见 | 一次 Coder 执行能产出完整证据目录 | 两个视图在 3 个 golden-state 快照上都渲染正确 |
| **附带** | 写 C 的 secret-scan 验收测试 | Git Worktree 隔离接上 | Electron 壳跑起来 |

### P1 编制期（约 2–3 周）

| | A | B | C |
|---|---|---|---|
| **主线** | 门禁引擎 + 预算树（按货币）+ 依赖快速通道 | 5 角色 RoleSpec + prompt + 工具面派生 | 甘特图 + 成本仪表 + 依赖图视图 |
| **判据** | 3 个 packet 真并行零冲突；一次依赖请求被自动策略拦截并给替代 | 5 角色都能跑完一个 packet | 甘特图上计划/实际双条，偏差可见 |
| **附带** | 契约测试自动生成（mock + 类型 + 一致性） | 模型路由表 + 隔离约束 | Provisioning 表单骨架 |

### P2 闭环期（约 3–4 周）

| | A | B | C |
|---|---|---|---|
| **主线** | Walking Skeleton 阶段 + 阶段门禁贯通 | 分级求助（Helper）+ 契约变更窗口 | **Provisioning 全链路 + 凭证扫描 + 打包 + 冷启动测试** |
| **判据** | 一句话 → 可交付应用 | 一次求助让 attempt 2 成功 | 表单填完 → 生产测试 → 打包 → 新容器冷启动通过 |

### P3 界面期（约 2–3 周）

| | A | B | C |
|---|---|---|---|
| **主线** | 人类输入通道的后端（批量升级、审批） | 溯源图写入 + Trace 接通 | **4 个管理模块 + 4 个交互界面 + 剩余视图** |
| **判据** | 全程不碰命令行 | 任意代码可回溯到需求 | 界面里说需求→确认计划书→看进度→批决策→填表单→拿交付包 |

### P4 之后（进化期）

进化层由 **B 主导**（他最熟 Harness 与 Trace），A 负责不动点的强制（`gates/**`、Policy、RoleSpec 的只读挂载），C 做进化曲线视图与 Skills 面板的待审区。

## C 的任务梯度（由易到难，每项带完成定义）

按这个顺序做，**前两项是"快速赢"**——先建立手感和信心，再上难的。

| # | 任务 | 完成定义（机器可判定） | 难度 |
|---|---|---|:-:|
| 1 | **看板视图** | 读 `state/graph.json`，按 status 分 9 列渲染，每列显示 `当前数/WIP上限`，超限标红。3 个 golden-state 快照渲染结果与预期截图一致 | ⭐ |
| 2 | **Agent 状态板** | 读 `state/agents.json`，卡片显示状态/当前任务/预算条/成功率。预算条 >60% 变黄、>85% 变红 | ⭐ |
| 3 | **Electron 壳** | 窗口、托盘、菜单、路由；`npm run dev` 起得来 | ⭐⭐ |
| 4 | **依赖图视图** | 读 `graph.json` 渲染 DAG，节点按状态着色，关键路径高亮 | ⭐⭐ |
| 5 | **甘特图** | 计划/实际双条并排；依赖箭头；拆分与 rework 标注；点击展开证据 | ⭐⭐⭐ |
| 6 | **成本仪表** | 读 `state/budget.json`，按阶段/角色/模型三维下钻 | ⭐⭐ |
| 7 | **Provisioning 表单** | 从 `provisioning.json` 渲染表单；格式校验；连通性探测；必填未填时阻断 | ⭐⭐⭐ |
| 8 | **凭证泄漏扫描** | 在 A 提供的测试集上：**含凭证的产物必须全部被拦截，不含的不得误报**。⚠ 验收测试由 A 先写 | ⭐⭐⭐ |
| 9 | **冷启动测试脚本** | 全新容器 → clone → 照 README → 起来 → E2E 全绿；失败时输出缺失的隐式依赖清单 | ⭐⭐⭐ |
| 10 | **4 个管理模块** | Skills / MCP / 连接器 / 模型与成本；含模型隔离检查器 | ⭐⭐⭐⭐ |

**每一项都可以在 golden-state 快照上独立验收，不需要控制平面跑起来。**

## 协作规范

### 一、每人一个 git worktree，Agent 只在自己的 worktree 里跑

```
git worktree add ../codentum-a  feat/control-plane
git worktree add ../codentum-b  feat/harness
git worktree add ../codentum-c  feat/desktop
```

**理由和系统里一样**：物理隔离 + 路径独占双层。三个人的 Agent 同时在一个工作区里跑，一定会互相覆盖。

### 二、契约只有 A 能改，别人提 ChangeRequest

改 `packages/contracts/**` 的流程：

```
提 ContractChangeRequest（说清：需要什么 / 为什么现有契约不够 / 建议的最小改动）
  → A 评估
      拒绝 → 说明如何在现有契约下实现（多数情况）
      接受 → ★ 变更窗口：通知受影响的人 → 改 → 记 ADR → 解冻
```

**别人自己改契约，是这个项目最容易出现也最难查的问题。** 它会让另外两人的代码在毫无征兆的情况下失配。

### 三、每日一次集成（绿线不变量的人类版本）

```
每天固定时间（建议下班前）：
  依次 rebase 到 main → 跑契约测试 + 单元测试 → 合入 → 打 tag
  ★ 合入失败立即 revert，不现场修 —— 保住 main 永远可跑
```

**顺序按冲突风险升序**（改动小的先合），跟系统里 Integrator 的规则一样。

### 四、评审关系（复用系统的制衡设计）

```
A 的控制平面  → B 评审      （B 是主要消费者，最容易发现接口不好用）
B 的 Harness  → A 评审      （A 是不变量守护者）
C 的前端      → B 评审      （视觉与交互，B 有余力）
C 的交付链路  → A 评审      ★ 且验收测试由 A 先写（安全关键）
```

**没有人评审自己的代码。** 这条不能因为"赶时间"破例——它是整个质量体系的地基，跟系统里 Coder↔Reviewer 是同一条原则。

### 五、周一定范围，周五砍范围

```
周一：本周做什么 + ★ 本周明确不做什么（≥3 条）
周五：没做完的，明确决定 —— 下周继续 / 砍掉 / 缩小
```

⚠️ **`wont_have` 每周必须写 ≥3 条。写不出来说明这周的边界没想清楚。**

## 给队长的三条提醒

这三条来自 `Codentum设计评价与自我认知报告.md`，在团队场景下更要紧。

### 一、你的缺口识别力会成为团队的范围膨胀源

你最强的能力是**看见缺的那一块**。三人团队里，这会变成"每周给两个人各加两件事"。而**三人 + Agent 移除了"一个人做不完"这堵反馈墙**——膨胀的代价不再自动显现。

**具体做法：把"砍范围"的否决权交给 B。** 你提新方向，B 有权说"这周不行"。不是走形式——是给你的特质装一个外部制动。

### 二、别成为瓶颈

契约在第 0 周冻结之后，你就不该是"谁都在等你"的那个人。如果一周里你被打断超过 5 次去裁决同一类问题，**那说明这类问题该被写成规则，而不是每次都问你**——这正是系统里"仲裁结论沉淀为规则"的机制，对人同样适用。

### 三、C 的"简单任务"不等于"不重要任务"

看板是全系统诊断价值最高的视图；凭证泄漏扫描是不可豁免的交付门禁；冷启动测试是唯一能抓出隐式依赖的手段。

**把这些讲清楚。** 一个知道自己在做关键路径的人，和一个觉得自己在打杂的人，产出差得很远。

## 距初赛的 14 天怎么排（8.02 → 8.16）

参赛是主线上的检查点，不是主线。这 14 天的目标就是 **P0 + 部分 P1**，然后拿真实产出录屏。

| 日期 | A | B | C |
|---|---|---|---|
| 8.02–8.05 | **三人一起：契约冻结周**（目录骨架 / Schema / 四接口 / golden-state 快照 / 路径表） | | |
| 8.06–8.10 | 状态机 + 路径锁 + 准入校验器 | Harness 最小壳 + Worktree 隔离 | 看板 + Agent 状态板 + Electron 壳 |
| 8.11–8.13 | 门禁 + 3 packet 并行跑通 | 5 角色最小版跑通 | 甘特图 + 录屏用界面打磨 |

| 8.15 | 作品简介 + PPT（A 主笔，B/C 补技术细节） | | |
| 8.16 | **缓冲 + 提交**（不要卡最后一天） | | |

### 初赛只需证明三件事

