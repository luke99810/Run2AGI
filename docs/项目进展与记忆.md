## ⚠️ 这份文件的定位：**派生视图，不是真源**

**本文仅供团队协作与进度同步参考。具体改动一律以事实文件为准。**

它是一份**方便人读的摘要**，用来快速恢复上下文、看清现在做到哪儿了。
它会滞后、会遗漏、也可能写错。**当它与事实文件冲突时，事实文件对，本文错。**

### 事实文件分别是哪些

| 你想知道的事 | 唯一真源 | 别看这里 |
|---|---|---|
| 代码实际怎么做的 | **源码与测试** | 本文的描述 |
| 数据长什么形状 | `packages/contracts/schemas/*.json` | 本文，或任何 md |
| 接口签名 | `packages/contracts/python/…/interfaces.py`（手写，非生成物） | 本文 |
| 谁能写哪些路径 | **`boundaries.yaml`** | 本文 §八 的目录树 |
| 角色权限 / 状态转换表 / 工具面 | **RoleSpec**（`packages/roles/**`） | 任何手写的表 |
| 某个决策为什么这么定 | **`docs/adr/`** | 本文的一句话摘要 |
| 到底发生过什么、谁改的 | **`git log`** | 本文的「最近任务」表 |

> ★ 这不是一句免责声明，是把本项目的核心主张用在自己身上：
> **同一件事有两个地方可查，它们迟早会不一致，而不一致时通常不报错。**
> 所以每件事都必须指定唯一真源，其余一律是派生视图 —— 本文就是派生视图。

### 发现不一致时怎么办

**改本文去对齐事实文件，不要改事实文件去迁就本文。**

如果确实是事实文件错了，那就改事实文件 —— 但那是一次真正的变更，
要走它自己的流程（契约走变更窗口、代码过测试与门禁），
而不是先在这里改一笔，让两边看起来一致了事。

### 命名

**Codentum = Code + Momentum**。Code 锚定软件开发赛道；Momentum 传递自驱动、自进化的持续成长势能，暗合多智能体协同的 1+1>2 涌现动力。
附带隐喻：动量 = 质量 × 速度且无外力时守恒 —— 能力沉淀是质量，交付速度是速度，L4 评测锚点保证已获得的能力不会在后续迭代中流失。

## 二、中心主张（一切设计的源头）

> **多 Agent 系统的可靠性来自不变量，不来自提示词。**
> 凡是"在提示词里叮嘱 Agent 不要做 X"的地方，都应改成"在结构上让 X 做不到"。

推论：**把不可恢复的部分交给确定性代码，把可恢复的部分交给模型。**
控制平面（锁、状态机、准入校验、门禁）出错不可恢复 → 一行 LLM 都不用；
执行平面（写代码、评审）出错可恢复（打回重试）→ 交给模型。

约束实现的优先级：**不可见 > 无权限 > 被拦截 > 提示词劝阻**。

## 四、架构速查

```
控制平面（确定性，无 LLM）  状态机 · 锁管理 · 准入校验 · 门禁 · 预算 · Guardian
执行平面（模型）            Intake·Architect·Planner·QA·Coder×N·Helper
                            Reviewer·Integrator·Manager·Evolver
数据平面                    四张图（依赖/所有权/溯源/知识）· Git 仓库 · Artifact · 三层记忆
上下文平面                  Context Broker（可见性矩阵 · 配方 · 预算降级链）
进化平面                    证伪门 · 影子回放 · Skill CI · 灰度（受"不动点"约束）
```

**同构参照**：控制平面 ≈ Kubernetes。`.codentum/` ≈ etcd，reconcile loop ≈ controller manager，
WorkPacket ≈ Pod spec，准入校验器 ≈ admission controller（此项对应精确），门禁 ≈ rollout gate。

### 双运行模式（共用同一套控制平面，一行代码不改）

- **Solo**：本地单进程 + 本地 Worker + 本地 Git + SQLite。零外部依赖，装完就跑
- **Team**：跑在 AgentTeams 上（Manager-Workers + Matrix + Higress + MinIO + PG）

四个接口抽象：`WorkerRuntime` / `ArtifactStore` / `MemoryIndex` / `ModelGateway`。**P1 就定死，之后只加实现不改签名**——否则双模式必然分叉。

## 十五、写第一块代码时踩到的：并发测试默认是空转的

**这条值得单列，因为它直接威胁「我们靠不变量而不是提示词」这个中心主张的可信度。**

路径锁写完后，先做了一次「这个测试真的能失败吗」的验证：把 `LockTable`
的互斥锁整个换成空操作，跑 **400 轮**五线程抢重叠路径 ——
**依然每轮都恰好一个赢家，一次都没红。**

原因是临界区太短，GIL 在 check-then-act 之间根本没机会切走。
也就是说：那条名义上验证 I1 的并发用例，**在锁被完全删掉的情况下照样全绿**。

把 `sys.setswitchinterval` 压到 1µs 后，无锁版本立刻暴露。已作为 autouse
fixture 固化进用例并写明理由。

### 三条推论

1. **并发测试不主动制造穿插，测的就只是「串行调用两次」。**
   写并发用例时必须配一次「把锁摘掉，它会不会红」的对照实验，
   否则那条用例的绿灯与「有没有锁」无关。

2. **这与 I2「验收可判定」是同一个问题的两面。**
   我们要求每个 packet 的验收谓词机器可判定 —— 但「可判定」不等于
   「判得出差别」。一条永远返回 true 的谓词也是机器可判定的。
   ★ 准入校验器将来要考虑：能否要求验收谓词附带一个「已知失败样本」，
   证明它在错误输入上确实为假。**没有这一步，I2 挡不住空转的验收。**

3. 顺带抓到实现里一个真 bug：`next(iter(...))` 抛的 StopIteration 会被
   Python 转成 `RuntimeError: generator raised StopIteration`，堆栈指向
   调用点，真实原因（计数器与树不一致）被完全掩盖。已改成显式抛出。
   —— 这个 bug 只有在无锁压测里才会现形，串行测试永远碰不到。

## 十七、08-09 踩到的：绿灯本身可以是假的

§十五记的是「并发测试第一版是空转的」。这次是同一个病的另外三种形态，
一天之内连着踩了三次 —— 值得把它当成一类问题记住，而不是三个孤立的 bug。

### 形态一：断言「到达成功终态」，而不检查「过程是否真的成功」

`test_pending_to_accepted_with_worker` 是我们宣称「P0 全链路打通」的旗舰测试。
它的 mock worker `evidence=()` 是空的，于是 packet 走到 accepted 时，
手上唯一那条证据是 `_try_ready_to_running` 自己写的 `sys:lock:<pid>`。

**系统自己记了一笔「我拿到锁了」，被当成了验收依据。**

这类测试有个恶劣性质：**放行逻辑越松，它越容易通过**。
换句话说，它在系统坏掉的时候绿得最稳。

> **判据**：写完一条测试，先问「如果这个功能坏了，它会不会红？」
> 答不上来的，它就不是测试，是装饰。

### 形态二：新写的测试第一次就绿

`ac-handoff.test.ts` 里有一条「找不到 Python 解释器就 return」的分支 ——
通过可能只是**没跑**。

于是临时把被测的修复退回去重跑一遍：C 真的吐出了
`[partial-write] ... missing nodes: wp-ac0001, wp-ac0002`。这才确认它是真的。

> **新测试第一次就绿，先怀疑它没跑，而不是庆祝。**
> 这和 §十五「把锁摘掉看它会不会红」是同一个动作。

### 形态三：报错位置不等于出错位置

两次都吃了这个亏：

- `CommandRunner` 里，真因是**读取线程**里的 `UnicodeDecodeError`，
  冒出来的是几十行外的 `TypeError: data must be str, not NoneType`
- worker 失败的真因是 `no worker runner configured`（一行配置没写），
  而控制面只保留了 `reason_code=runtime_error`，看上去像执行环境挂了 ——
  **排查方向被带偏了整整一轮**

> **推论**：机器可读的理由码是给**调度器**用的，人可读的详情是给**排查**用的。
> 两者都要留。丢掉详情不是精简，是把成本转嫁给下一个人。
>
> 看到「类型明显不该出现」的兜底型报错（None 出现在不该有 None 的地方），
> 要往上游找那个被吞掉的异常，而不是在报错处加个判空。

### 为什么这件事对本项目格外要紧

Codentum 的中心主张是「可靠性来自不变量，不来自提示词」，为此建了一整套确定性判定。
而这四个缺陷全是**静默**的 —— 不报错、不变红，只是安静地给出错的结果。
其中最要命的一个，让「worker 失败」和「验收通过」在系统眼里长得一模一样。

**一套以「可判定」为纲的系统，自己给出了一个不可信的判定。**

同一条批评也适用于护栏本身：`ReconcileLoop` 的
`gate_runner` / `guardian` / `budget_tracker` / `transition_table`
四个安全组件**默认全是 `None`**，默认配置下护栏是全关的。
「约定不等于约束」这句话，我们对别人说过，对自己也成立。

## 二十、08-11 踩到的：接线会暴露一整类设计里看不见的缺陷

`packages/engine/` 落地那天，代码量不大。但**接的过程**当场抓出
三个缺陷 + 一条流程漏洞，四个的共同点是：**只有真的把两头接上才会现形。**
设计评审看不出来，单测看不出来，各自模块的集成测试也看不出来。

> ⚠️ 先更正一处本节初稿的错误：初稿写 `__main__.py` 是「stdio + HTTP 双模式」——
> **没有 HTTP 模式，从来没有过。** 只有 stdio JSONL 一种。
> 一份记录自己没做过的功能的进展文档，比没有进展文档更危险，
> 因为下一个人会按它去找那段不存在的代码。

### 1. ★ 子进程继承了协议通道 —— 一个「不报错的死锁」

`LocalWorkerRuntime.__init__` 构造 `GitWorktreeManager`，后者跑
`git rev-parse --show-toplevel`。这个 git 子进程**继承了引擎的 fd 0**，
而 fd 0 正是桌面端发来的协议管道，引擎主线程还在阻塞读它。实测：

```
10:31:02  已取得状态锁，开始装配
10:35:02  装配完成，开始 tick      ← 整整四分钟
10:35:24  模型返回
```

四分钟里**没有任何报错、没有任何异常日志**。查了三轮才定位，
因为「装配一个 runtime 对象」看起来根本不像是会做 I/O 的事。

**而更严重的是它安静的那一面**：任何一个会读 stdin 的子进程，都会把
桌面端发来的命令**从协议通道里读走**。命令就此消失，桌面端等到超时，
引擎这边什么都没发生 —— 不报错、不可复现、没有测试会红。

★ 修的位置比修法本身更值得记：**没有去 `worktree.py` 每个
`subprocess.run` 补 `stdin=DEVNULL`。** 那既越界（B 的路径），也只能堵住
当下这几处 —— 下一个新增的子进程调用又会漏。**fd 0 只有一个，
在进程入口一次性换掉，才是覆盖全部子进程的那个位置。**
修复后装配从 240 秒降到 1.9 秒。

> 推论：**当一个缺陷有 N 个发生点时，先找那个「只有一份」的东西。**

### 2. 库的正确默认值，是产品的错误默认值

`ReconcileLoop.run_until_stable()` 内部连跑多轮，**只在最外层保存一次**。
对测试完全正确（load → 跑完 → 断言终态）。但产品入口照抄之后，
一次真实模型调用的整段时间里，`.codentum/` 一直是初始状态，
最后一刻突然跳到终态 —— **一个卖点是「执行过程看得见」的产品，
恰好在执行过程中什么都看不见。**

这与四个安全组件默认 `None` 是同一件事的两面：
`None` 对库合理，对产品是关掉护栏；`run_until_stable` 对测试合理，
对产品是隐藏过程。

> 推论：**「默认值由谁选」必须有归属。** 在有装配点之前，
> 每个调用方各选一次，测试选一套，产品入口会选另一套，而且没人负责。
> 这是 ADR-0007 真正的内容 —— 新增一个包只是形式。

### 3. ★ 又一次：对照组配错了，实验照样出数

给「执行过程可见」写的第一版判据是：**磁盘上必须出现过 ≥2 个不同状态**。
看起来合理。实际是空转的 —— 起点 `pending` 和终点本来就是两个状态，
用退化写法（只在最后存一次）照样能看到两个。
**把产品代码改回退化写法，那一版测试全绿。**

改成**数 `save_state` 被调用了几次**，并且跑**真正的**
`_run_until_stable`（不是测试里手搓的循环 —— 手搓循环只能证明我会写循环，
证明不了产品代码是那么写的），才真的会红。

这是 §十九.3 的第二个样本，也说明那条教训**上一次并没有学会**：
知道「对照组会配错」，不等于下次配对照组时会想起来。

> 推论：**写完判据要问的不是「它现在绿吗」，是「把被测的东西改坏，
> 它会红吗」。** 前者永远能满足，后者才是判据。

### 4. 防止「测试静默不被收集」的机制，自己被静默绕过了

`Makefile` 里写着完全正确的判断：

> ★ 不写死 tests/contract。写死的话，新增的测试目录会静默地不被
>   verify-offline 覆盖 —— 而「没跑过的测试」和「跑过且通过的测试」
>   在终端上长得一模一样。收集范围交给 pyproject 的 testpaths，保持单一来源。

判断是对的，做法只做了一半：**单一来源本身仍然是手维护的。**
于是 `packages/delivery/tests` 从落地起就没进过 `testpaths` ——
**C 的 15 条测试从来没有跑过**，而每一次 `make test` 都打印「全部通过」。

> 推论：**「保持单一来源」不是终点，「单一来源本身谁来保证」才是。**
> 一个需要人记得去更新的清单，等价于没有清单 —— 只是它失败时更安静。

### 5. 这一节自己也差点丢

写到一半时，另一个会话切了分支，本节与待办 27–30 的未提交改动一起消失。
**这正是 §十八 那件事的第二次发生**，只是这次原因不是 merge 选边，
是「改完没有立刻提交」。§十八 的推论 3 已经写过「合完当天就推」——
同样，**写完当轮就提交**。

★ 五条合起来指向同一句：**接线不是体力活。**
三个模块各自都对，接起来仍然会坏，而且坏的方式不会报错。
「组件齐」到「链路通」中间的那段距离，只能靠真的接一次量出来。

一度担心 B 的 `packet-intent` 与引擎的 `requirement:<packetId>` 会撞车。
实测合并后模型收到的 `Visible Context` 里两条都在，且分工清晰：

| | 来源 | 内容 |
|---|---|---|
| `packet-intent`（B） | 从**契约字段**派生 | 完成哪个 packet、什么角色、可写路径、验收谓词 |
| `requirement:<id>`（A） | 操作者提交的**自然语言原文** | 「在 workspace/ 下新建 subscriptions.py……」 |

B 那条对**任何** packet 都有（包括不是从需求提交来的），A 这条只有引擎建的
packet 才有。两条都是 `required=True`。

> 推论：两个人在同一天、互不知情地各自解决了「模型不知道要做什么」，
> **给出的答案不冲突，因为切入点不同**（一个从契约能推出什么，
> 一个从用户实际说了什么）。这不是运气 —— 是 `context_loader`
> 这个注入点本身设计得对：它允许多个来源叠加，而不是二选一。

### 3. ⚠️ 缺陷二当时只修掉了一半（另一半已于当日晚些时候补齐，见 §二十二）

B 在 `ModelGatewayRunner` 加了确定性 blocker 检测
（`Blocker Report` / `cannot proceed` / `无法继续` 等前缀 → `WorkerFailed`）。
引擎走同一个 runner，**直接继承，不需要自己再写一遍**。

**但合并后那一轮真机跑通就是另一半的样本**：模型没有报 blocker，
它把代码写在了回复正文里 —— `tool_calls` 为空、**一个文件都没被创建**、
packet 仍然 `accepted`。

> 前一半能靠关键词判定解决：**说了「我做不了」**。
> 后一半不能：**什么都没说，只是什么也没做。**
> 判据得从「模型说了什么」换成「工作区里多了什么」——
> 那是设计决定，不是补丁。

★ 记这一条是因为「缺陷二已修」是个很容易顺口说出去的结论。
`ModelGatewayRunner` 的单测确实绿了，但绿的是**能识别出显式 blocker**，
不是**能识别出没干活**。

### 4. ⚠️ 两处边界越界，都不严重，但要记

- **B 改了 `tests/e2e/**`**（A 的路径）：把缺陷二的确定性判定从真实模型 e2e
  移到 harness 单测，真实模型那条改成「只在模型本次确实返回 blocker 时才检查」。
  ★ **这个改法是对的** —— 原来那条把模型的随机行为写成了稳定判据。
  越界的是流程不是内容。
- **B 改了 `docs/**`**（A 的路径，规矩是「B/C 提 PR」）：这正是 08-09 被 merge
  吃掉 85 行的那个文件。这次没丢，因为解冲突时逐块确认了两侧都留。

> 推论：`boundaries.yaml` 保证「一条路径只有一个 owner」，但它**不阻止**
> 别人写 —— 它只是让越界这件事**事后可查**。真正的防线是 merge 时有人逐块看。

### 5. 一次完全可以避免的重复劳动

`.as_posix()` 那一行，A 和 B **在同一天各自独立修了一遍**，改法一致、
只有排版不同，合并时还撞了冲突。

根因不是谁做错了，是**待办清单里没写「谁来做」**：条目写了「要修什么」，
没写「归谁」，于是两个人都看到了、都觉得该修、都动手了。

> 推论：**待办条目必须带 owner。** 一份没有 owner 的清单，
> 要么没人做，要么两个人同时做 —— 前者更常见，后者更浪费。

### 6. ★ 一次险情：解冲突时选了 ours，差点把 B 的修复静默丢掉

合并过程中留下过一条提交：`157450f fix(merge): 应用 B 的 blocker 检测逻辑
（冲突解决时误选了 ours）`。

也就是说：`model_gateway.py` 的冲突第一次是按「取 ours」解的，
**B 那 40 行 blocker 检测就此消失** —— 而合并本身是「成功」的，
测试也全绿，因为**盯着那段逻辑的测试是 B 一起带过来的**，
取 ours 的时候它也一起没了。**缺陷和它的判据一起消失，于是没有任何东西会红。**

这与 §十八「merge 静默吃掉 85 行记录」是同一个病的第三次发作，
而且这次更危险：上次丢的是文档（只能靠人记得），这次丢的是**代码 + 它的测试**。

> 推论：**解冲突取「一侧」时，要连带检查那一侧的测试还在不在。**
> `git diff --stat` 里如果某一侧的测试文件也一起消失了，
> 那就不是解冲突，是回退。
>
> 更简单的判据：**merge 之后跑一次「被合入方的测试」**，
> 而不是只跑「合并后的全量测试」—— 全量测试是绿的，因为判据也一起没了。

★ 这次是靠人回头发现的，不是靠任何检查。

## 二十二、08-11 修完缺陷二的另一半：判据一直都在，只是没人看

### 修了什么

`_try_running_to_review` 现在检查 `WorkerCompleted.touched_paths`：
`kind ∈ {impl, test, fix}` 的 packet 自称完成、却**一个文件都没改**时，
落一条 `sys:worker-failed:<id>:acceptance_not_met`，停在 review，不得自动验收。

### ★ 这条缺陷为什么难抓

它是同一个病的第四层，每一层都比上一层安静：

| 层 | 表现 | 判据 | 修于 |
|---|---|---|---|
| 一 | 拿控制面自己的簿记当证据（`sys:lock:`） | 证据前缀 | 08-09（兜底分支） |
| 二 | 同一个洞在门禁分支没修，且门禁优先级更高 | 同上，收敛到 `evidence.py` | 08-10 |
| 三 | 模型明说 blocker，runner 仍判 completed | 文本前缀（B 的确定性检测） | 08-10（B） |
| 四 | **什么都没说，只是什么也没做** | **工作区里多了什么** | 08-11（本次） |

前三层都能靠「读某个字符串的前缀」解决。第四层不能 ——
证据是真的（`result.json` 确实落了盘）、模型也没说任何丧气话，
它只是把代码写在了回复正文里，工作区一个文件没变。

**判据必须从「模型说了什么」换成「工作区里多了什么」。**

### ★ 真正值得记的是：数据一直都在

`WorkerCompleted.touched_paths` 是**冻结契约里的字段**（`interfaces.py:156`），
worker 老老实实报了改过哪些文件，测试里的 `_MockWorkerRuntime` 从第一天起就在
填它。**控制平面从来没看过一眼** —— `grep touched_paths loop.py` 在本次修改前
是空的。

> 推论：**「缺判定」比「缺数据」更常见，也更难发现。**
> 缺数据会报错（字段不存在），缺判定什么都不会发生 ——
> 契约里那个字段静静躺着，看起来一切正常。
>
> 排查这类问题的一个具体动作：**把契约里的字段逐个 grep 一遍，
> 看有没有哪个只被写、从没被读。** 只写不读的字段要么是死代码，
> 要么就是一条没人执行的规则。

### 两个对照组

判据只对「必然产生文件改动」的 kind 生效（`impl` / `test` / `fix`）。
`review` / `spike` / `design` 的产出是判断和结论，本来就可能一个文件都不碰 ——
一刀切会把它们全判失败，**那不是更严格，是把判据变成噪音**。

三条测试：违规必须红 · 正常改了文件必须绿 · review 类没改文件也必须绿。
实测把判定摘掉后第一条立刻变红，两个对照组保持绿。

### ★★ 修完当天就踩了第二次：判据本身被系统自己的产物满足

改完之后跑真链路，日志写着「改动 10 个路径」，packet 照样 accepted。
去看那 10 条是什么 —— **全是 `.codentum/evidence/**`**：
harness 自己写进 worker 工作区的 prompt / response / usage / manifest。
模型的产出一个都没有。

也就是说：**「改动数 > 0」这条新判据，被系统自己的簿记满足了。**
这和「拿 `sys:` 前缀簿记当证据」是同一个 bug ——
前者污染 evidence 列表，这里污染 `touched_paths`，只是下沉了一层。

★ 而且当时**单元测试是全绿的**：mock 里的 `touched_paths` 是干净的
（`("src/app/main.py",)`），根本没有簿记文件。
**只有真的跑一次链路才看得见。**

> 推论：**新写的判据，第一件事是问「什么东西会不小心满足它」。**
> 「证据非空」被控制面自己的锁记录满足过；
> 「改动数 > 0」被 harness 自己的证据文件满足过。
> 两次都是**系统自己的产物**混进了「别人交的活」里。
> 判据的输入干不干净，和判据本身对不对，是两件事。

修法：`_worker_authored_paths()` 滤掉 `.codentum/` 前缀，并归一化反斜杠
（漏掉归一化的话，判据在 Linux 上有效、在 Windows 上失效且不报错 ——
这个坑本项目已经踩过两次）。三条测试钉着：只有簿记必须红 ·
反斜杠形式也必须红 · 簿记之外有真产出必须绿。

★ 第一版 `_worker_authored_paths` 还写错了一处：用 `lstrip("./")` 去前缀，
而 `lstrip` 剥的是**字符集合**不是前缀，`.codentum/x` 被剥成 `codentum/x`，
判定当场失效。**是刚写的那两条测试立刻抓住的** —— 先写会红的测试，
这次实实在在省了一轮。

## 二十三、08-11：把 251 个 mypy 错误清零，以及它们证明了什么

`make typecheck` 复活之后报出 251 个错误，全部修完，现在是
`Success: no issues found in 107 source files`。

### 最值得记的结论：门禁死了这么久，并没有真的漏进缺陷

源码那 71 个错误逐条看下来，**没有一个是运行时 bug**。全是类型卫生：

| 类型 | 例子 |
|---|---|
| 循环变量重名 | `for f in findings` 撞上前面的 `f: str`（运行时正常，读的人会懵） |
| 缺 `NoReturn` | `fail()` 不标，mypy 就认为异常分支会往下走，于是在**别处**报 possibly-undefined |
| 抽象方法用 `...` 当体 | 子类忘了实现会静默返回 None，而不是报错 |
| 泛型缺参数 | `list` / `tuple` / `dict` 裸写 |

> 推论：**「门禁没跑」和「有缺陷」是两件事，别把前者当成后者。**
> 反过来也成立 —— 这次没漏进缺陷是运气好，不是因为门禁不重要。
> 一个从未执行过的检查，它的价值不体现在「这次发现了多少」，
> 体现在「下次会不会发现」。

### 但确实抓到三处「现在不是 bug、迟早是」的东西

**1. 替身少实现了协议的三个方法，而没有任何东西会说。**

`_MockWorkerRuntime` 一直靠结构化匹配「碰巧像」`WorkerRuntime`，实际少了
`events` / `resume` / `adopt`。后果不是现在会崩，而是：
**协议以后加一个方法，这个替身不会有任何反应** —— 它只是悄悄地不再是
WorkerRuntime，而依赖它的一整批测试照样绿。

已改成显式继承 Protocol。现在协议变了，这里立刻红。

> 推论：**替身要显式声明它在替谁。** 结构化匹配的便利，
> 代价是「被替身覆盖的那条链路什么时候不再被覆盖」这件事没人会告诉你。

**2. `_loop: object` —— 靠调用顺序保证，不靠类型保证。**

`settle` 分支直接 `self._loop.run_until_complete(...)`，而 `_loop` 只在
spawn 分支里创建。当前 `_active_workers` 在 `load_state` 里被清空，
所以 settle 之前一定 spawn 过 —— 跑起来没出过事。
但那是**调用顺序**给的保证。哪天有人让 settle 能从别的路径触达，
那里就是一个 AttributeError，而且只在崩溃恢复场景下偶发。

**3. `RuleFn` 在两个文件里各定义了一份。**

与 §十九.1「一个概念两处实现」是同一个病的第四个样本
（前三个：证据判据、EvidenceRef 分隔符、流编码）。已合并为一份。

### 两处保留了运行时检查，只给 mypy 记案

- `engine_proxy` 对 argv 的 `isinstance` 校验：签名写着 `Sequence[str]`，
  所以 mypy 判它冗余。但命令来自环境变量 `CODENTUM_ENGINE_COMMAND_JSON`，
  **调用方未必经过类型检查** —— 这是信任边界。
- 并发压测里的 `r is not None`。

> 删掉它们能让 mypy 更干净，但那是**把「运行时校验」当成「类型已保证」**。
> 类型检查覆盖不到进程边界，而这两处正好在边界上。

### 一个反复出现的自伤

批量给测试函数补 `-> None` 时，正则把**三个返回 WorkPacket / RoleSpec 的
辅助函数**也标成了 `-> None`；后来又把两个返回 `GateVerdict` 的内嵌门禁
函数标错。两次都是**测试当场红掉才发现的**。

> 推论：**机械批改必须跑在有测试的地方。** 同一个正则如果作用在没有测试
> 覆盖的代码上，这五处会静静地留在仓库里 —— 而它们的症状（返回值被当成
> None）要到很久以后才会显形。

### 1. ★ 最难查的一个：诊断信息被**有意**丢掉了

### 2. ★ 启动能力不该取决于「谁开的那个终端」

引擎的启动命令是 `python -m codentum_engine`，而 `-m` 要求
`codentum_engine` 已在 `sys.path` 上 ——
也就是**要求启动 Electron 的那个终端事先 export 过 `PYTHONPATH`**。

换个终端、双击启动、从 IDE 里跑、别人 clone 下来照 README 跑，全都不成立。
而不成立时的现象正是第 1 条描述的那种「三层无人知情」。

修法不是「把环境配对」，是**让它不需要被配对**：
`_bootstrap.py` 从自己的 `__file__` 推出仓库根，把包根挂上 `sys.path`。

★ 中间有个值得记的坑：脚本模式下不能写
`from codentum_engine._bootstrap import ...` —— 那会先执行包的
`__init__.py`，而它又要导入 control-plane，
即**「为了把路径挂上去，先得路径已经挂好」**。改用 importlib 按文件加载绕开。

> 推论：**凡是「跑起来」依赖外部环境的地方，都要问一句
> 「换一台机器、换一个终端，它还成立吗」。**
> 不成立的部分，要么自举，要么在启动时明确报错 —— 而不是安静地不工作。

### 3. ★「显示了 11 个」不等于「接入了 11 个」

用户从界面截图上看出「系统岗位 11、项目投影 0」，并准确指出：
那 11 张岗位卡片来自桌面端自己维护的静态清单，
**不代表这 11 个角色真的被系统加载了**。

真源在 `packages/roles/specs/*.json`（B），桌面端读的是项目内的
`.codentum/roles/`（C），**两者之间原本没有任何人搬运**。
两边各自都对，没有任何测试会红。

> ★ 这是本项目「看得见的产物是真的，产生它的过程是另一回事」的又一个样本，
> 而且是**由用户从一张截图上的两个数字看出来的**。
> 「11 / 0」这个并列本身就是判据 —— 它把「系统认为有多少」和

## 二十六、08-13 —— 让平台真的开发软件，以及五次真机撞出来的东西

### 起点：平台当时做不到「开发软件」

08-12 的结论是「系统能诚实地说『没干成』，但它确实还干不成」。三个结构性缺口：

| 缺口 | 实况 |
|---|---|
| 没有 Planner | 一个需求只产出**一个** packet |
| 模型无法写文件 | `ModelGatewayRunner` 是 one-shot，**没有工具循环** |
| 工具面是声明不是实现 | `ToolDescriptor` 在契约里没有执行体，全仓库无工具注册表 |

### 落地的四层

1. **工具循环**（`agent_runner.py`）：write_file / read_file / list_files /
   run_tests / request_help 的真实实现 + invoke→执行→回传→再 invoke
2. **执行型验收门禁**（`acceptance.py`）：验收谓词**真的跑一遍**，
   而不是「有证据就算过」
3. **空测试检查**：把实现移走再跑一遍，**测试必须变红**
4. **状态目录自愈**：运行中被删也能补回来，而不是等重启

### ★ 第五层：验收通过了，而验收标准是空的

真机跑通那一刻打开模型写的测试文件：

```python
def test_example():
    assert True
```

**实现是对的。测试什么都没验证。而验收通过、packet 被 accepted。**

这是那条线的第五层：

| 日期 | 缺陷 |
|---|---|
| 08-09 | 拿控制面自己的簿记当证据 |
| 08-10 | 门禁层同一个洞 |
| 08-11 | 说完成了但一个文件没改 |
| 08-12 | 改了文件，但没达到验收标准 |
| **08-13** | **达到了验收标准，但验收标准是空的** |

前四层都能靠「看有没有 X」解决。这一层不能 ——
**任何检查测试内容的做法都是模式匹配**，模型总能绕过。

解法是**因果检验**：把实现移走，测试必须变红。绕不过去。
它恰好是本项目那句口号的可执行版本 ——「如果它坏了，哪条测试会变红？」

产物存 `docs/experiments/vacuous-acceptance/`。

### 起点：MCP 一直只是一份声明式清单

`packages/roles/mcp/*.json` 里写着 `"tools": ["dispatch_task", ...]`，
引擎投影到 `.codentum/mcp/`，桌面端显示出来 ——
**全程没有任何代码去连接、去列举、去调用**。

那份清单诚实地标了 `"status": "disconnected"`，所以它不算撒谎；
但「接入飞书 / GitHub / 支付宝」这件事，缺的正是这一层。

### 分层：为什么走 MCP 而不是各写适配器

| 层 | 归属 | 接入方式 |
|---|---|---|
| **Skill** | 能力抽象 | **共享**，跨角色跨项目复用 |
| **MCP / 插件** | 工具连接 | **主 Agent 接一次**，所有已连服务的工具自动进工具面 |

新增一个第三方应用 = 加一条配置，**不改任何代码**。
鉴权、重试、错误语义由各自的 server 负责，不污染主循环。

### 实现（零第三方依赖）

- `mcp_client.py`：JSON-RPC over stdio，完整生命周期
  （initialize → initialized → tools/list → tools/call → 关闭）
- `mcp_toolbox.py`：多 server 汇总。**一个连不上不影响其余**，
  但失败如实记入 `reports` 并在 `summary()` 列出 ——
  不静默降级成「没有这个工具」

### ★ 真机验证：模型自主调用了真实的 GitHub API

```
MCP server 连接        → ✓ GitHub 26 个工具
工具并入模型工具面      → 27 个（1 内置 + 26 第三方）
★ 模型自主选择工具      → github__list_commits
★ 真实执行             → 成功，返回真实 commit SHA 76d64c82…
```

模型**没有凭记忆编造**，而是自己选了工具并拿到真实数据。
这是「第三方应用能跟主 Agent 接上」的完整证明。

### 途中撞到并修掉的两个真实缺陷

**① 中文经 stdio 管道后乱码。**
子进程用系统默认编码（中文 Windows 上是 GBK）写 stdout，父进程按 UTF-8 解码。

> ★ **JSON 结构本身是 ASCII，解析不报错**，只有内容里的非 ASCII 字符坏掉 ——
> 这类故障不会让任何协议层断言变红，只能靠内容断言抓住。

本项目已在流编码上踩过一次，这是第二次。已加内容断言守住。

**② Windows 上 `npx` 找不到（WinError 2）。**
`npx` / `npm` 是 `.cmd` 批处理，`shell=False` 的 CreateProcess 找不到它们 ——
而 GitHub / 飞书 / 支付宝的推荐启动方式**正是 `npx`**。

> 表现为「配置写对了但连不上」，且**只在一个平台上出现**。
> 修法是 `shutil.which` 解析真实路径 ——
> **不能改用 `shell=True`**，那会引入命令注入面。

### 第三方应用配置的三条原则

1. `enabled` 默认 `false`，`status` 如实写 `disconnected`
2. **`tools` 字段刻意留空** —— 由 server 在 `tools/list` 时提供。
   预先罗列会在 server 版本变化后变成谎报
3. 高风险应用（支付宝）显式标注：涉及资金操作，
   接入前须确认 `riskLevel` 与人工审批链路，**不应默认对所有角色可见**

### ★ 顺带修掉三处「写死清单」的测试

新增配置后，三条断言因「恰好只有这四个文件」而红。改为守性质：

```python
# 之前：assert projected == ["agentteams.json", "browser.json", ...]
# 之后：
assert {"agentteams.json", "browser.json", "filesystem.json", "git.json"} <= set(projected)
assert names == sorted(names), "投影顺序必须确定"
```

> ★ 写死清单的测试**不会因为多一个文件而变得更有保障**，
> 只会让每次加应用都要改测试。
> 而第二条（顺序确定性）才是那条测试名字（deterministic）真正要守的东西。

### Skills 质量审计结论：不需要改

12 个 Skill 全部合格 —— `Use when` 开头的 description、正文 500–900 字、
权限最小化（工具 4–9 个、写路径 1–4 条）。

★ **复用率是架构健康度指标**：`testing` 被 4 个角色引用、`review` 被 3 个引用，
说明抽象粒度合适；若每个角色各有一套专属 Skill，说明抽象失败。

### 待办

- GitHub 配置目前写的是 docker 镜像，但本机 Docker 守护进程未启动；
  实测可用的是 `npx @modelcontextprotocol/server-github`
- 飞书 / 支付宝需各自开放平台凭据后才能验证

## 二十八、08-13 —— Planner：一个需求终于能拆成多个 packet

### 起点

`build_packet_for_requirement()` 返回**单数**：role 写死 coder、
`ownsPaths` 写死 `workspace/`。于是 11 个角色里实际只有 1 个会被调度，
「多 Agent 协同」体现在角色隔离上、**不体现在任务拆分上**，
系统产出上限是「一个模块」。

★ **缺的从来不是调度**。`ReconcileLoop.tick()` 遍历所有非终态 packet，
依赖看 `dep_states`、路径用 `LockTable` 互斥，
`test_parallel_packets_no_lock_conflict` 早已证明三个不相交路径能并行推进。
**缺的是没有人生产多个 packet。**

### 分工：模型只负责「拆成哪几件事」

| 环节 | 由谁做 |
|---|---|
| 需求 → 任务列表 | 模型 |
| 任务 → 角色 · 路径分配 · 依赖成图 · 预算切分 | **确定性代码** |

★ 这条分界不是保守，是**判据问题**：模型分配的路径没有任何测试会红，
而确定性分配可以在单元测试里穷举验证。

### 产出结构

```
[qa: 出题 M] ──→ [coder: 实现 M] ──┐
[qa: 出题 N] ──→ [coder: 实现 N] ──┼──→ [integrator: 集成]
```

### ★ 端到端验证到的那一幕

```
21:31:21,360  wp-5c2e57…  ready → running（锁：workspace/input-handling/tests/）
21:31:21,360  wp-720116…  ready → running（锁：workspace/list-tasks/tests/）
… 共 8 条，同一毫秒
```

**8 个 packet、8 把互不冲突的路径锁、同一时刻。**
这是「多 Agent 并行」第一次在真实调度里发生 ——
此前只有单元测试里的模拟调度器证明过。

且顺序正确：先跑 8 个出题 packet，impl 全部 pending 等它们。

---

### ★ 三个撞出来的缺陷，都值得单独记

#### ① 模型隔离：不变量拦住了实现它的人

端到端第一次跑，准入直接拒绝：

```
需求拆成 8 个任务 / 17 个 packet
packet wp-75148fda124a 未通过准入：MODEL_ISOLATION
```

我给所有 packet 硬塞了同一个模型，而 RoleSpec 里 qa / reviewer 声明了
`mustDifferFrom: [coder]`。规则原话：**同一模型既写又审 → 盲区重叠 → 评审失效**。

> 我这次做的正是「QA 独立出题」—— 为的就是让出题方与做题方不是同一方。
> **而我的实现给两者用了同一个模型，在实质上又把它们合成了一方。**

更值得记的是：**19 条单元测试当时全绿**。我测了路径不相交、QA 前置、
DAG 无环、可调度，唯独没测「模型不能相同」。

★ **判据的覆盖面由写判据的人的想象力决定，而想象力有盲区。**
真机跑一次就暴露了。

#### ② 逐条落盘：并行起来才暴露的可见性缺陷

8 个 QA packet 并行 running，两个 worker 21:33 就失败了，
**8 分钟后磁盘上仍是 8 个 running**。

根因：`_try_running_to_review` 里的 `settle()` 是**阻塞**的，
而 `save_state()` 在整个 tick 之后 —— 8 个 packet 顺序 settle，
磁盘状态直到最慢那个 worker 结束前一直不变。

★ 这与 §十九 记的是同一个缺陷，只是从「tick 粒度」下沉到「packet 粒度」——
**单 packet 时看不出来，并行起来立刻暴露。**

#### ③ 消融实验的隔离缺陷（②的连带发现）

改完逐条落盘后，护栏消融实验红了两条 `leaked_off == 0` ——
即「护栏关掉后一个都没漏」，而那条断言存在的意义正是防止这种读数。

诊断按「先取证不猜」走：

1. 单跑「护栏关」→ `running`，确实泄漏
2. 但 `measure_*` 是先跑开、再跑关、**共用同一个 state_dir**
3. 「护栏开」那轮**先拿锁、再被护栏拦下**，锁留在 `graph.json` 里
4. `_run` 只清 `packets/`，不清 `graph.json`
5. 「护栏关」那轮加载到残留锁 → 卡在 `ready` → **看起来像护栏还在生效**

> ★ 这个隔离缺陷一直存在，只是此前 `_run` 从不调用 `save_state()`，
> `graph.json` 从没被写过。
> **实验的隔离性不该依赖「被测代码恰好不写盘」。**

### 降级路径

拆解要调一次模型，而模型调用会失败。三条降级，**每条都出声**：

- 拆解失败 → 退回单 packet
- 只拆出 1 个任务 → 按单 packet 处理（三个 packet 做一件事，成本翻三倍产出不变）
- `enable_planner=False` → 完全退回旧行为

★ 静默退回单 packet，使用者会以为多 Agent 生效了，
而实际只有一个 coder 在干活。

### 待办：并发限流

8 路并发调模型时出现过 `Connection error`。
单个 API Key 的并发上限是真实约束，需要在 spawn 侧限流 —— 记在案。

## 三十、08-14 —— 按 ADR-0004 把执行平面改造成 LangGraph

### 起点：一个被用户问出来的缺陷

用户问：「为啥用的 DAG 没用 LangGraph？貌似不合理吧」。

查下来分两层：

**第一层我们是对的。** ADR-0004 专门澄清过概念重叠：

| | 是什么 | 例子 |
|---|---|---|
| 四张图 | **数据结构** —— 系统状态的拓扑 | 依赖图（谁等谁）、所有权图（哪条路径被谁锁） |
| LangGraph | **控制流图** —— 一次执行的步骤走向 | 节点是函数，边是转移 |

> **依赖图不是可执行的图，它是一张「谁要等谁」的表 —— 拿 LangGraph 表达它是范畴错误。**

**第二层是真缺陷。** ADR-0004 明确决定「执行平面 ✅ 用 LangGraph」，
README 与技术栈文档都这么写，`langgraph>=0.2` 一直在 `pyproject.toml` 里 ——
**而全仓库零 import**，实际是 `agent_runner.py` 里 560 行手写 for 循环。

> **一个装了却没用的依赖，比没有这个依赖更糟 ——
> 它让读者以为系统有 checkpointer、有流式、有 human-in-the-loop。**

这正是本项目一路在拆的那类问题：**声称与实际不一致，且没有任何测试会红。**

### ★ 用户的判断纠正了我的方案

我当时提了两条路：A 补上 LangGraph、B 更正文档去迁就实现，
并建议 B（理由是距 8.16 只剩 2 天，换框架有风险）。

用户否掉了：**「不能用 B，必须按照设计全方位改造」。**

★ 这个判断是对的。改文档去迁就实现，等于用「文档准确」换掉「设计被执行」——
而 ADR 是团队的决策记录，不是可以随实现漂移的注释。

### 改造：行为等价重构

```
              ┌──────────┐
    ┌────────►│  model   │◄──────────────┐
    │     ┌────┼────┐                    │
    │ tool_calls help  no calls          │
    │     ▼     ▼      ▼                 │
    │  ┌─────┐┌────┐┌────────┐          │
    └──┤tools││help││ verify │──────────┘  谓词不过 → 回推
       └─────┘└─┬──┘└───┬────┘
                └───────┴──►[END]
```

★ **判据：`test_agent_runner.py` 的 13 条测试一条都没改。**
它们定义了必须保持的语义（工具结果回传、撞上限不伪装完成、求助终止、
自验与门禁同判据、瞬时错误重试而确定性错误不重试、截断可恢复）。

> **能在不改测试的前提下换掉实现，才说明这是重构而不是改行为。**

### 改造带来的新能力：路由可单独测试

新增 `test_agent_graph.py`，10 条，**1.25 秒**跑完 —— 对比端到端那组 4 分钟。

路由是纯函数（只读 state、无副作用），可脱离模型/文件系统/网络穷举验证。
手写循环里「下一步走哪」与副作用混在一起，测一个分支得搭起整条链路。

其中一条守的是 LangGraph 的默认陷阱：**状态字段默认覆盖而非追加**。
消息历史若用默认合并，每轮只剩最后一条 ——
**模型会失去全部上下文，却没有任何报错。**

### 途中修的一处

截断回推时 `response` 为 `None`，初版路由把它当终局。
但「没有响应且没有终局」= 本轮被回推了，必须回到模型 ——
**把可恢复的情况判为终局，等于浪费一次本可成功的运行。**

## 三十三、08-14 —— 判据的因果检验：谁来判据判据

`vacuity_check` 防的是「执行者交上来的验收测试是空的」。但它有一个自己管不到的盲区：

> **它自己是谁在守？** 更一般地：那 8 条准入规则、4 道门禁，有没有任何测试守着它们？

于是把同一个算子抬高一层（`scripts/mutate_judgements.py`）：逐条把判据替换成「永远放行」，
断言至少一条测试变红。**首轮结果 0/12，每一条都有测试守着。**

### 两个实现细节决定了这个数是真是假

**一、变异体在结构上与原判据不可区分。** 朴素做法是把规则从 `DEFAULT_RULES` 里删掉 ——
那样测出来的数是**虚高**的：只要有一条断言 `len(DEFAULT_RULES) == 8` 的测试，
删掉任何一条它都会红，但那不叫「这条判据被守着」，叫「判据的**数量**被守着」。

所以改成置换 `__code__`：同一个函数对象、同名、元组同位置，**只有行为变**。
结构断言一条都杀不死它，能让测试变红的只可能是行为断言。

**二、三个控制点缺一不可。** 基线绿 · 至少一条被杀死 · **正对照（塞一条空规则）必须存活**。

> ★ 少了第三点，「12 条全部被杀死」这个漂亮结论**和「杀死判定永远为真」在证据上不可区分**。

### 强变异 0% 不够，弱变异才找到东西

强变异摘掉整条判据，测的是「有没有人**碰过**它」。但真实缺陷不长那样 ——
真实缺陷是判据**还在**、还会被调用，只是边界挪了一格：`<= 0` 写成 `<= 1`、`a or b` 写成 `a and b`。

于是做了弱变异（AST 层改写后重编译回填 `__code__`）：26 个变异点，22 被杀死，**4 个存活**。
逐个读源码判性质后：

| 存活的变异体 | 判定 |
|---|---|
| `check_budget_limit` `<= 0` → `<= 1` | **真缺口**：合法预算的下边界没测过（只有「0 无效」和「5.0 有效」） |
| `check_role_model_isolation` L219 `or → and` | **真缺口**：「角色不在 role_specs 里」这条卫语句没测过 |
| 同上 L227 `or → and` | **真缺口**：「被引用角色不在传入 specs 里」没测过 |
| `self_test_gate` `[:80]` → `[:81]` | **等价变异体**：只改给人看的文案截断长度 |

补三条测试后复跑：**0/25，三个变异体全部被杀死**。

★ 途中一个意外收获：第三条测试原本想构造「`mustDifferFrom` 指向不存在的角色名」，
  发现**它在类型层面就不可表示** —— `Literal` 枚举，pydantic 构造时就拒了。
  这正是「不可见 > 无权限 > 被拦截 > 提示词劝阻」的实例：不可表示的东西不需要运行时检查。

### 等价变异体：标注，不隐藏

排除列表天然是个**藏不方便结果的地方** —— 一个存活的变异体让人不舒服，最省事的做法就是把它加进来。
所以立两条规矩：**每条必须写清「为什么这个改动行为上不可观测」**（写不出来的就不是等价变异体，是缺口）；
**每次运行整张表都打印出来**，不管有没有命中。

> ★ 这个数的可信度取决于那张表有多短、理由有多硬。**表越长越该起疑。**

## 三十四、08-14 —— 进化层接线：记忆系统从只读变成能学

契约里的晋升链是完整的（L0 观察 → L1 重复 → L2 假说 → L3 过证伪门 → L4 规则），
`PersistentMemoryIndex` 也实现完了，包括一条真实生效的硬校验：
`L3 必须附 falsification_gate 理由否则抛异常`。

**但 `promote_now()` 在真实执行路径上从未被调用过。** `write_now()` 唯一的调用点是索引「用户提供的知识资源」。

> **记忆系统能记住你告诉它的，记不住它自己经历的。**

与「langgraph 装了零 import」是同一个形状：结构完整、从未被调用，
**而且没有任何测试会红** —— 测试测的是模块本身，模块本身当然是对的。

### 接上的闭环

```
工具失败 → L0 落盘（带证据引用）→ 跨 ≥2 个不同 packet 复现 → 晋级 L1（role 作用域）
        → 按角色召回，进下一次执行的上下文
```

**L0 由确定性提取产生，不由模型总结。** 让模型写复盘 = 执行者给自己写教材 ——
没有独立的东西检验它，而下次它照着自己写的教材做，**错误会被自己确认成经验**。

**只写事实不写结论。** 「run_tests 在 cwd=X 会 ImportError」可核对可推翻；
「用 pytest 比较好」是判据走私进执行者的上下文。无证据的 `Observation` 在**构造处**就拒绝。

**L1 门槛是「跨 ≥2 个不同 packet」而非「出现 ≥2 次」** —— 同一次执行撞 5 次是 1 条证据，
否则卡在重试循环的 packet 会单独把偶然顶成普遍约束。

### 途中修的两处静默缺陷

1. **检索嵌在 `if sources:` 里** —— 没有用户知识资源的执行，记忆一次都不会被读。
2. **经验不能和知识资源共用检索键。** 经验的相关性来自「**你是这个角色**」，
   不是「这次要做什么」。需求文本词法得分为 0，会把经验全部丢掉 ——
   写入侧越攒越多，读取侧一条出不来。

### L2 → L3 明确暂缓

不是技术难度，是**证据现在拿不到**：一条经验的证伪门只能是「判据冻结下，
带它跑与不带它跑出现显著差异」，而当前单 packet 完成率 20–40%，噪声远大于信号。
在拿到证据前直接改 SKILL.md，等于绕过项目自己设的门。

## 三十五、08-14 —— MCP 真正接通，以及两处「测试锁住谎言」

### 两个缺陷，第二个才是要害

**一、`mcp_config_dir` 全仓库无人传。** 定义了、README 写了、真机演示过，

> ★ 第二个比第一个隐蔽：第一个是「没接」，一眼看得出；第二个是「接了但接在错的地方」——
> 能跑通，只是代价荒谬。**而且因为第一个缺陷的存在，第二个从来没有机会暴露。**

补了 `describe_skipped()`，把配置自己写的开启指引原样带出来。

### 两处测试把谎言钉死了

`filesystem.json` / `git.json` 写着 `"status": "connected"` —— 而它们**根本没有 command**。
而 `test_builtin_mcp_services_load_and_say_connection_truth`（名字是 "say connection truth"）里写的是：

```python
assert by_id["filesystem"]["status"] == "connected"
```

**去修正那个字段反而会让测试变红。** 同样的断言在 `test_engine_service.py` 里还有一份。

## 三十六、08-14 —— 验收第六层与判据的生命周期

### 第六层：集成谓词的桩化检验

第五层（`vacuity_check`）抓「测试是空的」很准，但抓不到更隐蔽的一个：
**集成测试只是把各模块自己的测试又跑了一遍**。

> 各模块测试全绿 + 集成谓词全绿 ≠ 集成成立。前五层一层都判不出来。

算子：把模块 A 掏空，集成谓词必须变红。两个关键设计：

**桩必须签名保真。** 删文件得到 `ImportError` —— 那是「红对了、理由错了」：
它只证明 A 的文件存在，证明不了集成测试覆盖了 A 的**行为**。
所以走 AST 掏空函数体，保留导入、类、模块级常量。

**必须同时把该模块自己的测试藏起来 —— 这是结论成立的前提，不是优化。**
不藏的话，谓词跑全部测试时桩化 A 一定会让 A 自己的单元测试变红，
于是每个模块都显示「已覆盖」，**这个检查永远返回通过**。

> ★ 那正是它自己要防的那种零输入绿灯，只不过发生在**检查器身上**。
> 一个永远说「一切正常」的检查器，比不写更糟 —— 它让人以为查过了。

★ 门禁那两条测试差点写成假绿：最初断言 `"alpha" in verdict.detail`，
  但第五层的失败消息里会列出 `alpha/tests/test_alpha.py` —— 同样包含 "alpha"。
  那样这条测试可能是被第五层拦下而通过的、根本没走到第六层。改成断言第六层特有的措辞。

### 判据的生命周期：影子档位

判据此前是常量：写进 `DEFAULT_RULES` 就永远生效、永远存在。后果是新判据不敢加
（一上线就拦人，第一次误拦就被整条关掉，**之后再也不打开**）、旧判据不敢删。

`shadow` = 评估、记录、**但不拦截**。晋级 `enforcing` 两个条件缺一不可：
在真实案例上**命中过 ≥1 次** + **变异检验能杀死它**。

> ★ **默认是 `enforcing` 而不是 `shadow`**，方向是有意选的：
> 默认 shadow 会让新规则**静默地**不生效；默认 enforcing 可能误拦，但那是**响亮的**。
> **响亮的失败优于静默的失败。**

### 资产负债表与缺口报告

命中账本**连没命中的也记** —— 表要靠它区分「跑过 N 次一次没命中」（判据可能多余）
与「根本没人在记录」（**观测本身坏了**）。没有账本时显示 `未观测` 而不是 `0`。

首轮真实数据（3 次真实需求提交）：9 条规则各跑 3 次、命中 0、变异全被杀死 → 全部「留着」；
影子规则命中 0 → 老实停在影子里，**没被凑数晋级**；4 道门禁「未观测」（已知缺口，写在表上）。

缺口报告找的是「同一失败在 ≥N 个不同 packet 复现，且这些 packet 事前一条判据都没 fired」。
首轮结果是「**样本不足，未能判定**」—— 不是「没有缺口」，后者会是又一个零输入的绿灯。

★ **只报缺口，不自动写规则。** 让系统根据自己的失败去写判据，
  等于执行者给自己出考题，直接违反 `mustDifferFrom`。
  自进化系统里，**哪一环必须留给外部，是设计问题不是能力问题**。

## 三十九、08-15 —— A 的六条缺口：先修最基本的那条

外部核对列出 A 侧六条缺口。逐条对着代码核实，**全部属实**，然后按
「阻塞面 × 可解性」排序动手。第一条选的是 ⑤，因为它卡住的是**最基本的路径**：
打开一个新文件夹、提一个需求、什么都不发生。

### 空仓库没有 HEAD，worktree 起不来

```
spawn 失败，packet wp-xxx 保持 ready 并释放锁：
WorktreeIsolationError: fatal: invalid reference: HEAD
```

`git worktree add --detach <path> HEAD` 在**一个提交都没有**的仓库上必然失败。
后果不是崩溃 —— 是 **packet 永远停在 ready**：调和循环看不到任何转换，
就认为系统已稳定并正常退出。**使用者只看到「什么都没发生」。**

★ 为什么一直没被发现：`git_repo` 夹具**每次都建了一个提交**；
  `test_engine_service` 的 `project` 夹具虽然是空仓库，但那 33 条测试
  碰不到 worktree 那一层。**夹具假设了顺利路径**，
  于是「用户刚 git init 的空目录」这条真实路径从来没被测过。

`ensure_project_initialized()` 只在两种情况下动手，第三种一律不碰：

| 现状 | 行为 |
|---|---|
| 不是 git 仓库 | `git init` + 首个提交 |
| 是 git 仓库但一个提交都没有 | 首个提交 |
| **是 git 仓库且已有提交** | **什么都不做** |

★ 第三条是**安全判据**不是优化：在使用者已有的仓库历史上加提交，
  是不可接受的副作用。有人把 Codentum 指向真实项目时，
  它绝不能往那段历史里写东西。

★ 首个提交用 `git add -A` 纳入现有内容而不是建空提交 ——
  worktree 从这个提交检出，空提交会让 worker 看到一个**空工作区**，
  而使用者明明把文件放在那里了。

## 四十、08-15 —— scheduling.json / flow.json：根不是「缺个投影」

★ 这是本仓库同一形状的第四次：langgraph 装了零 import → `mcp_config_dir` 无人传
  → MCP 连接点在错的层 → `promote_now` 从未被调用。

### 撞车，以及一处会让桌面端整份拒收的形状

做到一半时 B 推了同一件事的另一个实现（`scheduling/wip_limiter.py` +
`ready_queue.py`）。于是出现**两个写者写同一个 `scheduling.json`**。
处置：B 的留下（在控制平面、限 running 与 review 两列、按关键路径排序），
我撤掉重复的那份 —— **两套做同一件事的机制比任何一套都糟**。

但他的产出过不了 C 的守卫：

```
B 产出   "readyQueue": [{"rank": 1, "packetId": "...", ...}]   ← 对象数组
C 守卫   isStringArray(value['readyQueue'])                    ← fail-closed
```

**整个 scheduling.json 会被拒**，WIP、队列、关键路径全都显示不出来。

★ 而这个失败在 Python 侧**没有任何信号**：守卫写在 TypeScript 里，
  控制平面的测试全绿。**两边各测各的，接缝上没有人。**

改法：`readyQueue` 改字符串数组、丰富信息挪 `readyQueueDetail`（未知键被忽略）、

## 四十一、08-15 —— 产出合入：让「accepted」不再是一句空话

worker 在隔离 worktree 写代码，证据也镜像回来了，但**代码改动一直留在 worktree 里**：

    packet 被判 accepted → 使用者打开项目 → **什么都没有**

三条拒绝，每条都是安全判据：**项目工作区不干净**（那是使用者的工作目录）、
**改动越出 ownsPaths**（I1）、**合并冲突**（中止并还原）。

★ 越界时**整批拒绝**而不是「悄悄只合法的那部分」——
  静默丢弃会让 worker 以为写成功了，而产出对不上时完全看不出发生过什么。

★ 一条**不拦但必须出声**的：找不到工作区是**信息缺失**（被清理、换机器），
  拦掉会误伤合法工作。所以放行，但结论写进 accepted 的 detail ——
  否则「合入了 3 处」和「压根没合」在状态上都是 accepted。

### 两个被测试当场抓住的真实缺陷

| 缺陷 | 后果 |
|---|---|
| `git status --porcelain` 把未跟踪**目录**折叠成一条 | 合法的 `workspace/alpha/m.py` 以 `workspace/` 出现，被误判越界。改用 `-uall` |
| git 默认 `core.quotepath=on` | 中文文件名转义成八进制，而那些路径**原样出现在给使用者看的拒绝消息里** |

★ 编码这个坑本仓库已经栽过两次（EvidenceRef 分隔符、流编码），**这是第三次**。

## 四十二、08-15 —— 角色转换表默认打开：一处范畴错误

`enforce_role_transitions` 一直默认 False，因为打开之后 coder 的 packet
会**永远停在 review**。此前的记录停在现象层，这次读契约才看清根因：

> 契约对 `RoleSpec.transitions` 的定义是「此角色可**触发**的状态转换。」

role 是**触发者**，而调和循环**不是角色** —— 它在门禁通过后代为应用。
拿 packet 自己的 role 去问「你能不能触发签字」，问的是错的人，
而它恰好把「不能给自己签字」变成了「**没有人能签字**」。

★ 顺带解掉一个看起来像不一致的东西：reviewer 要 `review` 门、
  integrator 要 `self-test` 门 —— **两者都对，因为触发者不同**。

修法是补系统侧查询 `check_system()`：**签字人 = 声明者 − packet 自己的角色**，
这是 **I2 在状态机层的落点**，与准入层的 `check_self_review` 是同一条不变量的
两个强制点。修的是范畴错误本身，不是在入口层绕过。

★ 那条钉住缺口的测试当时写着「如果它变成了 accepted，说明查询方式已经修好了」——
  **它如期红在那一行**。一条钉住缺口的测试，缺口修好时就该红。

★ 写「不能自签」那条新判据时先用 `review→accepted`，结果它是绿的 ——
  因为 reviewer 的 packet 会由 integrator 签，自签本来就轮不上。
  改用 `pending→ready`（**只有 planner 声明**）才真的暴露这条不变量。
  **一条永远绿的测试和没有测试是一回事。**

## 四十三、08-15 —— 两个会话并行改同一个工作区

期间发现**另一个会话在同一工作区并行写代码**（OTel 导出、人工审批/回滚、
RAG 向量检索）。审它的产出，找到并修了三个真缺陷：

| 缺陷 | 后果 |
|---|---|
| 回滚里 `git log` 用 `check=False` | **git 执行失败被报成「回滚成功」**（实测退出码 128 仍返回 True） |
| `RollbackResult` 文档与代码相反 | 文档写 `False` 表示无可回滚，代码返回 `True`，照文档分支的人永远等不到 |
| 人工审批先查 reject 再查 approve | **被驳回过一次就再也批不通**，operator 后来的批准被静默忽略 |

第三条最严重：`rejected → ready → 重做 → review`，那条旧 reject 还在日志里，
于是被同一条决定无限打回。人工审批的语义是**「最后一次表态算数」**，
不是「一票否决且永久有效」。

★ 审过**没问题**的也要说：RAG 的 TF-IDF 检索是干净的 ——
  并列按 `ref` 打破、浮点求和顺序确定、idf 由本轮语料算，
  满足契约「同 query + 同 index_version → 逐条相同」，
  而且文档不夸大（「不是神经网络 embedding —— 不夸大，也不假装有」）。

### 全量跑出来两条回归，幸好推之前跑了

红的是我自己那两条。根因是并行会话的一处**正确收紧**：`kind="manual"`
现在必须 operator 显式批准（此前 manual 的谓词永远不会被执行，
「有证据」就等于「验收通过」）。而我那组测试的夹具正好用 `manual` ——
**红的原因和转换表毫无关系**，那样它们测的就不是自己声称测的东西了。

★ 修的过程中我又弄红了第三条：第一版把 `_run(approve=...)` 默认设成 True，
  结果把「只有 sys: 簿记时不得验收」那条绕过去了。
  **夹具的默认值不该替某条测试做决定。**

## 四十四、08-16 —— 「可观测已落地」原来是句空话

用户问「还有什么要修的吗」。与其复述已知清单，先做一次实际排查：把
全仓库顶层符号按引用次数扫一遍，再单独查一类**这个项目反复出现的**形状 ——
**只有自己的测试在 import、生产路径零调用的模块**。

扫出来一个：`packages/engine/codentum_engine/otel.py`。

### 缺陷本身

| | |
|---|---|
| 模块 | 完整：GenAiSpan、trace/span id 派生、OTLP/JSON 序列化 |
| 测试 | `test_otel.py` 全绿 |
| 生产路径 import 它的地方 | **零** |
| 真跑一次产出的 span | **零条** |
| 材料里的说法 | 「**OTel 可观测已落地**」「『自研非 OTel』的扣分点已消除」 |
| 材料给的验证命令 | `pytest test_otel.py` —— 绿 |

★ **那条命令证明的是「编码器会编码」，不是「系统会产 trace」。**
这正是本仓库的「零输入的绿灯」在可观测这一层的复现：判据本身没错，
错在它守的东西和文档宣称的东西不是同一件事。

这与 `max_running`（08-15 删掉的死代码）同类但更重：死代码只是多余，
而这里**对外宣称了一项系统实际不具备的能力**。

### 接线时才发现的一处 API 缺陷

原 `genai_spans_from_model_response` 把 trace_id 和 chat 的 span_id
从**同一个 seed** 派生。而一次 packet 执行是多轮模型调用：

- 每轮换 seed → 一次执行被拆成 N 条互不相干的 trace
- 每轮同 seed → N 个 chat span 撞同一个 span_id

两种都不是一条能看的调用链。给它加了可选 `trace_id` 参数，让调用方
能分开指定这两者。**这个缺陷只有真接一次才会暴露** —— 单测编码器时
一次只造一条 span，撞不上。

### 接在哪、以及为什么

挂在 `_record_turn` 上：它是**每一次模型响应的唯一漏斗**。
与 `_harvest` 挂 `_write_result`、决策日志挂 `_apply_transition` 同一个做法 ——
接在漏斗上，就没有「某条分支忘了记」。

`gen_ai.system` 由装配层从 `ModelGatewayConfig.kind` 派生，不在 runner 里写死：
写死的代价是换网关后 trace 会**言之凿凿地报错误的 provider**，
而一条内容是假的 trace 比没有 trace 更坏 —— 它看起来完全正常。
那张映射表用**字典下标**而非 `.get(kind, "unknown")`：漏登记要在装配时当场炸，
不要攒一批 `system="unknown"` 的 span 等人去看 trace 时才发现。

### 判据换成守接线，并做因果检验

新判据不测编码器（那是 `test_otel.py` 的事），只测一件事：
**跑完一次，证据目录里有没有 trace。**

把 `_record_spans` 的调用摘掉 → 4 条当场变红。第 5 条（导出失败不拖垮主链路）
保持绿 —— 它守的是韧性不是存在性，本来就不该红。

还顺手守住两处容易「接上了但没接全」的地方：多轮必须共用一个 trace_id
（否则文件照样在、测试照样绿，但那不是一条调用链）；时间戳必须是真实挂钟
（全 0 的 span 在任何 Collector 里都排不出先后）。

### 副产物：一条差点写成的空转测试

`test_every_gateway_kind_has_a_gen_ai_system` 第一版用
`ModelGatewayConfig.__annotations__["kind"]` 取取值集合 —— 因为
`from __future__ import annotations`，拿到的是**字符串**，`get_args` 返回空元组，
于是 `missing` 恒为空，这条测试**恒绿**。

拦住它的是我顺手写的 `assert kinds, "取不到取值集合，这条测试会变成空转"`。
★ **写「这条判据的输入不能为空」比写判据本身更重要** —— 判据错了会红，
输入空了不会。这条已经是本项目第三次被同一句断言救下。

### 另一处：资产负债表把「未观测」写成了常量

顺着门禁那四行「未观测」查下去，发现 `GateRunner(recorder=...)` 其实
**早就接上了**（`service.py`）。真正的问题在 `judgement_ledger.py`：
门禁那几行把 runs/fired **写死成 `None`**，配一句「门禁未接命中记录」。
写的时候那句是对的，接上之后它不会变 —— 门禁哪天真记了账，表还是显示未观测。

★ 这是这张表自己要解决的那个问题的**镜像**：它立的规矩是「命中 0 次」与
「没人在记录」必须分开显示，而它自己这一行把后者写成了常量 ——
**一个写死的「未观测」和真的没观测，在表上不可区分。**
现在门禁与规则走同一条路：都去账本里查，查不到才叫未观测。

### 排查方法本身值得留下

「只被自己的测试 import」这个形状，到今天已经是第六次命中：
langgraph 装了零 import、`mcp_config_dir` 无人传、MCP 连接点在错误的层、
`promote_now()` 从未被调用、`DecisionRecord` 冻结却从未被构造，加上这次的 otel。

**共同点不是「忘了写」，是「写完了但没接上，而且没有任何测试会红」。**
单元测试天然只测模块自己，接线恰好落在每个模块测试的盲区里。
扫描脚本留在 scratchpad，值得考虑固化成第四道脚本门禁。
