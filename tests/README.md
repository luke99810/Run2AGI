# tests —— 跨模块测试

单元测试放在各自 package 里。**这里只放跨模块的。**

---

## 两个目录

| 目录 | owner | 手写？ |
|---|---|---|
| `contract/` | 无（自动生成） | ❌ **任何人都不手写** |
| `e2e/` | **A** | ✓ |

---

## contract/ —— 契约测试

**从 `packages/contracts/schemas/` 自动生成。**

生成脚本在 `scripts/`。这个目录里的文件不进任何人的 `owns_paths`——对应系统设计里"生成物不进 owns_paths"的同一条规则。

**为什么不手写**：手写的契约测试会与契约脱节，且脱节时不报错——它只是悄悄不再验证真正的契约。那时你有一堆绿灯，但它们证明的是三个月前的契约。

**改契约的正确流程**：改 schema → 重跑生成 → 提交生成结果。**不要直接改测试文件**，下次生成会覆盖掉。

## e2e/ —— 端到端验收

跨三人模块，由集成责任人（A）持有。

### 必须覆盖的

| 场景 | 验什么 |
|---|---|
| **主路径** | 需求 → 交付：Intake → Architect → Planner → QA → Coder → Reviewer → Integrator 全链路跑通 |
| ★ **并行安全** | 多个 Coder 同时改重叠路径时，锁生效，无覆盖，无合并冲突 |
| ★ **三种作弊** | 改测试 / 改契约 / 缩小范围——三条红队用例，**都必须失败** |
| **分级求助** | 卡住时按 L0 → L0.5 → L1 → L2 → L3 逐级升级，且能终止 |
| **崩溃恢复** | 中途杀进程，重启后能从检查点继续（用户会关电脑） |
| **冷启动交付** | 干净容器里从产物跑通 |

### 红队用例是这套设计的证明题

三种作弊如果有任何一种能成功，"结构性防作弊"这个论点就不成立了。**这三个用例不是普通测试，它们是论证的一部分。**

不要因为"实现还没到那一步"就注释掉——**注释掉的红队用例等于没有红队用例**。用 skip 标记并在 CI 里显式报告"N 个红队用例被跳过"。

---

## 硬约束

1. **`contract/` 的变更必须来自生成脚本**，手工提交视为违反不变量（`boundaries.yaml` 里 `no-handwritten-generated`）。
2. **e2e 不许为了跑得快而 mock 掉核心机制。** mock 掉锁的 e2e 测不到并行安全。
3. **每个 e2e 用例要写明"它证明了什么"**——写在文件头。证明不了任何东西的 e2e 只是在烧时间。
4. **跳过的用例必须显式报告**，不许静默跳过。
